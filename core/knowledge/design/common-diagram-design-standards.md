# 图表设计标准

## 目的与边界

本文件定义图表设计的决策规则：何时需要图、表达什么语义、选择什么图类型、如何控制粒度和布局。它是图表设计的最高层规则，不定义具体 Mermaid 语法。

本文件可被 AI-DLC 流程按需调用，也可独立使用。独立使用时不要求任何 AIDLC 状态（state.md、audit.md、审批流程）。

## 加载条件

需要图表设计时加载本文件。加载后按需加载下层：

1. 选择 Mermaid 作为图类型时加载 `common-mermaid-diagram-standards.md`；
2. 实际编写 Mermaid 语法时再加载 `common-mermaid-syntax-rules.md`；
3. 选择 ASCII 图时加载 `common-ascii-diagram-standards.md`。

本文件不复制下层规则。

## 与下层的分工

| 层 | 文件 | 回答的问题 |
|---|---|---|
| 设计层（本文件） | `common-diagram-design-standards.md` | 为什么画？画什么？表达什么？画几张？粒度是什么？是否拆图？使用什么图族？ |
| Mermaid 使用层 | `common-mermaid-diagram-standards.md` | Mermaid 图类型怎么选？信息怎么组织？布局规则？降级条件？ |
| Mermaid 语法层 | `common-mermaid-syntax-rules.md` | Mermaid 代码怎么写？什么语法可用？静态检查清单？ |

三层职责不重叠。本文件不定义 Mermaid 语法细节或具体图类型的节点样式。

---

## 第一节：是否需要图

不是所有信息都需要图表。以下条件满足任一时考虑图表：

- 存在三个以上实体之间的关系需要表达；
- 存在非线性的分支或循环流程；
- 存在按时间发生的多方交互；
- 存在状态迁移和生命周期；
- 存在层级结构需要可视化；
- 用户明确要求图表。

以下条件下优先使用表格或文字：

- 仅两个实体之间的简单关系；
- 线性无分支步骤（编号列表即可）；
- 字段定义和属性列表；
- 信息不足以确定关系。

## 第二节：图的目的

每张图必须有明确的单一目的。在设计前回答：

1. **这张图帮助读者理解什么？** — 一句话回答
2. **读者看完后应该能做什么？** — 判断、决策、实现或验证
3. **没有这张图会损失什么？** — 如果答案是"无"则不需要图

禁止为了"看起来专业"或"文档完整性"而画图。

## 第三节：图类型选择

基于表达目的选择图类型，不基于用户随意指定：

| 表达目的 | 首选设计语义 | Mermaid 实现（按语义优先级） | 适用示例 |
|----------|------------|------------------------------|----------|
| 系统整体结构和边界 | Architecture | `C4Context` > `C4Container` > `flowchart` + subgraph | 系统上下文、容器架构 |
| 业务步骤、决策、循环 | Flowchart | `flowchart` | 审批流程、数据处理管线 |
| 按时间发生的多方交互 | Sequence | `sequenceDiagram` | API 调用链、消息流 |
| 实体生命周期和状态迁移 | State | `stateDiagram-v2` | 订单状态、任务状态 |
| 数据实体和基数关系 | ER | `erDiagram` | 数据模型、概念模型 |
| 部署拓扑和运行时环境 | Deployment | `C4Deployment` > `architecture-beta` > `flowchart` + subgraph | 服务部署、网络拓扑 |
| 类型、接口和继承关系 | Class | `classDiagram` | 领域模型、组件接口 |
| AI/RAG 数据处理链路 | Pipeline | `flowchart LR` | Embedding → Retrieval → Generation |
| 容器内部组件结构 | Component | `C4Component` > `flowchart` + subgraph | 单服务模块划分 |
| 云/基础设施资源关系 | Infrastructure | `architecture-beta` > `flowchart` + subgraph | 云架构、CI/CD |

设计语义与 Mermaid 实现是分离的。表中的优先级符号 `>` 表示：左侧图类型语义能力更强，在目标环境验证可用时优先选择；如果目标环境不支持或渲染不可靠，则降级到右侧方案。

### Architecture 图类型选择原则

Architecture 图不等同于 `flowchart`。选择 Architecture 的 Mermaid 实现时：

1. **首先判断语义**：这是"系统结构"还是"处理流程"？
   - 系统结构（什么组件在这里、边界在哪里）→ Architecture 语义 → 优先 C4 图类型；
   - 处理流程（数据怎么流动、经过哪些步骤）→ Pipeline/Flowchart 语义 → 使用 `flowchart`。
2. **不因节点多就退化为流程图**：节点多时应拆图（Overview + Detail），而非把架构画成流水线。
3. **同时存在 Architecture 和 Pipeline 两种语义时**：优先考虑 Overview + Detail 拆图——Overview 负责 Architecture，Detail 负责 Pipeline。
4. **环境验证**：使用 C4 或 architecture-beta 前，确认目标环境支持（参见 `common-mermaid-diagram-standards.md` 的 Mermaid 能力验证章节）。

当表达目的不明确时，先确认目的再选择图类型。用户指定的图类型与目的冲突时，说明推荐类型和理由，由用户决定。

## 第四节：信息边界

图表只表达与目的直接相关的信息：

- 只呈现理解关系所需的节点和连线；
- 详细字段、约束和实现细节保留在正文或表格；
- 节点标签使用项目术语，控制在 2-6 个词；
- 连线标签使用动词或关键事件，控制在 1-4 个词；
- 不在图中堆叠段落式文本。

## 第五节：事实真实性（强制）

图表不得创造业务事实。允许的信息来源：

1. 用户明确提供的信息；
2. 当前代码中可验证的结构；
3. 当前项目文档中已记录的内容；
4. 当前 AIDLC 已批准产物（仅在 AIDLC 上下文中）；
5. 用户明确声明的假设。

不得因为"通常有"或"企业常见"而自动加入未经确认的组件、服务或关系。

信息不足时优先提问。用户明确允许推测时，假设信息必须在图中或图后明确标记，并在图后列出假设清单。具体标记语法由 `common-mermaid-diagram-standards.md` 和 `common-mermaid-syntax-rules.md` 决定。

## 第六节：图粒度与拆分

### 粒度判断

单张图应保持清晰可读。综合评估以下因素：

| 因素 | 单图适宜 | 考虑拆分 | 建议拆分 |
|------|----------|----------|----------|
| 节点数量 | ≤ 8 | 9-15 | > 15 |
| 关系/连线数量 | ≤ 12 | 13-20 | > 20 |
| 交叉边 | 0-1 | 2-3 | > 3 |
| 嵌套层级 | 1 | 2 | > 2 |
| 节点标签平均长度 | ≤ 4 词 | 5-6 词 | > 6 词 |

以上为参考指标，最终判断基于：**读者能否在 10 秒内理解图的主干结构**。

### 拆分策略

支持按层级拆分：

| 层级 | 内容 | 典型节点数 |
|------|------|------------|
| System Context | 系统与外部参与者的边界 | 3-7 |
| Container | 系统内的主要容器/服务 | 5-12 |
| Component | 单个容器内的组件 | 5-15 |
| Detail | 单个组件内的关键逻辑 | 3-8 |

拆分后：

- 每张图独立可理解，有明确标题；
- 正文说明图之间的层级关系；
- 上层图标注"详见下层图"的指示，但不强制使用 Mermaid 超链接。

### 语义视角拆分（Semantic Decomposition）

图表拆分不仅依据节点数量和连线密度，还要依据语义视角。不同语义视角服务于不同的阅读目的：

| 语义视角 | 回答的问题 |
|----------|------------|
| Architecture | 系统由什么组成？边界在哪里？ |
| Pipeline / Flow | 数据或请求如何流转？经过哪些步骤？ |
| Sequence | 参与方之间按什么时序交互？ |
| Deployment | 组件运行在哪里？网络关系如何？ |
| Data Model | 实体之间是什么基数关系？ |

规则：

1. 当一张图同时承担两个以上独立语义视角时，必须主动评估是否拆分；
2. 推荐 Overview + Detail 模式：
   - **Overview**（Architecture 视角）：回答"系统由什么组成、边界在哪里"——展示组件和职责，不展示详细步骤；
   - **Detail**（Pipeline/Sequence 等视角）：回答"某个局部如何工作"——展示步骤、时序或数据流转；
3. 不应为了减少图表数量而强行合并不同语义；
4. 即使节点数量低于拆图阈值，只要拆分能够显著提升可读性和阅读效率，也允许拆图；
5. Architecture 图的核心价值是展示"什么在这里、职责是什么"，而非"数据怎么流动"——后者属于 Pipeline 或 Sequence 视角。

### 节点识别原则

不是用户输入中的每个条目都应成为图中的独立节点。区分：

| 类别 | 应作为 | 示例 |
|------|--------|------|
| Entity / Component / Actor | 独立节点 | 用户、LLM、向量数据库、文档解析服务 |
| Action / Event | 连线标签或连线 | 返回答案、上传文档、触发通知 |
| Relationship / Attribute | 连线标签或正文 | 包含、依赖、1:N 关系 |

动作（如"返回答案"）默认优先作为关系/事件标注在连线上，而非独立组件节点。只有当动作对应独立的部署单元或独立服务时，才提升为节点。

### 抽象关系保持原则

Overview 对 Detail 进行组件聚合时：

- 可以隐藏内部节点；
- 可以合并同一职责域中的多个组件；
- 可以减少内部连线；
- 但不得改变原始关系的语义主体和方向。

例如，Detail 中存在：

- Embedding → VectorDB
- Retrieval → VectorDB

Overview 可以抽象为：

- Document Processing → VectorDB
- Retrieval → VectorDB

但不得错误抽象为：

- QA Engine → VectorDB（除非 QA Engine 本身就是直接访问 VectorDB 的职责主体）

当聚合后无法准确表达关系主体时，应保留关键内部节点，而不是过度抽象。

### Subgraph 语义原则

subgraph 用于表达：

- 系统边界；
- 职责边界；
- 部署边界；
- 信任边界。

subgraph 本身默认不是业务实体或组件。除非聚合后的职责域本身就是明确的能力边界，否则不要为了减少连线而直接把关系连接到 subgraph。

当外部节点需要与职责域内部组件建立关系时：

- 优先连接到真正承担职责的节点；
- 如果多个内部节点共同承担入口职责，可选择明确的入口节点；
- 不得为了视觉简化而改变真实关系。

### 核心原则

**可读性优先于信息完整性。** 不为完整而生成蜘蛛网图。信息太多时拆图，不要把所有内容塞进一张图。

## 第七节：布局与美观

### 布局方向

- 顺序流程、层级结构：默认 `TD`（上到下）；
- 时间线、管线、阶段链路：使用 `LR`（左到右）；
- 方向必须显式声明，不依赖默认值。

### 层级结构

- 主流程节点在图的主干线上，从入口到出口保持单一方向；
- 辅助节点（错误处理、可选分支）偏离主干；
- 外部系统和数据存储放在图的边缘或底部；
- 使用 subgraph 或 Boundary 分组稳定的职责边界，嵌套不超过两层。

### 节点密度

- 同一层级的并行节点不超过 4 个；
- 相邻层级之间保持 1:1 到 1:3 的连接比；
- 避免单个节点向外发散超过 4 条连线。

### 连线

- 保持连线方向一致（主流程单向）；
- 避免反方向回流穿过多个节点（循环用明确的回退边表示）；
- 避免长距离跨层连线；需要时拆图。

### 主流程突出

- 主流程使用实线连接；
- 次要关系、可选路径使用虚线或注释说明；
- 不使用颜色作为唯一信息载体；状态和分类必须同时通过文字表达。

### 图的标题

每张图在正文中必须有明确标题（Markdown 标题或加粗文本），说明图的目的。标题紧邻 Mermaid 代码块之前。

### 视觉层级

不是所有节点和关系都应该拥有相同视觉权重。按重要性分层：

| 层级 | 内容 | 视觉优先级 |
|------|------|------------|
| Level 1 | 核心系统 / 主流程 | 最高 — 主干线、显眼位置 |
| Level 2 | 核心组件 / 主要参与者 | 高 — 主干线附近、清晰标签 |
| Level 3 | 辅助组件 / 次要依赖 | 中 — 边缘位置、简短标签 |
| Level 4 | 实现细节 / 注释 | 低 — 优先进入正文或详细图 |

默认 overview 图只展示 Level 1~3。Level 4 优先放入正文描述或独立的 Detail 层图。

核心原则：**核心路径必须具有最高视觉优先级。** 辅助信息不得干扰对主干结构的理解。

### Architecture 视觉质量要求

对于 Architecture 图，优先考虑以下视觉质量目标：

1. **清晰的系统边界**：系统内外必须有明确的视觉分隔（Boundary、subgraph 或分组）；
2. **明确的层级**：组件之间的层次关系（调用方/被调用方、上下游）通过布局位置体现；
3. **参与者区分**：外部参与者（Person、外部系统）与系统内部组件有视觉区分——C4 图类型天然支持，flowchart 中通过节点形状区分；
4. **数据存储区分**：数据库/存储节点与服务节点有视觉区分——C4 使用 ContainerDb/ComponentDb，flowchart 使用圆柱形节点；
5. **主次关系**：核心依赖使用实线，次要或可选依赖使用虚线或更细连线；
6. **避免蜘蛛网**：当连线交叉超过 3 处时，优先拆图而非调整布局；
7. **避免把 Architecture 画成 Pipeline**：Architecture 图展示"什么在这里"，不是"数据怎么流"——如果图看起来像流水线，检查是否应该拆分为 Architecture + Pipeline；
8. **避免拥挤**：单个 subgraph/Boundary 内节点不超过 6 个；超过时考虑进一步拆分或抽象；
9. **利用图类型能力**：C4 图类型本身提供 Person/System/Container/Component 等语义区分，应充分利用而非仅用标签文字区分；
10. **架构可读性优先**：图表应优先追求"架构可读性"——即读者能快速理解系统结构——而不是单纯语法正确。

### Architecture Quick Scan

架构图应能在约 3 秒内让读者识别：

1. 系统边界（什么在系统内，什么在系统外）；
2. 核心入口（用户或外部系统从哪里进入）；
3. 核心业务能力（系统做什么）。

并在约 10 秒内理解主要依赖关系（谁调用谁、数据流向哪里）。

无法满足此标准时，优先简化或拆图，而非增加图例和注释来补救。

## 第八节：输出格式

### 默认输出

默认输出为 Markdown 文件中的 Mermaid fenced code block：

- 代码块语言标识使用 `mermaid`；
- 一个 Markdown 文件可包含多张图，每张图有独立标题；
- Kiro Markdown Mermaid Preview 为默认预览方式。

### SVG 定位

SVG 是渲染中间产物或交付产物，不是 Markdown 默认源文件格式：

- 默认文档产物为 Markdown + Mermaid fenced code block；
- 仅以下情况生成 SVG：用户明确要求、Mermaid CLI 验证、DOCX/PDF 导出流程、其他明确要求图片文件的交付流程。

### 禁止默认生成

- 不得默认生成 SVG、PNG 或 PDF；
- 不得为了"渲染成功"自动生成图片文件；
- 不得要求安装额外渲染器才能查看。

### 导出条件

仅在用户明确要求"导出 SVG"、"生成 PNG"或"生成图片"时进入额外导出流程。导出不改变默认的 Markdown 内嵌格式。

## 第九节：降级规则

以下情况从 Mermaid 降级为其他格式：

| 条件 | 降级目标 |
|------|----------|
| 目标环境不支持 Mermaid 渲染 | ASCII 图（加载 `common-ascii-diagram-standards.md`） |
| 信息结构不适合任何图类型 | 分层表格 + 编号列表 |
| 单图节点超过 25 且无法按业务边界拆分 | 多级表格 + 正文描述 |
| Mermaid 语法无法表达目标关系 | 正文描述 + 参考外部工具建议 |
| 高级图类型（C4、architecture-beta）在目标环境验证失败 | 降级为 `flowchart` + subgraph |

降级后的内容必须保留完整的业务语义。

## 第十节：Diagram QA

生成图表后执行自检：

1. **目的检查**：图是否回答了设计时确定的单一目的？
2. **事实检查**：图中所有节点和关系是否有明确来源？有无假设未标记？
3. **粒度检查**：能否在 10 秒内理解主干结构？是否需要拆图？
4. **可读性检查**：标签是否简短清晰？连线是否方向一致？有无蜘蛛网？
5. **一致性检查**：图中术语是否与正文和项目术语一致？
6. **降级检查**：如果 Mermaid 不渲染，正文是否仍能传达关键信息？
7. **视觉冲突检查（Visual Conflict Check）**：
   - 是否存在多个视觉中心（读者不知道先看哪里）？
   - 是否存在不必要的大范围空白？
   - 是否存在节点拥挤区域？
   - 是否存在不同语义的连线交汇（Architecture 连线与 Pipeline 连线混在一起）？
   - 是否需要读者在不同区域之间来回跳跃才能理解主干？
   - 拆成多图是否能够明显提升理解效率？
8. **语义混合检查**：Architecture 图是否混入了 Pipeline 语义？是否需要 Overview + Detail 拆分？

自检未通过时修复后再输出。无法修复时说明原因并提供降级方案。

## 第十一节：独立调用规则

本能力可独立于 AIDLC 调用。独立调用时：

- 不要求 state.md、audit.md 或任何 AIDLC 状态；
- 不要求用户先完成需求分析、应用设计等前置步骤；
- 不更新 AIDLC 状态或审计记录；
- 不等待审批流程；
- 仅基于用户提供的信息和可访问的代码/文档设计图表。

独立调用的输入为用户提供的语义描述或指向已有代码/文档的引用。输出为 Markdown 中的 Mermaid 图表和自检结果。

## 第十二节：AIDLC 内调用

在 AIDLC 流程中被调用时：

- 调用方提供语义上下文（已批准产物、设计决策等）；
- 本能力根据上下文设计图表并返回；
- 不操作 state.md 或 audit.md；
- 不发起审批或标记完成；
- 调用方负责将产物纳入自己的流程。

## 第十三节：Mermaid 验证

验证层级沿用 `common-mermaid-diagram-standards.md` 的定义：

1. Level 1：静态结构检查 → 记录为"静态检查通过"；
2. Level 2：Mermaid CLI 语法解析 → 记录为"CLI 语法解析通过"；
3. Level 3：Mermaid CLI 实际 SVG 渲染 → 记录为"CLI 渲染通过"；
4. Level 4：Kiro Markdown Mermaid Preview 实际视觉检查 → 记录为"Preview 渲染通过"。

验证环境优先级：

- 最终目标为 DOCX/PDF 交付时：Level 3（Mermaid CLI SVG 渲染）必须通过；
- Kiro 内部 Markdown 使用：至少完成 Level 1，条件允许时执行 Level 2；
- 无法执行 Mermaid CLI 时必须明确标记"未执行真实渲染验证"。

不为验证目的自动生成 SVG（除非是 Level 3 验证本身）。
