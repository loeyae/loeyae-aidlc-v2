# 图表设计标准

## 目的与边界

本文件定义图表设计的决策规则：何时需要图、表达什么语义、选择什么图型、如何控制粒度、布局和可读性。新图表的 SVG 设计规则以开源 [Blueprinter](https://github.com/SonicBotMan/blueprinter) 为唯一设计层参考，重点吸收其[图型与设计规则](https://github.com/SonicBotMan/blueprinter/blob/main/skill/references/svg-styles/diagram-types-and-rules.md)、[布局最佳实践](https://github.com/SonicBotMan/blueprinter/blob/main/skill/references/svg-styles/svg-layout-best-practices.md)、[生成策略](https://github.com/SonicBotMan/blueprinter/blob/main/skill/references/svg-styles/svg-generation-strategy.md)和[图标规则](https://github.com/SonicBotMan/blueprinter/blob/main/skill/references/svg-styles/icons.md)。AIDLC 只将这些规则作为 SVG 源设计约束使用，不内置或运行 Blueprinter；SVG 源字段、Provider 适配、静态安全和验收契约由 `common-svg-diagram-standards.md` 定义。

本文件可被 AI-DLC 流程按需调用，也可独立使用。独立使用时不要求任何 AIDLC 状态（state.md、audit.md、审批流程）。


## 统一单色视觉基线（强制）

本节是所有新建、调整和迁移图表的统一视觉事实来源，优先于 Blueprinter 中关于配色、填充、图例和装饰性注释的可选建议。业务语义只能由文字、形状、边界、方向和线型共同表达，不能依赖颜色。

| 项目 | 统一值 | 约束 |
|---|---:|---|
| 画布背景 | `#ffffff` | SVG 必须有覆盖完整 `viewBox` 的不透明白色 `rect[data-canvas-background]`；不得使用透明画布或其他背景色 |
| 框体填充 | `none` | 节点、判断、分组、泳道、系统边界和其他框体均不设置背景色 |
| 视觉墨色（业务对象） | `#000000` | 业务节点边线与文字、关系线、箭头和边标签必须黑色；不得使用灰色、强调色或语义色 |
| 结构性分组层级 | `#666666`（受限例外） | 仅 `styleRole: structural` 的非业务泳道、阶段或区域框及其标题使用；不得表达状态、责任、风险、确认或其他业务语义。系统/责任/信任等业务边界使用 `business-boundary` 并保持黑色 |
| 字体 | `Microsoft YaHei, 微软雅黑, sans-serif` | `Microsoft YaHei`/微软雅黑必须是首选字体；后备字体只用于目标环境缺字或未安装时继续渲染，不得在同图混用字体 |
| 框体文字 | `16` | 节点文字、分组/泳道标题及框体内详情统一字号；不得用缩小详情字号塞入框体 |
| 连线标签 | `14` | 全图所有边标签统一字号，且必须小于框体文字 |
| 框体/连线线宽 | `2` | 节点轮廓、分组边界、泳道边界、生命线和连接器统一线宽 |
| 箭头 | `10 × 10` | marker 与独立 `data-edge-arrow` overlay 使用同一源坐标尺寸；`markerUnits="userSpaceOnUse"` |
| 标签—连线净空 | `6` | 以实际文字 bbox 到线段的最短距离计算，不包含虚构背景框内边距 |

边标签不得使用 `rect`、描边、底色、光晕或遮罩。标签应放在所属水平、垂直或斜向线段的中点，沿线段法向移到线外：横线标签放在线的上方或下方，竖线标签放在线的左侧或右侧；实际文字 bbox 与所属及无关连线均不得相交。多折边优先选择最接近整条路径中部且能容纳文字的线段；候选线段净空不足时调整路径或布局，不能给标签增加背景框。

SVG 内禁止全局图例和全局备注说明层，不生成 `legend`、`annotations[]`、`data-legend-item` 或 `data-note`。视觉差异必须由对象自身或紧邻对象的明确文字就地说明；较长解释、设计理由、验收状态和待确认事项写入相邻 Markdown、Design Notes 或 evidence，不进入图表画布。结构化 expected contract 的 `legend_ids` 与 `annotation_ids` 必须为空。

## 是否需要图

不是所有信息都需要图表。以下条件满足任一时考虑 SVG 图：

- 存在三个以上实体之间的关系需要表达；
- 存在非线性的分支或循环流程；
- 存在按时间发生的多方交互；
- 存在状态迁移和生命周期；
- 存在层级结构需要可视化；
- 用户明确要求图表。

以下条件下优先使用表格或文字，不生成 SVG：

- 仅两个实体之间的简单关系；
- 线性无分支步骤；
- 字段定义和属性列表；
- 信息不足以确定关系；
- 目录树、可复制命令或单行状态表达。

## 图的目的

每张图必须有明确的单一目的。设计前回答：

1. **这张图帮助读者理解什么？** — 一句话回答；
2. **读者看完后应该能做什么？** — 判断、决策、实现或验证；
3. **没有这张图会损失什么？** — 如果答案为“无”，则不需要图。

禁止为了“看起来专业”或“文档完整性”而画图。

## 图类型选择

基于表达目的选择图型语义，不基于历史渲染器的语法限制：

| 表达目的 | SVG 场景语义 | 适用示例 |
|---|---|---|
| 系统整体结构和边界 | Architecture / Context / Container | 系统上下文、容器架构 |
| 业务步骤、决策、循环 | Flowchart | 审批流程、数据处理管线 |
| 按时间发生的多方交互 | Sequence | API 调用链、消息流 |
| 实体生命周期和状态迁移 | State | 订单状态、任务状态 |
| 数据实体和基数关系 | ER | 数据模型、概念模型 |
| 部署拓扑和运行时环境 | Deployment | 服务部署、网络拓扑 |
| 类型、接口和继承关系 | Class | 领域模型、组件接口 |
| AI/RAG 数据处理链路 | Pipeline | Embedding、Retrieval、Generation |
| 容器内部组件结构 | Component | 单服务模块划分 |
| 云/基础设施资源关系 | Infrastructure | 云架构、CI/CD |

Architecture 图回答“什么在这里、边界在哪里”；Pipeline/Flowchart 图回答“如何流转、经过哪些步骤”。两种语义同时存在时，优先拆为 Overview + Detail，而不是强行合并。

## 图型单一目的与拆图决策

Architecture / Context 图用于表达“有哪些领域、边界在哪里、静态关系是什么”；Flowchart / Pipeline 图用于表达“业务如何流转、依赖如何按过程发生”。领域分类边界与业务过程流不是同一种阅读目标，不能仅靠实线/虚线或箭头差异把它们压在一张图中。

当一张图同时承载领域分类边界和业务过程流、数据流或按过程发生的领域依赖时，默认拆为：

1. **领域总览图（Architecture / Context）**：只保留领域、边界、成员归属和静态关系；
2. **关键域依赖/业务流图（Flowchart / Pipeline）**：只保留过程顺序、依赖发生条件、数据流或反馈关系。

如果决定保留单图，`Design Notes` 必须同时记录：

- 两类语义为何不能拆，以及读者唯一的理解目标；
- 静态边界、静态关系、依赖关系和过程流分别如何区分；
- 常规查看、适合窗口、放大查看三种状态的可读性证据；仅有 SVG 源而没有目标 Provider 时，对应状态必须记录为 `UNVERIFIED`，不能写成通过。

不得只通过不同线型而不加就地文字或结构化区分，同时表达成员归属、约束关系、数据流和执行流程。拆图状态、混合语义和证据字段见 `common-svg-diagram-standards.md` 的结构化契约；没有结构化清单时，Design Notes 仍必须以同名字段记录。

## 信息真实性与边界

图表不得创造业务事实。允许的信息来源仅限：

1. 用户明确提供的信息；
2. 当前代码中可验证的结构；
3. 当前项目文档中已记录的内容；
4. 当前 AIDLC 已批准产物（仅在 AIDLC 上下文中）；
5. 用户明确声明的假设。

## SVG 所属文档位置上下文

图表的业务语义默认从 SVG 所属文档位置的上下文获取，而不是从 SVG 坐标、当前折线路径或节点短标题推断。来源解析顺序为：`.diagram.json` 的 `document`/`sourceBasis`（如有）、引用该 SVG 的 Markdown 文件及对应章节、SVG/sidecar 所在文档目录中明确关联的相邻正文。SVG 路径只是定位信息，不是业务事实来源。

开始新建或调整图表前，应读取 SVG、sidecar、所属文档的对应章节和已加载的图表规范。若同一 SVG 被多个文档引用，必须以当前目标文档或 sidecar 明确声明的文档为准；若无法唯一确定上下文，返回 `NEEDS_CONTEXT`，不得根据几何形状猜测业务关系、流程状态、回路语义或分支含义。


优化布局、拆图、换行或应用视觉风格时，**不得**删除业务动作、改变边方向、合并语义不同节点、调换状态含义，或省略决策分支。完整语义以结构化源和相邻正文为准，视觉效果只能服务于语义。

## 可检查的人类手绘式视觉目标

“人类手绘式”在本仓指 **human-organized-light（人工整理、轻量表达）**：图表像经人有意识组织过，而不是把随机性、纹理或不规则路径当作风格。它不是主观“好看”的替代词，也不得降低语义、几何或可访问性要求。

### 允许与禁止的视觉表达

- 允许使用适度圆角、清晰层级、自然留白和规整但不机械的分组；所有对象仍须遵守统一白底、无填充和黑色墨线基线；
- 连线可以使用稳定的正交或经验证的自然路径，但主流程方向、端口和箭头必须可辨识；
- 禁止随机抖动、装饰性噪点、纸张纹理、模糊、低对比度、栅格化“手绘”贴图或不确定性 SVG 变形；
- 不得通过夸张手绘效果掩盖文字裁切、节点重叠、连线穿越、空白失衡或语义缺失；
- 不得在通用 `.diagram.json` 中臆造渲染器未支持的 `roughness`、`sketch`、`visualStyle` 等字段。只有 Provider 实际支持且已验证时，才可在其适配层使用对应样式；验证记录必须说明 Provider 和实际效果。

### 必须可验证的结果

| 目标 | 通过条件 | 最低证据 |
|---|---|---|
| 不空 | 内容边界（节点、分组、端点、箭头和标签）由实际范围计算；每侧留白均为稳定内边距，不使用无意义的大面积空白填充画布 | 结构化源边界检查或渲染后几何检查 |
| 不挤 | 节点、文字、标签和非相连连线的可视边界不重叠；相邻元素保留至少一个文本行高或等价的可读间距 | 几何检查与实际视觉检查 |
| 不穿越 | 连线不穿过非端点节点、节点文字、无关分组边界或无关标签；允许共享的仅是同一声明端口 | 几何检查 |
| 不遮挡 | 白色画布、无填充分组边界、节点、标签、连接器和标题按层级呈现，任一对象不遮挡另一个对象的业务信息 | 几何检查与实际视觉检查 |
| 不重复 | 节点、连线、分组和标签的稳定 ID 与显示文本均无非语义重复；文本规范化多次执行结果不变 | 结构检查与语义检查 |
| 可缩放 | 在常规浏览器查看、适合窗口查看和放大查看三种状态下，标题、节点、边标签和箭头均可读且未裁切 | 三种状态的实际视觉证据 |
| 不改义 | 输出 SVG 的节点、边、方向、端口、分支标签、状态转换和边界与结构化源一致 | 源与 SVG 的语义对照 |

颜色、位置、线型或手绘效果不得成为唯一的业务语义载体；关键含义必须同时由标签、箭头、形状或正文表达。

## 就地视觉语义与无全局说明层

图表不设置全局图例或全局备注说明。节点形状、边界、箭头方向、实线/虚线等视觉差异只能作为文字语义的辅助，不得单独承担关键含义。

- 判断节点通过菱形和每条出口边的可见标签共同表达；起止、步骤、边界和状态均保留自身明确名称；
- 实线、虚线、回路、反馈或双向关系必须在对应边上直接标注业务含义，不能让读者查阅全局图例后再反推；
- 分组、泳道和系统边界使用框体标题及成员结构表达，不使用背景色，也不以全局说明解释成员归属；
- `designNotes.visualSemantics` 仍记录形状、线型和分组角色的语义或装饰用途；存在语义化差异时，`legendDecision.status` 使用 `exempt` 并提供逐对象 `inlineSemanticEvidence`，表示已就地表达而不是生成图例；不存在差异时使用 `not-needed`；
- 需要长篇说明时移到图表相邻正文；需要表达可连接的业务事实时建模为普通业务节点或关系，不能伪装成无连接的全局备注。

## 粒度、拆分与画布控制

### 粒度与拆分触发条件

| 因素 | 单图适宜 | 考虑拆分 | 必须作出拆分决策 |
|---|---:|---:|---:|
| 节点数量 | ≤ 8 | 9–15 | > 15 |
| 关系/连线数量 | ≤ 12 | 13–20 | > 20 |
| 非端点交叉边 | 0–1 | 2–3 | > 3 |
| 分组嵌套层级 | 1 | 2 | > 2 |
| 节点标签平均长度 | ≤ 4 词 | 5–6 词 | > 6 词 |
| 同一方向连续主流程层级 | ≤ 6 | 7–10 | > 10 |
| 画布宽高比 | 1:1–3:1 | 3:1–4:1 | 超过 4:1 或低于 1:4 |

达到“必须作出拆分决策”阈值时，不得默认继续压缩单图。必须按业务阶段、系统边界、角色边界或独立语义视角拆分；若保留单图，`Design Notes` 必须说明理由，并以三种阅读状态的实际视觉检查证明没有损害可读性。

拆分规则：

1. 在自然的业务阶段、系统边界、角色边界或已完成的决策链之后拆分；
2. 相关图使用“上一图继续”“下一图继续”或等效的明确衔接标识，并在正文说明衔接点；
3. 拆分后不得丢失节点、边、分支条件、状态转换或方向；
4. 不得从一个不可分割的判断到结果链中间截断；需要展开时保留完整决策链，或把未展开部分明确标为边界节点；
5. 异常、重试、反馈等复杂支路优先拆为独立子图，而不是挤进主流程。

### 主阅读方向、主轴与业务层级

生成或调整图表时，必须先在结构化 `designNotes.layout` 中声明主阅读方向和主轴，再计算节点、路径和边标签的实际边界。该声明属于共享 V1 语义契约，不是 Provider 私有字段：

```json
{
  "direction": "<TB-or-LR>",
  "mainAxis": "<computed-axis>",
  "layerTolerance": "<computed-tolerance>",
  "symmetryGroups": [{"nodeIds": ["<node-id>", "<node-id>"], "tolerance": "<tolerance>"}],
  "mergeNodes": [{"nodeId": "<node-id>", "reason": "<business-merge-reason>"}],
  "branchLayerExceptions": [],
  "branchPortExceptions": [],
  "readabilityEvidence": {
    "normal": {"status": "UNVERIFIED", "evidence": "<provider-evidence-or-reason>"},
    "fit": {"status": "UNVERIFIED", "evidence": "<provider-evidence-or-reason>"},
    "zoom": {"status": "UNVERIFIED", "evidence": "<provider-evidence-or-reason>"}
  }
}
```

- `direction` 只能为 `TB`（由上到下）或 `LR`（由左到右）；`mainAxis` 是主轴坐标；`layerTolerance` 是同层坐标允许的最大差值。
- `TB` 图使用 `y` 表达业务层级，分支结果默认处于同一 `y` 层；`LR` 图使用 `x` 表达业务层级，分支结果默认处于同一 `x` 层。默认规则只可由已声明的跨组、显式换行、障碍避让或不同业务层级例外放宽，并必须逐边记录原因。
- 首层多个外部实体必须围绕主轴均匀分布。使用 `symmetryGroups` 声明需要对称检查的节点集合；节点中心到主轴的距离必须相等，且集合本身必须处于同一层。
- `TB` 图的分支结果默认从目标节点 `top` 端口进入，最后一段连接线沿垂直主轴方向；两个分支应分别从判断节点的 `right`、`left` 侧出线。`LR` 图的分支结果默认从目标节点 `left` 端口进入，最后一段连接线沿水平主轴方向；两个分支应分别从判断节点的 `top`、`bottom` 侧出线。
- 多条边进入同一节点时，该节点必须出现在 `mergeNodes` 并有明确汇合理由；汇合节点可以使用 `top`/`bottom` 等其他合法端口，但普通分支不得借用汇合例外。
- `readabilityEvidence.normal`、`fit`、`zoom` 分别对应常规、适合窗口、放大视图；状态只能为 `PASS`、`FAIL` 或 `UNVERIFIED`。存在 `FAIL` 时不能宣称完整通过；没有目标 Provider 或浏览器证据时必须为 `UNVERIFIED`。
- 业务层级、阅读顺序和语义清晰度优先于“一屏显示”。允许扩展画布高度并产生纵向滚动；禁止整体缩放、缩小字体、压扁节点间距、改变分支层级或把注释放到流程主体旁边来适配固定窗口。

#### 主轴优先、端口扇出与同侧通道

布局完成后，实体间距不得被解释为全图等距。共享 geometry profile 必须同时声明方向性主轴净空：以当前布局的参考矩形长边和高度为基准，`LR` 图的主轴相邻实体边界净空至少为 `0.5 × referenceLongSide`，`TB` 图的主轴相邻实体边界净空至少为 `1.0 × referenceHeight`；形状尺寸、文本尺寸、分支整组外移和业务层级造成的更大间隔应保留。actual 使用 `designNotes.layout.geometryProfile.axisSpacing`（含参考矩形宽高、长短边和 LR/TB 最小值），expected 使用 `route_contract.geometry_profile.axis_spacing`，两者必须逐字段一致。该规则是方向性下限，不要求不同形状、不同层级或不同分支的间隔相等。

布局和路由必须按以下优先级决策：先将连续主流程按主阅读方向排在主轴上，再将同一业务层的并列实体在垂直主轴方向对称、均匀分布，最后才计算分支、汇合、回路和例外边；不得为了消除一处交叉而破坏主流程顺序、主轴或同层关系。节点位置、尺寸、端口、标签、分组边界或画布变化后，必须枚举该对象全部 incident edges 和通道受影响的邻边，先重算主轴/层级/可用净空，再按直达 → 一折 Manhattan → 两折 Manhattan → 必要外侧 lane 重新选择路径；不得只缩短或平移旧折线。

交叉控制属于上述路由决策的低优先级优化，不是机械的零交叉硬目标。在合法候选路径中，优先级依次为：业务语义与主流程主轴连续性 → 业务层级、同层均衡与已声明对称 → 源/目标的就近合法端口和实体外侧出入 → 直达/少折点的合法 Manhattan 路径 → 非端点交叉数量最少。不得为了消除单个交叉而破坏更高优先级的主轴、层级、就近出入或路径合法性。无法同时消除时，可以保留必要交叉，但必须使用 `designNotes.layout.crossingExceptions` 记录实际边对和理由，并确认交叉不触及节点、文字、标签、箭头或关键端点，且方向和业务语义可读。既有图的布局迁移可用 `changeImpactReview` 记录 baseline、移动节点、受影响边及逐边复核；新建图不要求伪造历史 baseline。

- 单一正向出边优先从主轴前进方向离开：`TB` 使用 `bottom` 或菱形下顶点，`LR` 使用 `right` 或菱形右顶点；对应的单一正向入边分别优先经 `top` 与 `left` 进入。
- 分支布局计划必须为每个有多个正向出口的判断节点记录唯一 `primaryEdgeId`；该边表示该组的主流程出口。`TB` 图的 primary edge 优先从 `bottom` 或菱形下顶点离开，`LR` 图优先从 `right` 或菱形右顶点离开。其他分支边使用垂直主轴的侧端点：`TB` 为 `left/right`，`LR` 为 `top/bottom`；两个或以上其他分支必须在两侧分布并使用边界偏移区分端点。对没有 branch-port 例外的 primary edge，源节点中心与目标节点中心必须严格共享主轴：`TB` 的中心 `x` 相同，`LR` 的中心 `y` 相同。没有确认的 primary edge 时返回 `NEEDS_CONTEXT`，只有真实端口/障碍例外才可声明 `branchPortExceptions`，不得默认把所有出口放到两侧。
- 需要偏离主轴的边遵循同侧通道优先：源、目标在主轴同一侧时，应从该侧离开、在该侧通行并从该侧进入；不得无障碍地从左侧绕到右侧后再回左侧，或形成上下/左右的 S 形折返。源、目标分居主轴两侧时，最多允许一次最短的跨轴过渡。
- `loopLanes` 的边必须使用声明的外侧 lane，并在该侧和最小 lane 偏移约束内采用最少折点的合法回折路径；不得因已声明回路保留多余折点或外绕。跨侧、背向端口或更多折点只有在业务端口语义、真实障碍或可读间距无法满足时允许，并通过 `sideSwitchExceptions: [{ edgeIds, reason }]` 声明原因。
- 连线交叉的目标是主流程零歧义而非机械零数量。交叉默认避免；若消除交叉会破坏主轴、同层业务顺序或造成更长、更难读的折返，可为每个声明边对保留必要交叉。它必须不触及节点、文字、标签、箭头或关键端点，边方向和语义可区分，且在 `crossingExceptions: [{ edgeIds: ["edge-a", "edge-b"], reason }]` 中声明。非零共线重叠、未声明交叉、节点/文字/标签穿越始终失败。



以下约束用于防止生成器为了适配一屏而破坏业务层级；它们是通用验收要求，不绑定任何项目节点、边 ID、业务路径或坐标：

- 业务层级、同层对称、分支端口和回路 lane 必须从当前图的结构化设计记录中读取，并由 expected contract 指定的语义意图对照 actual 结构；不能把某个历史图的坐标或名称复制为默认规则。
- 图表只保留业务主体和就地标签；不得添加全局图例或全局备注。空间不足时扩展画布并允许纵向滚动，不能用固定窗口压缩语义。
- 每个 route contract 必须说明适用的边集合、路由 kind 和可接受折点范围；折点是连续有效线段的方向变化次数，不是 `points.length`。


### 独立 expected contract 与 route contract

进入机器门禁的图表必须有独立于 SVG/sidecar 的 expected contract 文件。它是业务语义和验收意图的输入，不是 SVG、`.diagram.json`、浏览器 DOM 或其 bbox 的副本；不得从 actual 产物反向生成后再把结果当 expected。expected contract 的来源必须指向需求、批准的设计资料、代码结构或其他可追溯业务来源，且记录 source revision/digest、generator name/version、config summary/digest 和 source refs。source refs 不得是 SVG、sidecar、截图或浏览器输出。

expected contract 使用通用 V1 协议，不绑定图表类型或 SVG 内部数据结构。以下代码块只展示协议形状；尖括号占位符必须由受控 Producer 替换后才能进入机器门禁，不能直接作为输入：

```json
{
  "version": "1",
  "type": "diagram-expected-contract",
  "source": {"kind": "<approved-source>", "ref": "<business-source>", "revision": "<revision>", "digest": "sha256:<64-hex>"},
  "generator": {"name": "<name>", "version": "<version>", "config_summary": "<summary>", "config_digest": "sha256:<64-hex>", "source_refs": ["<business-source>"]},
  "diagrams": [{
    "id": "<diagram-id>",
    "diagram_type": "<diagram-type>",
    "intent": "<single-business-intent>",
    "nodes": [{"id": "<node-id>", "shape": "<optional-expected-shape>"}],
    "edges": [{"id": "<edge-id>", "from": "<node-id>", "to": "<node-id>", "from_port": "<optional-port>", "to_port": "<optional-port>", "kind": "<optional-kind>"}],
    "groups": [],
    "legend_ids": [],
    "annotation_ids": [],
    "route_contract": {
      "direction": "<TB-or-LR>",
      "edge_intents": [{"edge_id": "<edge-id>", "kind": "<route-kind>", "bend_count": 0, "label_required": false}],
      "main_flow": {"entry_node_ids": ["<node-id>"], "exit_node_ids": ["<node-id>"], "node_ids": ["<node-id>"], "edge_ids": ["<edge-id>"]},
      "loop_lanes": [],
      "branch_groups": [],
      "exceptions": []
    }
  }]
}
```

`route_contract` 是所有图型共享的路由意图层：`kind` 说明关系在业务中的路由角色，`bend_count`/`min_bend_count`/`max_bend_count` 约束实际连续有效线段的方向变化次数；共线中间点不增加折点，不能用 `points.length` 代替。`main_flow`、`loop_lanes` 和 `branch_groups` 仅在该图型有相应语义时声明；未声明不等于允许 checker 猜测。

expected 与 actual 的比较至少覆盖节点/边集合、端点、端口、边类型、分组、业务主流程（如适用）、route intent，以及 `legend_ids`/`annotation_ids` 均为空。SVG/sidecar 内部一致只能证明 actual 自洽，不能替代 expected 业务语义对照。expected 缺失、来源不可解析或 expected-vs-actual 无法完成时为 `UNVERIFIED`，不得升级为 `STATIC_PASS` 或 `PASS`。

交叉、回路、端口例外和分支例外必须在 expected contract 中记录 `object`、`type`、`business_reason`、`geometric_reason`、`scope` 和 `visual_evidence.required: true`；checker 必须验证对象确实命中对应实际偏离，Provider 必须验证实际几何与截图/快照视觉证据。只存在字段、空理由、无适用范围或没有真实视觉证据均不构成通过。

生成器变更必须重新生成 expected、sidecar、SVG 及其他声明的派生产物；actual manifest 的 `generation` 元数据必须列出 generator/version、config summary/digest、source refs 和 outputs。缺少或不一致时为 `UNVERIFIED` 或 `FAIL`，不得保留旧产物并宣称闭环完成。



画布、`viewBox` 和滚动区域按节点、分组边界、路径、箭头和无背景边标签的联合实际边界计算。较长说明、待确认事项和验收状态保留在 SVG 外部，不为它们扩展画布。

页面纵向滚动不构成失败；裁切、水平溢出、对象越界、文字不可读、样式偏离统一基线或标签压线才构成失败。没有实际三视图证据时，视觉验收状态必须记录为 `UNVERIFIED`。

### 画布与留白

- 画布由实际内容边界计算，不得以固定宽高承载所有图表；`canvas.width`、`canvas.height`、SVG `width`、`height` 和 `viewBox` 必须表示同一可见坐标范围；
- 对使用本仓通用坐标单位的图表，内容边界到画布每一侧至少保留 `24` 单位内边距；常规情况下该内边距不得超过该轴长度的 `15%`。因标题或明确外侧回边而超过时，必须记录用途；
- 所有节点、文字、分组边界、端点、箭头尖端和无背景边标签均必须位于 `viewBox` 内；
- 不得使用整体缩放、压缩 `viewBox`、缩小全局字体或 `transform: scale()` 处理过大的图。应先换行、扩展对象、调整布局或拆图；
- 框体内文字统一为 `16` 个源字体单位，边标签统一为 `14` 个源字体单位；不得通过缩小字号适配空间。

## 节点、文字与决策图形

### 动态尺寸与文本完整性

布局器必须使用同一组语义文本、字体大小和换行结果计算节点尺寸与 SVG 文本位置。对每个节点：

- 节点宽度至少为最长渲染行的测量宽度加左右内边距，节点高度至少为行数 × 行高加上下内边距；多行详情必须计入同一计算；
- 普通节点的水平内边距不少于 `16` 个源单位、垂直内边距不少于 `12` 个源单位；Provider 使用其他坐标系时必须提供等价的可读留白；
- 文字不得裁切、溢出、贴边或与其他对象重叠；长文本优先按自然词边界换行、扩展节点或拆为节点 + 关联说明，而非缩小字体；
- 节点显示文本可以为排版而换行或使用已确认的短标题，但不得删除术语或改变业务含义；完整条件、规则或说明应保留在关联标签、注释或正文中。

### 决策节点

菱形不是矩形。布局器必须根据菱形的可读内接区域测量文字，而不能先按矩形宽高排版后直接放入菱形。

对居中的决策文本包围盒，使用实际测量后的 `textWidth`、`textHeight` 与菱形 `diamondWidth`、`diamondHeight` 检查：

```text
textWidth / diamondWidth + textHeight / diamondHeight ≤ 0.70
```

不满足时必须扩大菱形、缩短已确认的显示标题并把完整条件放入关联说明，或改用适合长文本的节点形状。每条“是/否”“通过/不通过”等分支标签必须保留并紧邻所属分支。

### 文本规范化与重复防护

- 文本规范化必须幂等：`normalize(normalize(text)) = normalize(text)`；
- 规范化只能统一空白、换行或已定义的单次格式，不得每次处理都追加括号说明、标题后缀或同义提示；
- 写入结构化源前检查显示文本与 ID 的重复：只有被明确建模为独立业务事实的同名实体可以共存，并须以不同上下文和唯一 ID 区分；
- 不得将同一节点拆成多个视觉相同的节点，或以多次追加的方式重复渲染同一标签。

## 连线、端口与边标签

### 端口分配与边界连接

- 连线必须从结构化源中声明的正确端口出入，主流程方向保持一致；端口、字段名称、端口偏移和路径点契约见 `common-svg-diagram-standards.md`。
- 单条连线可以使用节点某一侧的中点；同一节点同一侧存在多条独立语义连线时，不得默认使用同一个精确端点，必须使用可区分的边界偏移位置。
- 相反方向的两条连线不得共用同一端口坐标；同一端点只有在业务语义明确表示 `junction`、`bus` 或共享汇合点时才允许共用。
- 端口偏移的相邻端点间可读间距默认不小于 `D = max(24 个源坐标单位, 1.5 × 最小正文行高)`；该间距按同一边界上的相邻连接位置计算，而不是只比较连线 ID。
- `fromPort`/`toPort` 仍表达节点的逻辑侧；需要同侧多边差异时使用 SVG 标准定义的 V1 `fromPortOffset`/`toPortOffset` 扩展，不改变 `version: 1` 或端口侧语义。Provider 不得以私有字段替代该扩展。
- 连线靠近节点时，最后一段应尽量垂直进入目标边，源节点离开边界时也应保持清晰的法向离开；禁止沿节点边界长距离平行后再贴边进入。确需绕障碍时必须在 Design Notes 中说明原因，并保留上述可读间距。

### 直连、拐角与内部路径

- 生成器必须先检测 `from` 节点到 `to` 节点的直线路径；当直线不穿越节点、文字、标签、无关分组或其他连线时，必须使用直线。对 `delivery-business-flow`，该直线还必须是合法的水平或垂直直连；若无障碍直线路径不满足交付型流程的正交约束，则使用最少拐角的 Manhattan 路径，不以通用直线规则绕过专项约束。
- 只有存在实际障碍、需要改变方向或完成合法端口连接时，才允许增加路径点；不得以冗余折线代替布局调整、拆图或端口重新分配。
- Manhattan 路径必须以最少拐角为目标；所有不改变方向、不绕过障碍、不完成端口连接的共线中间点必须删除。直线已经合法时，增加拐角即为几何失败。
- 不同业务关系不得共享非端点中间线段；非端点路径段不得重叠、交叉或共线混淆。无法满足时重排、拆图或使用关联说明，禁止一条超长斜线跨越主流程。
- 如果业务确实需要总线或汇合关系，必须显式声明 `junction`/`bus` 语义、成员关系和分支方向；当前通用 V1 不新增 Provider 私有的总线字段，优先使用已有通用结构中的显式汇合/关联节点、Design Notes 或拆图表达，不能用多条重叠路径伪造总线。共享汇合点必须能从该节点的稳定 ID、连接边集合和 Design Notes 证据反查成员与分支方向。

### 节点、文字与标签避让

- 连线内部路径不得穿过非源节点、非目标节点、节点文字或边标签；跨分组连线可以穿越其所属分组边界，但不得穿越无关分组标题、节点或标签。
- 端点必须落在源节点和目标节点的实际可连接边界上。碰撞检查必须考虑实际节点形状，不能只使用粗略矩形；无法对目标形状执行可靠边界检查时不得标记为几何 `PASS`。
- 分支之间保留至少一个文本行高或等价的可读间距；分支标签放在对应分支附近，读者无需猜测其归属。
- 边标签不使用任何背景框。标签锚点位于所属线段中点，并沿法向偏移到文字实际 bbox 与连线至少保留 `6` 个源单位净空；不得覆盖所属或无关连线、关键端点、箭头、节点或其他标签。
- 流程图、时序图、状态图和 Pipeline 图的连线必须保持单一方向；返回、回退、重试、异常和反馈使用另一条带明确语义标签的有向边。只有 Architecture、Context 或 Infrastructure 等明确表达双向数据互通的关系图，才允许使用 `bidirectional`；不得用双向线代替流程返回或状态回退。
- 需要表达回退、重试、异常或反馈时，使用清晰的外侧回边或注释，不得以没有标签的反向线暗示业务语义。

## 分组、泳道与系统边界

### 动态尺寸与区域容量（强制）

节点、分组和局部 lane 都必须在布局前根据**同一份**文字测量、换行结果、成员边界、边标签和内部连接器计算尺寸；不得先固定区域或节点大小再挤压流程。框体同类节点可在同一局部 lane 内对齐为统一尺寸，但该尺寸必须取该 lane 的最大内容需求，不能以全图固定宽高覆盖不同文本。

- 节点宽度至少为最长渲染行宽度加左右内边距，节点高度至少为行数 × 行高加上下内边距；中文、英文、数字和空白必须使用同一 CJK 感知测量方法，不能按字符数的统一比例低估中文宽度；
- 分组必须先预留标题区，再以成员节点、**内部**路径、内部边标签和箭头的联合边界反推宽高。默认标题区高度不少于 `48`，左右内容留白各不少于 `40`，底部留白不少于 `32` 个源坐标单位；
- 组标题宽度必须连同左右标题内边距完全落在框体内；成员、内部标签或内部路径进入标题区、贴近侧边/底边或越出边界即为容量不足，必须扩展区域、建立局部 lane、重排或拆图；
- 多个并列流程、反馈 corridor 或局部 lane 的总宽/高必须先纳入区域容量估算。空间不足时扩展画布或区域，禁止缩小字体、压缩节点间距、把回路借到无关分组外，或依赖整体缩放制造“一屏可见”；
- `styleRole: structural` 仅表示上述非业务结构层，可使框体与标题使用 `#666666`；它不改变 `semanticType` 的成员/嵌套语义，也不得被用于业务系统、责任或信任边界。


- 分组、泳道和系统边界表达系统、职责、部署、信任或角色边界，不得只靠颜色表达关键语义；
- 每个新建或调整的分组必须声明一种语义类型：`exclusive`（与同层其他分组互斥）、`nested`（明确的父子嵌套）、`cross-cutting`（贯穿关注点，不作为与业务域并列的成员容器）或 `overlay`（仅作辅助视图，不改变成员归属）；并声明 `styleRole`：`structural` 仅用于非业务结构层，`business-boundary` 用于承载系统、职责、信任或其他业务边界；
- 分组的直接成员必须以结构化 `members` 节点 ID 表达；`nested` 分组必须以 `parent` 分组 ID 表达层级。坐标包围不能替代成员声明；旧 V1 资产可继续读取，但缺少这些字段时只能记录迁移诊断并保持图表 `final_status: "UNVERIFIED"`，不能作为新语义图的完整通过证据；
- 未明确声明为 `nested`、`overlay` 或经 Design Notes 说明的 `cross-cutting` 的分组，不得发生面积交叠；显式 `nested` 只允许与声明的父级交叠，`overlay` 只作辅助交叠，`cross-cutting` 若确需穿越业务域必须显式声明、保持 `members` 为空，并在框体标题、相邻正文或 Design Notes 中解释不代表成员归属；
- 对互斥分组，同一个节点不得同时属于两个互斥分组；无填充分组边界和标题不得相互覆盖；分组边界必须与节点、标签和连接器保持可读间距；
- 贯穿关注点优先使用独立横向/纵向无填充边界、带标签的关系边或相邻正文表达，不得通过与业务域容器重叠使其节点被误读为业务域成员；
- 绘制顺序固定为：不透明白色画布 → 无填充分组/泳道边界 → 连线主体 → 无填充节点及节点文字 → 无背景边标签 → 箭头尖端 overlay。箭头尖端不得依赖一个位于节点下方的 `marker-end` 保证可见；分组边界不得遮挡其他分组的标题或业务信息；标题区和边界内边距必须预留；
- 分组范围从其声明成员、相关标签和必要端口的实际边界计算并保留稳定内边距；跨系统、跨角色或跨域关系使用形状、标题、边界和标签组合表达，不使用颜色编码；
- 外部系统或不展开的范围必须以边界节点或明确边界标记表达，不能把未展开内部流程伪装成已展开流程；嵌套分组不超过两层，内层不得覆盖外层标题、边界或其他内层分组的业务信息。

## 不同图表类型的专项规则

| 图表类型 | 必须保留的语义 | 布局与验收重点 |
|---|---|---|
| 运营端流程图 | 页面操作、业务动作、关键校验和分支 | 节点使用简洁的操作标题；长规则进入说明/正文；主操作顺序与页面实际顺序一致 |
| C 端流程图 | 用户动作、系统反馈和关键分支 | 不把实现细节混入用户动作节点；页面名称与系统内部处理按既定规范区分 |
| 系统对接时序图 | 参与者、请求、返回、异常、重试与异步回调 | 参与者标题按实际名称扩展；生命线间距可承载消息；消息不压在线或生命线上；长消息换行、扩距或用注释；方向用箭头/线型区分 |
| 状态图 | 状态名称、转换条件、初始/终止状态 | 转换条件紧邻对应箭头；自循环和回退路线置于状态外围；状态、标签和终止节点互不遮挡 |
| 数据流或系统边界图 | 数据对象、系统、角色、边界与关系方向 | 形状语义稳定一致；复杂关系分层或拆图；禁止一条超长线跨越多个无关区域 |

### Sequence 图消息与生命线

适用于 `sequence` 图：

- 参与者标题矩形只用于显示参与者名称，不作为消息端点；生命线必须作为可追溯的实际 SVG 连接对象，普通消息从源参与者生命线发出并连接到目标参与者生命线。生命线映射与通用端点检查的例外见 `common-svg-diagram-standards.md`，不得把标题矩形重新解释为生命线。
- 消息起点的 `x` 坐标必须等于源生命线的 `x` 坐标，消息终点的 `x` 坐标必须等于目标生命线的 `x` 坐标；消息 `y` 坐标只表达时间顺序，不得改变消息与生命线的绑定关系。
- 自调用必须从同一条生命线出发，绕行后返回同一条生命线；请求和返回消息不得共享中间路径。
- 消息文字不得压在生命线上或覆盖其他消息线；无法容纳时应换行、扩展消息间距或改用关联说明，不得把文字压入参与者标题矩形。

## SVG 源与 Provider 交付模式

本仓图表默认由 AIDLC 交付**可审阅的 SVG 源、可选语义伴随清单和 Provider Request**，不默认交付或调用静态渲染器：

1. SVG 源表达按 Blueprinter 规则组织后的节点、连线、文字、分组、图标和可访问性信息，是 AIDLC 的主要图表产物；
2. `.diagram.json` 对进入 `diagram-contract` 门禁的新建或调整过程图是必需的语义伴随清单，用于稳定 ID、节点/边/端口、连通性、方向、箭头目标和事实映射的机器检查；独立 `source-only` 的静态关系图只有在不要求结构化门禁时才可省略。它不是默认本地渲染输入；过程图缺少适用清单时记录迁移诊断并保持 `final_status: "UNVERIFIED"`。
3. 需要保存源文件或伴随清单时，优先放在目标 Markdown 同级 `assets/`，但是否提交静态交付物由目标产物和用户要求决定；
4. Provider Request 记录目标操作（预览、渲染、导出）、目标环境、源路径、可选语义清单、期望验收项和已知能力状态；它可以作为结果中的结构化请求，不要求 AIDLC 绑定某个 Provider 或固定文件扩展名；
5. 外部 Provider 负责实际文字测量、最终坐标和连线布局、SVG 预览/渲染、SVG 到 PNG/PDF 等导出以及目标环境视觉检查。AIDLC 不调用、安装或默认绑定 Kiro Preview、Claude runtime、OpenCode runtime、draw.io、浏览器或本仓脚本；
6. Markdown 只有在目标环境需要时才引用 SVG 源或 Provider 生成的静态 SVG；引用本身不证明目标环境已渲染成功。没有 Provider 时仍可交付 SVG 源和语义检查结果，并在外部验收证据中记录视觉状态为 `UNVERIFIED`；不得把该状态渲染为 SVG 内的可见文字、注解、图例、角标或水印。只有用户要求目标渲染/导出而没有可验证 Provider 时才返回 `NEEDS_CAPABILITY`；不得回退为 Mermaid、ASCII 图或伪造渲染成功。

## 交付型业务流程图

面向 PRD、业务方或客户交付的业务流程图自动使用 `delivery-business-flow` 约束：

- 一张图只有一条入口到出口的主干；分支回到主干或终止；复杂多角色流程优先使用同一张带角色泳道的全局图，只有在全局布局仍不可读或语义边界明确时才拆分；
- 连线默认避免交叉、零节点穿越、零标签覆盖；为保持主轴、同层业务顺序或避免更差折返而无法消除的交叉，必须按“主轴优先、端口扇出与同侧通道”规则声明并验证；复杂异常可拆为独立子图。
- 仅使用开始/结束圆角矩形、步骤矩形和判断菱形；主流程只能有一个显式起始节点，判断节点不得作为起始节点；
- 主流程方向一致；流程图不得使用双向连接线；回退关系使用明确的外侧有向路径，但线型严格继承来源关系，不能因其是回路而改为虚线；双向箭头只适用于架构/关系图中确有数据互通的关系；
- 长流程优先采用横向分行或泳道内分段，保证主流程与连接器在主阅读方向居中；纵向布局也必须以内容边界居中，不得靠固定画布或整体缩放制造偏移；
- 每个承载业务事实的节点必须有声明的入/出关系，孤立节点只能是明确标注的外部边界、注释或起止节点；单一入口不得并列生成多个无共同前置的实体；
- 不使用强调色或语义色；业务节点、连线、箭头、边标签和业务边界保持黑色，只有已声明 `styleRole: structural` 的非业务泳道/阶段/区域框及其标题可使用 `#666666`；
- 交付型流程的判断节点必须保留声明的主流程入端口：主流程边使用该端口的零偏移，除已声明 profile 明确提供等价顶点映射外不得把主顶点沿外轮廓移动；分支从相邻顶点出，其他独立入线必须使用不同的合法端口/偏移或显式汇合节点。
- 跨泳道或跨分组连线可以穿越其所属的边界，但必须保留边界两侧的可读间距；不得穿越无关分组标题、节点、标签或边界。
- 未通过结构、几何、语义和目标环境视觉检查时，必须拆图、简化或降级为编号步骤与分支表，不能以“语义大致相同”放行。

## Diagram QA

图表设计层只检查设计决策是否成立：

1. 图是否回答单一目的，节点和关系是否均有明确事实来源；
2. 粒度、拆图、画布比例、文字、回边和分组是否符合本文件的可读性与不改义规则；
3. 是否把 Architecture、Context、Pipeline、Flowchart、Sequence、State 等独立语义错误混合，混合时是否有拆图决策；
4. 是否未生成全局图例/备注，并为形状、线型和分组角色提供就地文字或 `inlineSemanticEvidence`；
5. 分组类型、直接成员、父子层级、交叠许可和贯穿关注点是否明确；
6. 是否存在需要改用文字/表格、补充事实或请求 Provider 的情形。

正式 SVG 的字段、静态安全、结构、几何、语义、视觉检查和 `PASS` / `FAIL` / `UNVERIFIED` 状态只按 `common-svg-diagram-standards.md` 的“验收顺序与证据”执行。本文件不重复定义该矩阵；Design Notes 必须包含该矩阵要求的决策和证据索引。

## 遗留兼容边界

Mermaid fenced block 与二维 ASCII/Unicode 图已不再是本仓的新图表输出格式。它们只能作为历史文档的语义输入，按对应遗留说明迁移为 SVG；目录树、命令、单行状态和其他可复制文本仍保持文本形式。

## 调用边界

独立调用时不更新 `state.md` 或审计，也不代替用户审批；AIDLC 内调用时，调用方提供已确认语义上下文并负责将 SVG 产物纳入自身流程。图表能力不得自行创造业务事实、修改代码、提交 Git 或宣布 AIDLC 阶段完成。


## 流程图主流程追踪与回路 lane 契约

对 `flowchart`、`pipeline`、`state` 和其他具有过程语义的图，`designNotes.layout` 必须把“读者如何追踪流程”记录为结构化契约，而不能只依赖节点位置或 SVG 的 `data-*` 标识：

- `mainFlow` 必须声明 `entryNodeId` 或 `entryNodeIds`、`exitNodeIds`、`nodeIds` 和 `edgeIds`。它必须覆盖全部业务节点和流程边；从入口集合出发必须可达所有主流程节点；`exitNodeIds` 表示主链完成态，除已声明并实际进入 `loopLanes` 的反馈/重试边外不得有出边。多个入口只适用于已确认的上游汇合流程，不得用来掩盖不可追踪的断链。
- `loopLanes` 必须为每个回退、失败、重试或反馈边声明独立 lane：`{ id, side: "left"|"right", laneOffset, reason, edgeIds }`。`laneOffset` 至少为 `24` 个源坐标单位；来源有标签的回路边必须显示该标签，来源无标签时不得为通过门禁凭空添加标签，并在路径中实际进入声明的外侧 lane；回路不得参与主流程层级、对称和普通汇合判断。
- 只有来源语义明确为判断的节点才使用 `diamond`；多个出口本身不是形状转换依据。判断节点的来源出口标签必须保留且可见；来源无标签的普通处理关系不得为满足布局规则新增标签。菱形只有一个出口时不能被当作有效判定节点。
- 菱形端口使用四个顶点，主流程端口不得偏移；连接器首段必须沿 source port 法向离开，末段必须沿 target port 法向进入。菱形不能用矩形边中点近似，也不能用缩小文字掩盖菱形内文字越界。
- 流程边的非零路径段不得重叠、共线混淆或穿越非端点节点。交叉默认避免；仅当已声明的必要交叉更能保持主轴、同层顺序和可读性，且不触及文字、标签、箭头或关键端点时才允许保留。共享端点必须有显式汇合语义；普通关系不能通过重叠路径伪造总线。冗余共线路径点必须删除。

上述约束属于源级共享契约。箭头和无背景边标签仍须按本文件及 `common-svg-diagram-standards.md` 的实际边界规则计算；没有目标 Provider 证据时，三种阅读视图的视觉状态只能记录为 `UNVERIFIED`。


## 方向预分析与主干—树冠布局契约

过程图在生成节点坐标前必须先执行结构预分析。预分析只消费业务来源、expected contract 和文本尺寸配置，不得从 SVG、sidecar 或已有坐标反推主流程。至少输出节点数、边数、入口/出口、判断节点、合流节点、反馈边、分支组、分支路径数、最大分支深度、最大并行分支数和预计内容宽度。

`route_contract.main_flow` 与 `route_contract.primary_flow` 具有不同含义：

- `main_flow` 表示完整业务流程覆盖，必须覆盖全部业务节点和流程边并保证从入口可达；
- `primary_flow` 表示视觉上的中心主干，是一条由 expected contract 明确声明的连续节点路径；不得用最长路径、节点顺序或 SVG 坐标猜测；
- `branch_groups` 表示从判断节点展开的分支组；结构化分支组可以声明 `id`、`decision_node_id`、`edge_ids`、`target_ids`、`merge_node_id`、`depth`、`mode` 和 `reason`；
- `loop_lanes` 只表示真实反馈、失败、重试或回退关系，不得把普通分支放入外侧 lane。

方向决策按以下顺序执行：

1. 无复杂分支、无反馈且预计内容宽度不超过目标阅读区域时，使用 `LR_SINGLE_ROW`；
2. 只有一个浅层、最多两个出口且无反馈时，允许使用 `LR_COMPACT_BRANCH`；
3. 存在嵌套判断、多个判断、多出口分支、反馈回路或横向宽度超限时，默认使用 `TB_MAIN_AXIS`；
4. 多连通组件使用 `TB_MULTI_REGION`；入口不唯一且没有已确认主干时返回 `NEEDS_CONTEXT`。

TB 布局中，`primary_flow` 沿中心纵向主轴连续向下；判断节点的普通分支先横向离开主轴，分支超过一个简单步骤或再次出现判断时立即进入与主轴平行的局部纵向 lane；分支完成后在最近的业务合流点接回主轴。不得等待多层后再任意改变方向，也不得以 edge ID 交替决定左右端口。只有真实反馈关系才能进入最外侧 loop lane。

expected contract 使用 snake_case 字段，`.diagram.json` 的 `designNotes.layout` 使用 camelCase 映射：`primary_flow` 对应 `primaryFlow`，结构化 `branch_groups` 对应 `branchGroups`。没有 expected 主干和分支语义时，生成器必须返回 `NEEDS_CONTEXT` 或保持旧兼容模式，不得把 actual 几何升级为业务事实。


## 既有过程图的完整重绘设计闭环

完整重绘与局部连线修复必须分开建模。完整重绘允许改变节点位置、业务层级和画布，但必须保持来源事实和稳定语义映射，并在相邻复盘中记录 before/after 决策。

### 重绘前冻结

- 先读取业务源、关联文档、当前 SVG、sidecar、expected contract 和适用规范；业务语义不能由旧坐标、短标题或旧路径方向推断；
- 冻结重绘前的 SVG、sidecar、expected、generator/config 快照，记录绝对路径、SHA-256、`STATIC_PASS`/`UNVERIFIED` 等状态；
- source relation merge 必须使用稳定来源序号、display edge ID 和业务标签精确记录；不能因为重排而按 `from/to` 猜测同一节点对的关系；
- 新图没有可靠历史 baseline 时不能伪造 `changeImpactReview`；既有图迁移则必须使用真实冻结样本作为 baseline。

### 预分析与布局计划

坐标生成前必须从来源和 expected contract 执行结构预分析，至少输出节点数、边数、入口/出口、判断节点、合流节点、反馈边、branch groups、分支路径数、最大分支深度、最大并行分支数和预计内容边界。方向决策、主轴、业务层级、`mainFlow`、`primaryFlow`、branch groups、merge nodes 和 loop lanes 必须在生成路径前声明。

- `mainFlow` 表示完整流程覆盖，`primaryFlow` 表示已确认的连续视觉主干；不能用最长路径、旧坐标或节点顺序替代业务确认；
- `TB` 图先冻结中心主轴和层级，再放置同层分支和局部 lane；复杂分支超过一个简单步骤或再次出现判断时，应立即进入与主轴平行的局部 lane；
- 普通分支不能因为路由困难被放入 `loopLanes`；只有真实反馈、失败、重试或回退关系可以进入外侧 lane；
- 布局计划必须优先保持主轴连续、同侧通道、端口法向、标签净空和内容边界，而不是满足固定窗口的一屏显示；
- 例外只能记录实际发生且有业务或几何理由的偏离，不能预先声明例外来掩盖尚未解决的碰撞、交叉或最短路问题。

### 重绘后的比较记录

案例复盘至少比较：节点/边集合、来源合并、`mainFlow`/`primaryFlow`、branch groups、loop lanes、实际 crossing 集合、路由折点和方向、端口及偏移、箭头目标、标签位置、内容边界、画布尺寸、SVG 绘制层以及 generation closure。通用标准不保存具体图表名称、节点名称、edge ID 或坐标；这些只属于案例复盘。

## 来源语义、阅读路径与路由保真

Mermaid、批准流程或其他业务来源是不可变语义事实。生成器必须先冻结 `source_graph`：节点的 source ID、display ID、原文文本和形状，以及每条来源关系的稳定序号、端点、线型和标签；再声明阅读路径、主轴、局部分支和反馈 lane。`source_graph` 存在时必须覆盖每个 display 节点和关系；多条来源关系映射到一条 display edge 只允许端点和线型完全相同且显式记录 `display_label` 的受控合并。

阅读路径是可追溯的设计产物，不是来源修改。`reading_paths` 必须以连续节点/边 ID 表达主场景、分支场景或反馈场景；所列标签必须来自来源关系并紧邻分歧或所属路径段。候选路由固定按“直连 → 一折 Manhattan → 两折 Manhattan → 局部 lane → 必要 feedback lane”评估。局部分支必须保留在局部区域；只有真实回退、失败或重试可使用外侧 lane。任一关系不得在离开 source 后再次进入其内部（`SOURCE_REENTRY`）；移动节点后必须重算全部 incident edges。样品和截图只能指导阅读体验，不能覆盖来源文本、形状、线型或标签。

### 最近合法反馈 lane 与同端点关系合并

反馈/重试边使用 outer lane 前，必须先计算从来源端口到 lane 的**最近合法净空**：lane 只需越过来源节点、相邻节点、标签和箭头所需的最小间距；不得以固定的大偏移、历史坐标或“预留空间”为由拉宽回路。`laneOffset` 是相对主轴的结果值，来源节点本身偏离主轴时该数字可以较大，但来源端口到实际 lane 的横向清场距离必须是最窄合法距离。若需要更宽的 corridor，布局计划必须记录具体障碍和最小净空依据。

当同一来源节点到同一目标节点存在两条或以上**端点与线型完全相同**的来源关系时，布局计划必须先评估受控 display merge，再考虑端口偏移、平行折线或远离主轴的绕行。被批准的 merge 必须完整记录全部 source ordinal、每条来源标签、唯一 display label 和理由；不得删除条件或用新业务词替代来源标签。若合并后可同轴直达，必须优先采用直线。

边标签必须位于其所属连接器的可辨识邻域：优先紧邻分歧点或最长可读路径段，并与该段居中附着；不得为躲避而把标签推到读者无法判断归属的远处。标签绕行前必须先评估受控 merge、局部 lane 和标签附近的合法空白。

无关节点的可见边界同样属于障碍：连接器可以在自身 source/target 的端口处接触边界，但不得沿任何无关矩形、圆角矩形或椭圆节点的边框共线行走。边界重叠会让读者误读为节点的一部分；应将 corridor 外移到最小净空位置，而不是贴边通过。


## 统一几何 profile 与布局计划（强制）

所有新建、调整和迁移图表必须在布局前消费同一份项目无关的几何 profile；布局分析器、生成器、sidecar、expected contract、静态 checker 和目标 Provider 不得各自维护尺寸或间距常量。默认 profile 的 `entityGap` 为 `24`、`portGap` 为 `36`、`obstacleGap` 为 `12`、`laneGap` 为 `48`，并同时声明节点内边距、行高、画布边距和每种支持形状的基础尺寸/边界模型。`round`/`rect`、`diamond`、`ellipse`、`database`、`actor`、`note` 必须按其真实边界模型计算；菱形、椭圆和其他非矩形形状不得退化为矩形碰撞模型。

actual `.diagram.json` 使用 `designNotes.layout.geometryProfile` 的 camelCase 字段；expected contract 使用 `route_contract.geometry_profile` 的 snake_case 字段。两者必须逐字段对照，且 `shapeBaseSizes`/`shape_base_sizes` 必须覆盖生成器声明支持的形状。节点基础尺寸和动态文本尺寸必须在同一测量结果上计算；节点、端口、连线、标签和回流 lane 的间距门禁均消费该 profile，不能通过图表名称、节点 ID、edge ID 或固定坐标特判。

过程图必须先冻结来源确认的 `primaryFlow`，再生成 `branchLayoutPlan`。未提供业务确认的主流程时返回 `NEEDS_CONTEXT`，不得把最长路径自动升级为业务主干。计划使用确定性 `primary-flow-then-longest-branch` 策略：主流程边优先，其余分支按语义路径长度排序，同长度按稳定 edge ID 排序；该排序只是布局候选，不改变业务事实。分支组应作为整体外移或进入局部 lane，连同成员节点、incident edges、标签和受影响通道一起重算，不得按 edge ID 逐条堆叠坐标补丁。

同侧多条反馈/重试 lane 必须先计算最窄合法 corridor，再按实际 lane 的中心偏移保持至少 `laneGap`；`laneOffset` 不是免除间距检查的理由。普通分支不得借用 `loopLanes`，回流 lane 也不得参与普通主流程层级和对称计算。
