# 项目接手与资料收敛

旧项目、资料冲突或跨会话接手时使用；普通局部修改无需遍历历史或迁移全部文档。已知 CR ID 时第一条资料查询就取导航对应行，再按锚点/标题边界读所指接续段；不要先输出整份导航、CR 或 progress 再定位。其他事实沿引用展开，已读且未变的段落直接复用。读取、产出物/依赖扫描与输出遵循[真实验证](verification.md#限定读取扫描与输出)，不为接手制作全目录哈希或加载整卷故事、历史和测试日志。沿用现有需求、任务说明和宿主记录，不建立接手台账、版本兼容模式或恢复门禁。

## 恢复当前目标

先从用户原始约定及可核验的已确认变更定位本次目标、验收和授权，再看交接摘要、现有清单与实际代码。摘要只能定位来源，不能取代来源或扩大授权；文件日期较新、勾选完成或写有“已批准”本身不证明其权威。真实授权适用性按[权限边界](permissions.md)核对。

## 核实实际代码基线

在修改代码、编写替代实现或安排回归前，先核实本次涉及仓库的实际基线。多仓库只查相关仓库，不能用其中一个仓库的分支推断其他仓库；本地 main 与 tracking branch 也不必然是 CR 的实施分支。

1. 读取当前分支/HEAD、未提交改动及远端配置，从已有接续、分工或相关提交定位候选工作分支。没有仍适用的最新核对结果时，按现有权限 fetch 相关远端引用；必要时才扩大候选分支。无需 pull、全仓库同步或自动清理 Git 历史，也不为核实基线新增记录或审批。
2. 沿 CR ID、已知修复提交或相关路径查看候选分支的提交与代码差异，确认行为是否已修复、当前分支是否包含该修复，以及对应结果是否适用。提交标题、远端默认分支和“远端已有提交”都不能独自证明修复正确、已合并或已部署；找到修复后核对相关实现与证据即可，不重做替代实现。
3. 先保护当前未提交成果与他人工作；读取远端和选择候选不授权 checkout 覆盖、stash 他人改动、合并、推送或部署。需要切换或隔离时沿用宿主现有工作区能力及授权，不强制创建 worktree。若工作中才发现基线过旧，立即停止旧基线上的重复实现，保全自己的改动，按新基线重新判断补丁与测试结果的适用性；不能直接搬用旧提案或把旧测试计作新基线通过。

无法访问远端、没有远端或分支关联仍不明确时，如实保留未核实范围；仅暂停依赖该事实的修改或完成声明，独立分析与已获授权的工作继续。已核实且相关输入未变的结果直接复用，不把每次续作变成重复 fetch 或新的开工门禁。

## 围绕真实未完成项收窄工作

“完整”以本次用户范围及已确认变更为界。局部 CR 先定位变更决定及实际依赖，不把整个模块的需求/NFR 自动列为待重验；交接中的“整体核验”或复制件缺少其他实现，都不是扩大范围的依据。扩展到消费者、端到端链路或非功能检查时说明具体受影响关系；未受影响的既有结果沿用，材料未提供只说明本次证据边界，不写成新增实施缺口。

校正基线后，将原目标与已核实实现、适用证据及交付事实对照，区分尚未实现、只缺验证、只缺外部验收或交付动作。这个判断在当前工作上下文中完成；已有权威记录只补实际变化，不另建清单。主要实现已完成时，直接处理剩余缺陷或最小充分验证，不继续按旧待办重写，也不为交接“看起来完整”主动发起模块审计。无独立可推进项时报告真实待办并收口，外部等待不能靠扩大文档整理或测试规模填补。

在这个范围内逐项检查目标行为、必要消费者/集成、数据迁移/回滚和交付条件，包括尚无实现或测试的项。已完成且仍适用的影响分析与结果沿用；只有真实未完成行为、尚未核实的语义变化或具体覆盖缺口，才按[既有 STORY/AC 引用](verification.md#沿既有验收引用查全影响)查全相关候选并判断影响，新增消费者 AC 也查其全部引用。把遗漏的具体编号、位置和原因补回现有权威接续段，并核对已定位集合与写回内容的差集，不另建映射表。已有测试全绿时仍检查是否沿用旧口径；验收语义改变才使对应结果失效，文档路径或摘要变化不自动触发重跑。外部待办保留边界，不另建目标矩阵。

同一 CR 的“产品文档完成”“代码完成”“验收完成”“关闭”分别判断。一个参与者完成自己的范围不取消其他参与者的待办；摘要省略、旧清单勾选或子集通过不能证明整体覆盖。`work` 的截断预览只能定位资料，相关完整内容需由宿主按需读取；`assess` 不会发现输入遗漏，按[完成判定](completion.md)收口。

## 提交与推送续作

用户只要求提交或推送已有成果时，复用已加载且未变化的规则、实施结论和原验证结果；检查实际工作区/暂存差异、授权范围、目标分支与必要远端增量，直接推进剩余交付动作。新增改动、远端整合、证据适用性不明或覆盖缺口才需要补查或复验，按[验证顺序与复用](verification.md#先短回归再集中核验)判断；不因进入提交步骤重启需求排查、业务测试或打包。明确暂存本次路径，保护其他在途改动；推送成功按实际退出码及远端 SHA 核对。

提交 hook 保留并实际执行；提前了解 hook 覆盖以减少同范围手动重复检查，自动改码后仍核对差异并补受影响验证。多仓库的状态与结果分别判断，健康仓库可按授权独立交付，不让某个仓库的环境故障阻塞其他无依赖成果。

Git 操作失败先区分权限、认证、网络、引用与对象问题，保留具体错误；不能仅凭超时、502 或 pack 数量认定对象损坏。有明确对象/索引不一致或坏对象证据时，停止在相同故障条件下反复提交、抓取或触发维护，先核对受影响引用、可读成果和 hook 如何定位仓库，再选定有依据的最小恢复路径。需要隔离且授权允许时，可使用能完整运行原 hook 的干净检出及已有依赖；hook 会自行发现仓库或清理 Git 环境变量时，不继续仅替换外部 Git 元数据试错。

隔离交付须核对目标远端基线、待提交内容与原暂存成果的一致性，以及 hook 后的实际差异，沿用原验证的适用部分；相关基线或语义改变时补必要检查。不得绕过 hook，也不默认 repack、删除对象、强制推送、覆盖工作区或接管未知进程。缺权限、唯一成果不可读、存在写入冲突或操作结果未知时，只挂起对应动作并说明缺口；不盲目重放外部操作。上述处理不要求统一修复脚本、证据副本或恢复台账。

## 处理旧流程残留

旧阶段命令、claim/grant、refresh/re-attest、补签名、固定审批轮次及过期状态仅说明历史流程，不恢复旧运行时、不重跑阶段。业务决定、原始失败与验证依据继续保留；项目现行 CI、安全、质量和发布权限要求仍有效，不能因它们出现在旧文档中一并废弃。

遇到“已确认”与“待拍板”并存，先沿来源找到真实答复及适用范围；有效且未被覆盖的答复直接复用。旧待办已有设计结论时引用该结论并核实当前适用性，将未实现/未验证与待决定区分，不重新提出同一选择。仍有真实业务歧义或无法核实的授权时，只暂停依赖部分；不得根据版本号、推荐选项或 AI 摘要代替用户决定。现行项目指令与当前任务存在真实冲突时处理具体冲突，不把“旧流程”当作绕过项目指令的理由。

当前任务涉及这些入口且有写入权限时，就地把失效的行动提示替换为现有来源和剩余工作引用，清除已解决的“待批准”提示。只更新本次接手会用到的 CR/任务入口；纯历史记录无需改写，唯一、未提交或他人维护的材料保留。安装新版规则不等于项目资料已迁移，也不授权批量清理工作区。

发现旧描述时，先判断它是否仍决定本次实施、接口消费、验收或约定交付。会误导当前工作的权威语义及必要消费者文档必须纠正；纯追溯文字、已由有效来源替代的历史正文和无关设计不逐份重写。无需维护的入口改为指向权威来源的稳定引用，不把一次局部修复扩成所有关联文档的同步工程。

## 收敛重复资料

同一故事、决定或状态已有多份正文时，先看实际维护者、引用及消费者，选定现有权威来源。比较并保留副本中的独有验收、例外和未决项，再将可编辑的重复正文替换成指向原来源的短引用；保留仍被引用的 ID/锚点，核对链接和调用方。无法确认哪份有效时保留冲突并调查，不能以“去重”删除需求。

先沿现有引用识别哪份 CR、任务说明或交接正文维护当前事实，其他入口仅导航；文件名为 handoff 不意味着它也要保存状态。链接有效、权威来源未迁移时，不因新会话、日期、完成状态或测试数变化改写导航，也不在链接标题或表格行加“进行中”“不能关闭”“本轮已核验”等状态摘要。首次缺少入口、断链或来源迁移时才调整必要引用；失效的手工状态副本在授权范围内一次收敛，后续不再同步。既有生成视图或用户明确要求的状态展示从权威来源派生，不新增手工维护点。

先区分手工副本与生成物：生成物维护其源和生成方式，独有修改先回归源；生成器缺失不证明生成物失效。未确认消费者与交付形态可变时，保留生成物的完整正文，不能直接改为索引或要求下游适应删减。独立消费者必需的契约、可执行测试及约定交付物保留。无权修改的副本通过当前入口指明来源，不能接管他人文件。仅当本次变更触及重复内容时收敛，不为文档整洁扩大任务。

## 继续未完成工作

复用上述已核实代码基线及验证适用输入，按现有分工处理共享接口和实际写入重叠。先查询宿主可见的未决操作：超时不等于未执行，提交、推送、发布、迁移等不能盲目重放；结果未知只挂起相关操作，独立工作继续。不接管未知进程，不因交接创建强制 worktree 或全项目锁。

需要持久续作时只在上述既有权威记录中补充新的事实、未完成目标、适用验证和下一步引用；新会话本身不是文档更新理由。没有新事实时保留记录，在对话中说明结果；无权写入权威记录时先完成独立工作并说明待归源内容，不把导航或新文件变成第二份记录。接手者独立核对原始目标与实际输入；只重验受影响部分，不重建全量基线。

同一会话或两个 CLI 查询进程不证明新模型会话恢复。跨会话/换宿主验证需让独立模型从实际资料接手，核对真实动作和产物，并明确未测的自动唤醒、外部操作恢复等边界。按[验证顺序](verification.md#先短回归再集中核验)先检查改变的局部行为，再集中核验稳定候选；独立接手要核对原目标和证据适用性，不要求重新执行所有未变检查或复制整套验证脚本。复用准备成果与原结果引用，实际输入、验证工具或环境变化时才补齐受影响证据。
