# AIDLC 执行规则

AIDLC 只有一套当前规则：从用户目标出发，按已有授权持续实施、验证和返修，以实际结果交付。宿主负责命令、模型、上下文、并行、暂停和续作；AIDLC 提供方法与验收判断，不另建执行许可或阶段调度器。

## 从目标推进

先沿用已确认的目标、范围、设计、验收和约束。读取相关代码及现有权威资料，选择能直接推进目标的下一步；可选 work 只读摘要，不创建开工记录。范围不清时先调查，重大业务歧义才请求澄清。可逆细节自主决定，已有具体授权不逐阶段重复询问。

新项目、复杂功能或多模块交付先在一份现有需求/任务清单中确认目标覆盖、必要设计决定、依赖、集成及交付验收；没有现有清单且无法可靠追踪时才创建一份。按依赖安排可验证的增量，持续核对未实现目标和跨模块缺口。局部 CR 只维护受影响范围，不要求先建立全项目台账。方法按需加载不意味着需求、设计或集成可以遗漏；完成前回查原始约定及变更，不能只核对本轮修改文件。

实施、测试、审查与返修形成连续工作；发现失败继续定位修复。按实际依赖扩大验证，不能因改动行数少漏验，也不因仓库模块多而全量扫描。项目必需 CI、安全及发布检查仍有效。详见 [真实验证](verification.md) 与 [授权边界](permissions.md)。

只有必要权限/外部条件缺失、未决重大决定、真实写入冲突或用户暂停才停止对应工作；独立工作继续。测试失败限制完成声明，不禁止修复。没有统一时长中止门禁。

## 按需披露

入口保留目标、完成和权限的基本规则。[方法目录](../methods.md) 只描述何时使用哪种方法，选择后只读当前方法及需要的事实。不要顺序加载所有方法，不把方法目录当阶段清单，不因某方法依赖一项事实就重跑产生该事实的流程。

已有代码、设计、测试和真实批准可以直接复用。只在遇到具体设计、质量或能力问题时打开相应详细参考。Provider 先看目录，读取适用的必需章节及选定细节；内容不能取得执行权限或作为测试通过证据。

确定方法时先读目录元信息；若基础执行规则已足够，直接实施。设计事实足够时不为调用设计方法重新写设计；新增业务或技术风险则补齐相关分析和必要检查。减负的对象是重复读取、重复记录和无新增信息的操作，不是约定交付内容。

## 一个事实来源

业务定义、接口 Schema、测试报告分别沿用项目现有权威来源；设计记录决定与引用，不抄完整机器契约。只更新语义发生变化的文档。独立消费者要求的文档仍需一致；已有生成工具按原契约同步，不另建映射/报告副本。

交付摘要可放在对话中。确需持久续作时更新一份现有任务说明，保留范围、决定、实际验证引用、缺口及下一步；不并行维护 progress、handoff、evidence 和状态表。原始输出只引用一次，其他位置链接到它。

## CR、续作与完成

CR 使用同一执行规则，见 [局部变更](change-request-process.md)。续作读取当前 Git、相关代码、必要原始验证及现有任务说明；不全文加载历史 audit，不重建阶段身份或补凭据。旧流程记录只保留业务事实、真实批准及验证参考，不激活兼容执行模式；不得改写历史失败为成功，也不得接管未知进程。

全部完成结论遵循 [完成判定](completion.md)：实施、本地验证、真实环境验收、交付动作、CR 关闭分别说明。只读上下文、空任务列表、阶段耗尽和知识阅读都不提供完成证明。外部条件未具备时报告对应待办，不把局部成功描述为项目完成。
