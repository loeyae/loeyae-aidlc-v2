# 测试执行策略

**目的**：定义增量测试执行策略，根据变更范围智能选择测试执行粒度，避免全量测试导致的 OOM 和效率问题。

**加载时机**：TDD 验证阶段、构建和测试阶段。

---

## 核心原则

1. **变更范围决定测试范围** — 修改了什么，就测什么及其依赖方
2. **最小充分验证** — 默认运行目标测试及必要关联测试；有影响分析或既定门禁依据时才扩大，不要求逐层全部重跑
3. **资源感知** — 考虑项目规模和可用资源，避免 OOM
4. **工具无关** — 策略适用于任何构建工具（Maven、Gradle、pnpm、yarn 等）

---

## 测试执行分层模型

```
┌─────────────────────────────────────────────────┐
│ L1：焦点测试（当前修改的类/文件对应的测试）      │  ← TDD RED/GREEN
├─────────────────────────────────────────────────┤
│ L2：模块测试（当前修改所在模块的全部测试）       │  ← 模块内广泛影响时
├─────────────────────────────────────────────────┤
│ L3：影响域测试（变更行为 + 受影响消费者的测试）│  ← 单元完成后验证
├─────────────────────────────────────────────────┤
│ L4：全量测试（所有模块）                         │  ← 明确交付门禁 / 广泛影响
└─────────────────────────────────────────────────┘
```

---

## 各场景适用层级

| 场景 | 适用层级 | 说明 |
|------|----------|------|
| TDD RED 验证 | L1 | 只运行当前编写的测试方法/文件 |
| TDD GREEN 验证 | L1，按影响补充 L2/L3 | 当前 UC-D 与受影响存量行为通过，不默认整个模块 |
| TDD REFACTOR 验证 | L1，按影响补充 L2/L3 | 验证受影响行为和调用方 |
| 快速模式无回归 | L1，按影响补充 L2/L3 | 不降低行为覆盖和证据要求 |
| 单元（Unit）完成后 | L3 | 验证必要影响闭包；无跨模块影响时可只含 L1 |
| 构建和测试阶段 | L1–L4 中最小充分范围 | 根据影响分析和既定门禁选择 |
| CI/CD 流水线 | 按既定配置 | 保留全量交付门禁，不套用到每轮局部修改 |

---

## 构建和测试阶段的决策规则

根据行为影响和既定门禁决定测试范围；单模块、模块数量或进入本阶段本身都不是全量触发条件：

- 默认 L1 目标测试及受影响存量行为、调用方测试（L3）。
- 模块内广泛耦合、无法可靠按测试定位时，扩大到 L2。
- 公共基础能力、接口、依赖、构建/测试配置发生广泛影响时，扩大到实际影响域。
- 影响域覆盖全仓、无法可靠界定，或既定交付门禁明确要求时，执行 L4。
- 每次扩大范围均记录触发原因、受影响行为和选用命令。

纯文档等无可执行行为的变更，运行相关结构、链接或分发一致性检查，不因此触发业务全量测试。I13 结构化不适用及确定性替代验证要求保持不变。

## 影响域分析方法

### 确定受影响模块

1. **识别变更文件所属模块** — 根据文件路径确定
2. **查找依赖关系** — 分析构建配置中的模块依赖声明
3. **确定影响闭包** — 结合调用关系、共享契约、构建依赖与运行时消费者，纳入必要的直接及传递依赖方；记录排除依据，不自动运行闭包内模块的全部测试

### 示例（多构建工具）

**Maven 多模块**：
```bash
# 局部修改：按项目 wrapper 和测试插件选择真实类/方法
mvn test -pl changed-module '-Dtest=ChangedServiceTest#changedBehavior'

# 按影响需要测试变更模块及其依赖方（-amd = also-make-dependents）
mvn test -pl changed-module -amd
```

单模块可省略 `-pl`，仍用 `-Dtest` 选择相关测试。以上是命令形态示例，不替代项目配置发现；`-Dtest` 适用于 Surefire，集成测试按现有插件选择。`-amd` 扩大 reactor 范围，不等于分析所有运行时消费者。不得允许零测试、禁用失败检查或跳过必需测试来伪造通过。

**Gradle 多模块**：
```bash
# 只测试变更模块
./gradlew :changed-module:test

# 变更模块 + 依赖方
./gradlew :changed-module:test :dependent-module:test
```

**pnpm workspace（前端多包）**：
```bash
# 只测试变更包
pnpm --filter changed-package test -- --run

# 变更包 + 依赖方
pnpm --filter ...changed-package test -- --run
```

**Turborepo**：
```bash
# 只运行受影响的包的测试
turbo run test --filter=...changed-package
```

## 分批策略（防 OOM）

当必须执行 L4 全量测试时，采用分批执行避免资源耗尽：

### 分批规则

1. **按模块分批** — 每批不超过 3 个模块（可根据实际内存调整）
2. **串行批次** — 批次之间串行，批次内可并行（如资源允许）
3. **优先级排序** — 公共/核心模块先测，业务模块后测
4. **快速失败** — 任一批次失败立即停止，先修复再继续

### 示例

```bash
# Maven 分批（每批 2 个模块）
mvn test -pl core-module,common-module
mvn test -pl service-a,service-b
mvn test -pl service-c,web-module

# pnpm 分批
pnpm --filter core --filter common test -- --run
pnpm --filter service-a --filter service-b test -- --run
```

### JVM 项目内存建议

```bash
# Maven：限制 fork 进程内存
export MAVEN_OPTS="-Xmx512m"
mvn test -pl module-name -DargLine="-Xmx256m"

# Gradle：限制测试 JVM 内存
./gradlew :module:test -Dorg.gradle.jvmargs="-Xmx512m"
```

## 与 TDD 流程的集成

### RED 门禁

```
I13 完成
  → L1 真实测试先运行
  → 受控失败且 failure_class=behavior、编译/环境均通过
  → 生成 red-test-evidence
```

RED 不能由编译错误、环境错误、命令找不到或普通文本声明替代。

### GREEN 门禁

```
消费 RED evidence
  → 写最少生产代码
  → L1 目标测试通过
  → 受影响存量行为和调用方测试通过，按影响决定是否补充 L2/L3
  → 生成 green-test-evidence 和 UC-D 映射
```

### 快速模式

```
压缩文档 → 仍执行 I13 → RED → GREEN → 审查 → 构建测试
```

快速模式不得 Code-First、不得先写生产代码后补测试、不得跳过 RED 观察。

### 单元完成

```
I13、RED、GREEN 和代码审查全部完成 → 核对 L3 影响域覆盖 → 补跑缺失或失效的必要测试 → 通过后标记单元完成
```

## 与构建和测试阶段的集成

在 `construction-build-and-test.md` 步骤 1（识别范围）和步骤 5（执行测试）中：

1. 分析本次 Construction 阶段涉及的模块清单
2. 根据"决策规则"确定最小充分范围（L1–L4），覆盖必要 UC-D 和受影响消费者
3. 如果是 L4 且模块数 > 3，采用分批策略
4. 记录每批执行结果
5. 全部通过后汇总到测试摘要

## 失败复测和证据复用

- 失败后先复测失败用例及修复涉及的关联测试；影响域扩大时重新分析，补跑新增范围，不自动重启已通过的全部批次。
- 同一验证目标下，相关源码、测试、依赖、构建/测试配置、环境和必要制品均未变化，且覆盖当前要求时，可复用真实通过结果。记录原命令、时间、代码版本/工作树内容标识、范围、结果、证据位置及有效性依据；无法比较时视为失效。
- 提交号相同不足以证明工作树未变；提交号变化也不能仅凭文字声明旧证据有效。仍须满足受控 producer、source revision、阶段实例和现有 freshness 校验；校验不接受时，重跑当前最小充分矩阵。禁止手改 JSON、伪造新执行或跨阶段冒用 RED/GREEN/BASELINE 证据。
- 阶段切换、审查结论或说明文档更新本身不要求全量重跑。相关输入变化及明确门禁决定补跑范围；门禁要求在新版本重新执行时，遵守门禁。

---

## 验证纪律

- **每个层级的"通过"声明必须附带实际命令输出**
- 明确记录测试执行范围（哪些模块、哪些层级）
- 记录范围选择和排除依据；扩大到 L2/L4 必须说明触发原因，不以“保险起见”默认全量
- 未触发全量要求时标注：`全量测试：未触发（影响分析：…；已验证范围：…）`；已触发但未执行时标注“未验证/阻塞”，不能写成“不适用”
