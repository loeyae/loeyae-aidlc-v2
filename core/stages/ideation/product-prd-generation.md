# PRD 生成（I15）

> **定位**：独立的 PRD 生成流程。PRD 是面向业务方的产品需求文档，可独立执行也可基于已有 Inception 产物生成。
> **反幻觉**：缺失信息标记 `[待确认: 需要什么]`，不得臆造业务规则。
> **SSOT 优先**：绑定 SSOT 项目时，优先从 SSOT 检索领域知识和已有需求文档作为上下文输入。

## 执行条件

- 用户要求生成 PRD 时执行
- 无硬性前置步骤依赖；有 I5-I10 产物时作为输入参考，无则通过 Discovery 收集
- SSOT 已绑定时自动启用 SSOT 检索增强

## 核心原则

1. **不臆造业务规则** — 每个功能点必须通过三维检查（数据来源、业务规则、异常处理），不知道就标记 `[待确认]` 并询问用户
2. **规模自适应** — 根据项目规模自动调整 PRD 深度和章节
3. **面向业务方** — 输出对非技术利益相关者友好，不含内部技术实现细节
4. **增量可 Patch** — 生成后支持增量修改，不必每次重写全文
5. **可追溯** — 章节级标注信息来源（SSOT 文档 / 用户输入 / 已有产物 / AI 综合），但不要求逐句标注

---

## 规模检测

| 信号 | 小型 (S) | 中型 (M) | 大型 (L) |
|------|----------|----------|----------|
| 用户角色 | 1 或无 | 2-3 | 4+ 或角色层级 |
| 数据实体 | 1-3 | 4-10 | 10+ 或跨服务 |
| 外部集成 | 0-1 | 2-4 | 5+ 或支付/认证/实时 |
| 页面/视图 | 1-5 | 5-15 | 15+ 或多端 |
| 部署 | 静态/单文件 | 单服务/PaaS | 多服务/基础设施 |

匹配多数信号判定；不确定时向上取值。

---

## 工作流（三阶段）

### Phase 1：Discovery（理解需求）

**入口条件**：用户描述产品想法、功能需求或说"生成 PRD"。

**SSOT 检索增强（条件）**：
若 state.md 已绑定 SSOT 项目，在 Discovery 开始时：
1. 用 `search_documents` 按用户描述的关键词检索相关文档（需求文档、会议纪要、调研报告）
2. 用检索结果补充上下文，减少对用户的提问
3. 引用来源记录为 `[来源: SSOT/<document_title>/<version_no>]`
4. 检索规则遵循 `common-ssot-integration.md` 三至四节

**已有 Inception 产物增强（条件）**：
若工作区已存在 `docs/aidlc/inception/` 下的产物（requirements.md、stories.md、data-model.md 等），直接读取作为输入，跳过对应的 Discovery 问题。

**执行步骤**：

1. **复述理解** — 用 2-3 句话总结用户意图，请求确认
2. **规模检测** — 按上表判定 S/M/L
3. **发现式提问** — 针对缺失信息提 3-5 个问题（批量提问，不逐条）：
   - 产品/功能名称是什么？
   - 解决什么问题？目标用户是谁？
   - 核心业务目标和成功指标？
   - 有无时间约束或技术限制？
   - 明确不包含什么？（Non-Goals）
4. **追问**（最多一轮） — 若回答引出新歧义，进行一轮聚焦追问
5. **澄清一致性检查** — 每次收到用户回答后，立即执行：
   - **闭环检查**：新信息与已确认的业务逻辑是否自洽？是否存在矛盾、循环依赖或逻辑断裂？
   - **破坏性检查**：新信息是否改变或推翻已确认的功能点、业务规则或边界约束？
   - 发现不一致时，立即向用户指出冲突点并请求裁决，不得静默采纳矛盾信息
   - 裁决结果更新已有结论，被推翻的旧结论标记为废弃
6. **范围确认** — 总结已确认的范围，获得用户同意后进入 Phase 2

**自适应规则**：
- 用户已提供详细 brief 或 SSOT 已检索到充分信息 → 减少提问，直接确认范围
- 已有 I5 需求文档 → 跳过 Discovery，直接进入 Phase 2
- 用户说"快速生成" → 最小提问（仅确认范围边界），直接进入 Phase 3

### Phase 2：三维需求深化

**目的**：对 Discovery 确认的每个核心功能点进行结构化深化，确保 PRD 内容可实施。

**三维检查（每个功能点）**：

| 维度 | 问题 | 未确认时处理 |
|------|------|--------------
| 数据来源 | 这个功能读/写什么数据？数据从哪来？ | 标记 `[待确认: 数据来源]` |
| 业务规则 | 触发条件、计算逻辑、状态流转是什么？ | 标记 `[待确认: 业务规则]` |
| 异常处理 | 失败时怎么办？边界条件？权限不足？ | 标记 `[待确认: 异常处理]` |

**SSOT 辅助**：针对每个维度的未知项，先尝试从 SSOT 检索已有定义；找到则引用，找不到则向用户提问。

**澄清一致性检查**：三维深化中每次收到用户对功能点的回答后，同样执行闭环检查和破坏性检查——验证该功能点的三维定义与其他已确认功能点之间无矛盾（如：功能 A 的状态流转与功能 B 的触发条件是否冲突；数据来源是否形成循环依赖）。发现冲突时指出并请求裁决。

**规模调整**：
- **S**：仅对核心功能（≤3 个）执行三维检查
- **M**：所有功能执行三维检查
- **L**：所有功能 + 跨功能交互 + 非功能需求

### Phase 3：PRD 生成

**输出格式**：Markdown 文件，路径规则：
- 多模块场景：`docs/aidlc/product/scenarios/<scenario-id>/prd.md`
- 单模块/独立：`docs/aidlc/inception/prd.md`
- 用户指定路径时从其指定

**按规模选择模板**：

| 规模 | 模板 | 说明 |
|------|------|------|
| S | 精简 PRD | 6 章节，1-2 页 |
| M | 标准 PRD | 13 章节，完整文档 |
| L | 完整 PRD | 13 章节 + 里程碑分解 + 阶段规划 |

## PRD 模板

### 精简 PRD（S）

```markdown
# <产品/功能名称> — 产品需求文档

## 文档信息
| 项目 | 内容 |
|------|------|
| 版本 | v0.1 |
| 状态 | draft |
| 作者 | AI-DLC |
| 日期 | <ISO日期> |

## 1. 概述
<1-2 段，说明做什么、为谁做、为什么做>

## 2. 目标与成功指标
- 业务目标：
- 成功指标：

## 3. 功能需求
<按功能点列出，含验收标准>

## 4. 非目标（明确不做）
<显式排除项及原因>

## 5. 待确认问题
<所有 [待确认] 项汇总，含负责人和是否阻断开发>

## 6. 来源索引
| 章节 | 来源类型 | 来源说明 |
|------|----------|----------|
```

- <规则 1>

|----------|----------|----------|

| 类别 | 要求 |
|------|------|
| 性能 | |
| 安全 | |
| 兼容性 | |

## 10. 里程碑与优先级（条件：L 规模时）
| 阶段 | 范围 | 预计时间 |
|------|------|----------|

## 11. 风险与依赖
| 风险/依赖 | 影响 | 缓解措施 |
|-----------|------|----------|

## 12. 待确认问题
| # | 问题 | 涉及章节 | 负责方 | 是否阻断 |
|---|------|----------|--------|----------|

| 章节 | 来源类型 | 来源说明 |

**来源类型**允许值：
- `SSOT` — 从 SSOT 检索获得，附 document_title 和 version_no
- `用户输入` — 用户在 Discovery 中直接提供
- `已有产物` — 从工作区 Inception 产物读取
- `AI 综合` — 基于上下文 AI 综合推导（必须有支撑依据）

---

## 来源标注规则

章节级标注，不要求逐句。规则：

1. 每章在"来源索引"表中注明主要来源类型和说明
2. 章节内的关键决策点可行内标注：`[来源: SSOT/需求评审会议纪要/v3]`
3. AI 综合推导的内容，其支撑依据必须可在同一文档或来源索引中找到
4. `[待确认]` 标记的内容不计入来源要求

---

## Patch 模式（增量修改）

用户说"加 X"、"删 Y"、"改 Z"时：

1. 识别受影响章节
2. 检查级联影响（删除功能影响数据需求、页面、验收标准等）
3. 仅更新受影响章节
4. 输出变更摘要：改了什么、影响了哪些章节
5. 更新版本号（minor bump）

---

## 自审清单（生成前验证）

输出 PRD 前必须逐项自审：

| # | 检查项 | 通过标准 |
|---|--------|----------|
| 1 | 每个功能点是否有验收标准 | 无遗漏 |
| 2 | 是否存在臆造的业务规则（无来源支撑） | 数量 = 0，不确定的已标记 `[待确认]` |
| 3 | 非目标是否明确 | 至少 1 条排除项 |
| 4 | 待确认问题是否全部汇总 | 所有 `[待确认]` 在 §12 有记录 |
| 5 | 来源索引是否完整 | 每章有对应来源 |
| 6 | 是否包含技术实现细节（不应包含） | 无 URL 路径、表结构、API 设计等 |

自审全部通过后输出。未通过项修正后重审，不得跳过。

---

## 状态流转

```
draft → reviewed（用户确认内容无误）→ approved（利益相关者签收）
  ↓ 用户要求修改
patch → draft（更新版本号）
```

- `draft`：初次生成或 Patch 后
- `reviewed`：用户确认
- `approved`：业务方签收（AI-DLC 不自动设置此状态，需用户显式确认）

---

## 与 Inception 流程的关系

| 场景 | 行为 |
|------|------|
| 独立执行（无 I5-I10） | 完整 Discovery → 三维深化 → 生成。产出的 PRD 可作为后续 I5 的输入参考 |
| I5-I10 已完成 | 读取已有产物，跳过 Discovery，直接三维深化 + 生成 |
| 部分完成 | 已有产物直接使用，缺失部分通过 Discovery 补充 |
| PRD 生成后进入 Construction | PRD 中的功能需求和验收标准可直接作为 Construction 输入，无需再走 I5 |

## 完成标准

- [ ] 自审清单全部通过
- [ ] 所有 `[待确认]` 项已汇总到"待确认问题"章节
- [ ] PRD 已写入指定路径
- [ ] state.md 已更新 PRD 状态
- [ ] 用户已确认 PRD 内容（或标记为 draft 等待确认）
