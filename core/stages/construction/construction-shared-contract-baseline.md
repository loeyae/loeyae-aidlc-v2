# 共享契约基线物化（C5 条件）

## 目的与边界

在各业务单元进入代码生成前，为已批准的跨单元共享声明建立一次可验证的代码基线。基线仅物化已在 I14 明确的声明，并以实际验证证据决定 `contract` 依赖是否可用。

本文件只定义共享契约基线的执行规则；不重新定义 I14 的契约建模、C5 路由、TDD 循环、变更请求流程或团队调度规则。涉及业务行为的代码继续遵循 `construction-tdd.md`，基线后签名或语义变化继续走 CR1—CR5。

## 触发与跳过

同时满足以下条件时执行：

1. 项目有两个或以上工作单元；
2. `unit-of-work-dependency.md` 中存在 `contract` 类型依赖；
3. 对应共享契约已在 I14 产物中完成设计。

以下情况跳过基线物化，并在 `state.md` 记录原因后继续 C5：

- 单单元项目；
- 不存在 `contract` 类型跨单元依赖；
- 依赖仅为 `implementation`、`runtime` 或 `none`。

跳过不创建空基线、空共享代码或伪验证记录。

## 输入与完整性门禁

执行前读取：

- `unit-of-work.md` 的跨单元共享契约索引；
- `unit-of-work-dependency.md` 的带类型依赖矩阵；
- `shared-interfaces.md`（进程内声明设计，适用时）；
- 跨进程机器契约（OpenAPI、Proto、AsyncAPI、Schema 等，适用时）；
- 工作区现有代码和实际构建入口；
- `state.md` 中已有的共享契约基线状态（适用时）。

每项待物化契约必须具备稳定 ID、类型、边界、唯一 Owner、非空消费者、权威来源、目标模块和目标代码路径。缺少任一项、存在未解决设计问题或消费者未知时：

- 不创建或修改代码；
- 将该基线标记为 `blocked` 并记录缺口；
- 返回 I12 或 I14 补齐设计事实；
- 不得用猜测、默认路径或消费者私有副本绕过门禁。

## 权威来源与物化范围

- 进程内共享声明：以 `shared-interfaces.md` 的完整设计为物化输入，基线验证后以 Owner 目标路径中的实际代码声明反映实现状态。
- 跨进程 API、事件和 Schema：仅以机器契约为完整字段事实来源；本阶段只生成或验证其对应类型、索引或兼容性证据，不得以 Markdown 或进程内接口替代机器契约。
- `unit-of-work.md` 只提供索引；不得从索引推断未定义的签名、字段、错误语义或兼容策略。
- 只允许修改批准清单中的 Owner 目标路径和机器契约生成路径；消费者不得另行声明同职责接口、DTO、枚举或 Schema。

## 存量代码复用与冲突处理

对每项契约先检查目标代码路径：

| 现有状态 | 处理 |
|----------|------|
| 不存在 | 按批准设计物化声明 |
| 存在且与批准设计一致 | 复用并执行对应验证 |
| 存在但与批准设计不一致，且尚未建立基线 | 阻断并返回 I12/I14 澄清或修订设计 |
| 已验证基线后发现签名、语义或路径不一致 | 标记 `change_requested`，进入 CR1—CR5 后重新验证 |

不得通过覆盖现有声明、删除消费者代码或悄悄迁移调用方来消除冲突。

## 允许与禁止的声明型物化

允许物化：

- 无默认方法的接口；
- 只有抽象成员的抽象类；
- DTO、record、data class 与枚举值声明；
- 由已验证机器契约生成的类型；
- 必要的序列化、校验或代码生成元数据。

禁止物化：

- 空方法体、返回伪默认值或通过异常制造可编译的伪实现；
- 默认方法、构造器或静态方法中的业务逻辑；
- 数据访问、网络调用、状态转换或伪 Bean；
- 为绕过依赖而创建消费者私有副本；
- 未出现在批准契约清单中的声明。

发现任何可执行业务行为时，停止将其作为基线物化处理，改按 `construction-tdd.md` 的正常流程实施和验证。

## 执行步骤

1. 根据触发条件决定执行或跳过，并写入实际决定与原因。
2. 校验 I14 输入完整性；未通过时阻断，不进入物化。
3. 将相关基线状态设为 `in_progress`，记录本次代码版本和待验证契约 ID。
4. 对每项契约在 Owner 路径复用或物化声明；不改动非 Owner 范围。
5. 按契约类型执行实际验证，并保留可复现命令、运行标识或工具输出。
6. 分别完成规格一致性审查与代码标准审查。
7. 全部必需验证和两类审查通过后，标记 `verified`；任一项失败则标记 `blocked`。

## 分类型验证矩阵

| 契约类别 | 最低验证 | 证据要求 |
|----------|----------|----------|
| 进程内接口或抽象声明 | Owner 目标模块实际编译 | 实际构建命令及成功结果 |
| DTO、record、data class、枚举 | 编译，加上项目适用的结构或序列化验证 | 编译结果与结构/序列化检查结果 |
| 跨进程同步 API | 机器契约检查与兼容性验证 | 机器源版本、检查或兼容性结果 |
| 异步事件 | Schema 校验及适用的兼容性检查 | Schema 校验结果与消费者影响证据 |
| 由机器契约生成的类型 | 机器源生成或一致性检查，加上目标模块编译 | 生成/一致性结果与编译结果 |

验证命令必须来自工作区的实际构建、测试或契约工具；不得伪造通用命令、以文档审阅替代执行，或将未执行项标记为通过。

## 双轴审查

规格一致性审查确认：

- 契约 ID、类型、边界、Owner、消费者、权威来源与目标路径均和 I14 一致；
- 进程内声明的签名、错误语义与兼容策略符合批准设计；
- 跨进程字段未脱离机器契约；
- 每条 `contract` 依赖只关联已验证的相关基线。

代码标准审查确认：

- 声明位于 Owner 目标路径且命名、包结构符合项目约定；
- 不存在空实现、伪默认值、异常占位或业务行为；
- 不存在同职责重复声明或消费者私有副本；
- 物化范围未扩展到非 Owner 或未批准的代码。

任一审查失败均保持 `blocked`，修复后必须重新执行受影响验证和两类审查。

## 基线状态与证据

`state.md` 的可选共享契约基线区块使用以下状态：

| 状态 | 含义 | 对 `contract` 依赖的影响 |
|------|------|--------------------------|
| `pending` | 已识别，尚未执行 | 不满足 |
| `in_progress` | 正在物化或验证 | 不满足 |
| `verified` | 声明、验证和审查均有实际证据 | 满足，派生 `contract_ready` |
| `blocked` | 输入、物化、验证或审查失败 | 不满足 |
| `change_requested` | 已验证基线发生签名或语义变化 | 不满足，须走 CR |

允许的转换为：

- `pending` → `in_progress` → `verified`；
- `in_progress` → `blocked`；
- `verified` → `change_requested` → `in_progress` 或 `blocked`。

每次状态更新至少记录基线 ID、范围、契约清单、代码版本、实际验证证据和阻断原因。`contract_ready` 仅由相关基线为 `verified` 推导，不在 `state.md` 创建第二份独立状态。

## Git 与团队记录

不自动创建 commit、分支、PR 或发布。团队模式下，只记录由用户批准后实际产生的 commit、PR 或 SHA；没有实际 Git 证据时必须标记未验证。

## 失败回退

- 输入不完整：返回 I12/I14，保持或设为 `blocked`。
- 物化冲突：停止修改，保留现有代码，按存量代码复用规则处理。
- 验证或审查失败：保持 `blocked`，不解锁任何消费者。
- 已验证基线发生变化：设为 `change_requested`，进入 CR；不得继续使用旧 `contract_ready` 结论。
- 仅回退本次未验证的声明时，先确认其没有消费者或已获用户批准；不得自动删除已被使用的业务代码。

## 完成标准

满足以下任一结果才可结束本门禁：

- 确认不适用并记录跳过原因；或
- 每项适用共享契约均在唯一 Owner 路径完成复用或声明型物化；
- 分类型验证和双轴审查均有实际通过证据；
- 相关基线状态为 `verified`，且仅此时解锁对应 `contract` 依赖；
- 未验证、冲突或失败项仍明确为 `blocked` 或 `change_requested`，没有被静默忽略。

## 平台适配一致性检查

修改本文件的门禁规则、状态转换或依赖就绪判定逻辑后，必须检查 `.claude/workflows/aidlc-construction-batch.js` 中的 `deriveReadiness` 函数是否仍与共享规则一致。不一致时同步更新该适配器，或在 `state.md` 记录待同步项。
