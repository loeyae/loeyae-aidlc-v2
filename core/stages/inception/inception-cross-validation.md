# Inception 产物交叉验证（强制审查）

**目的**：确保 Inception 阶段各产物之间保持一致性，问题发现越早成本越低。

**执行时机**：每个产物完成后立即执行对应的审查项，不等待所有产物完成。

---

## 审查项总览

| 审查项 | 执行时机 | 条件 | 步骤编号 |
|--------|---------|------|----------|
| a) 需求 ↔ 逆向工程 | 需求分析完成后 | 有逆向工程产物 | 3.1 |
| b) 需求 ↔ 澄清记录 | 需求分析完成后 | 始终 | 3.1 |
| c) 用户故事 ↔ 需求 | 用户故事完成后 | 始终 | 4.1 |
| d) 需求完整性评估 | 用户故事完成后 | 始终 | 4.1 |
| e) UI 设计 ↔ 用户故事+需求 | UI 设计完成后 | 执行了 UI 设计 | 5.1 |
| f) 页面基准产出物一致性 | 变更请求完成后（CR4 就地基线更新后） | 变更涉及已有页面 | CR5 |
| g) PRD ↔ I5-I10 产物一致性 | PRD 汇编完成后 | 执行了 PRD 汇编 | I16 |

## 审查项 a：需求文档 ↔ 逆向工程

**执行条件**：存在逆向工程产物（`docs/aidlc/inception/reverse-engineering/`）

**输入文件**：
- `docs/aidlc/inception/requirements/requirements.md`
- `docs/aidlc/inception/reverse-engineering/architecture.md`
- `docs/aidlc/inception/reverse-engineering/component-inventory.md`

**审查清单**：

| # | 检查点 | 通过标准 |
|---|--------|---------|
| 1 | 需求涉及的现有组件是否在逆向工程中被识别 | 所有涉及组件均已列出 |
| 2 | 需求是否与现有系统架构矛盾 | 无架构冲突，或已说明改造方案 |
| 3 | 需求引用的现有功能是否与逆向工程描述一致 | 功能描述无偏差 |
| 4 | 需求中的"新增"与"改造"分类是否与现有代码对应 | 分类准确 |
| 5 | 需求是否遗漏了逆向工程中发现的相关依赖 | 依赖关系完整 |
| 6 | 存量项目的新需求状态是否与基座既有状态机完成对照 | 对照表存在，冲突项已显式列出；不涉及状态时有明确依据 |

**未通过处理**：
1. 列出所有不一致项
2. 向 Boss 报告发现的问题
3. 修正需求文档中的不一致
4. 重新执行审查项 a 直到通过

## 审查项 b：需求文档 ↔ 澄清记录

**执行条件**：始终执行

**输入文件**：
- `docs/aidlc/inception/requirements/requirements.md`
- `docs/aidlc/inception/requirements/requirement-verification-questions.md`
- `docs/aidlc/audit.md`（澄清问答部分）
- 当前 inception 根下的 `requirements/business-flows.md`
- 条件适用的 `requirements/data-model.md`
- 当前场景 `scenario-manifest.md`

**审查清单**：

| # | 检查点 | 通过标准 |
|---|--------|---------|
| 1 | 用户在澄清中提供的每个答案是否已体现在需求文档中 | 所有答案均已反映 |
| 2 | 用户明确否定的内容是否已从需求中移除 | 无被否定内容残留 |
| 3 | 用户补充的新信息是否已纳入需求 | 补充信息完整纳入 |
| 4 | 澄清中确认的优先级是否与需求文档优先级一致 | 优先级一致 |
| 5 | 澄清中确认的范围边界是否在需求中明确标注 | 范围边界清晰 |
| 6 | 业务流程图节点是否与 FR 双向可映射 | 无孤立节点、无未映射到流程节点或明确外部系统动作的 FR |
| 7 | 状态流转判定是否已显式记录 | 触发时有状态图；未触发时有判定结论及依据 |
| 8 | I5 形成的状态、字段、数值、枚举能否生成有效场景定位键 | 符合 manifest §8 固定格式，在模块/语义类型/来源路径内唯一，且关联 FR 无悬空 |

**未通过处理**：
1. 列出所有遗漏/不一致项
2. 向 Boss 报告发现的问题
3. 修正需求文档
4. 重新执行审查项 b 直到通过

## 审查项 c：用户故事 ↔ 需求文档

**执行条件**：始终执行（用户故事完成后）

**输入文件**：
- `docs/aidlc/inception/user-stories/stories.md`
- `docs/aidlc/inception/user-stories/personas.md`
- `docs/aidlc/inception/user-stories/role-permission-matrix.md`
- `docs/aidlc/inception/requirements/requirements.md`
- 当前场景 `scenario-manifest.md`

**审查清单**：

| # | 检查点 | 通过标准 |
|---|--------|---------|
| 1 | 需求文档中每个功能需求（FR）是否都有对应的用户故事覆盖 | 100% FR 被覆盖 |
| 2 | 用户故事的验收标准是否与需求中的 GWT 一致 | 验收标准对齐 |
| 3 | 用户故事涉及的角色是否与 `personas.md` 及 `role-permission-matrix.md` 一致 | 角色映射正确；矩阵中每个角色至少被一个故事覆盖 |
| 4 | 用户故事是否引入了需求文档中不存在的功能 | 无超范围故事（或已标注为增强建议） |
| 5 | 需求中的优先级（Must/Should/Could）是否在故事中体现 | 优先级传递正确 |
| 6 | 权限矩阵条目能否生成有效场景定位键 | 符合 manifest §8 权限键固定格式，在模块/权限/来源路径内唯一，且关联 FR 无悬空 |

**未通过处理**：
1. 列出覆盖缺口和不一致项
2. 向 Boss 报告并建议：补充用户故事 或 修正需求文档
3. 获得 Boss 确认后执行修正
4. 重新执行审查项 c 直到通过

## 审查项 d：基于用户故事评估需求完整性

**执行条件**：始终执行（与审查项 c 同时，用户故事完成后）

**目的**：从用户故事角度**反向**验证需求文档的完整性。当用户故事描述了用户期望的行为，但需求文档中找不到对应支撑时，说明需求可能有遗漏。

**输入文件**：
- `docs/aidlc/inception/user-stories/stories.md`
- `docs/aidlc/inception/user-stories/personas.md`
- `docs/aidlc/inception/requirements/requirements.md`

**审查清单**：

| # | 检查点 | 通过标准 |
|---|--------|---------|
| 1 | 每个用户画像的核心场景是否都有需求支撑 | 所有场景有需求覆盖 |
| 2 | 用户故事中隐含的前置条件是否在需求中定义 | 前置条件明确 |
| 3 | 用户故事中的异常路径是否在需求中有对应处理 | 异常路径覆盖 |
| 4 | 跨故事的数据流转是否在需求中有完整定义 | 数据流完整 |
| 5 | 用户故事暴露的新需求是否已标注 | 新发现需求已记录 |

**未通过处理**：
1. 列出需求文档中可能遗漏的内容
2. 向 Boss 报告发现并建议补充
3. 获得 Boss 确认后补充需求文档
4. 重新执行审查项 d 直到通过

## 审查项 e：UI 设计 ↔ 用户故事 + 需求文档

**执行条件**：执行了 UI 设计步骤后（HTML Mock 模式或 Figma 模式均适用）

**输入文件**：
- 页面计划：单模块 `docs/aidlc/inception/ui-design/page-plan.md`；多模块为当前模块 `docs/aidlc/modules/{module-name}/inception/ui-design/page-plan.md`
- HTML Mock 模式：`docs/aidlc/inception/ui-mock/*-page-specs.md` + 对应 HTML 文件（标准或大型模式）
- Figma 模式：`state.md` 的 `## UI 设计` 区块 `产物位置` 中的唯一主 Figma 文件链接 + `Figma 页面进度`（通过 `get_metadata` / `get_screenshot` 验证）
- `docs/aidlc/inception/user-stories/stories.md`
- `docs/aidlc/inception/user-stories/role-permission-matrix.md`
- `docs/aidlc/inception/requirements/requirements.md`

**审查清单**：

| # | 检查点 | 通过标准 |
|---|--------|---------|
| 1 | 页面计划是否完整覆盖用户故事涉及的页面，且不存在未决项 | 所有涉及页面已计划，页面 ID 唯一稳定 |
| 2 | 模式产物是否与页面计划逐项映射 | 每个计划页面恰有一个 mock-box 或 Frame/nodeId，无遗漏或重复 |
| 3 | 可见字段/组件、输入与展示约束、条件可见性是否一致 | 与页面内容契约及需求定义逐项一致 |
| 4 | UI 设计中的角色权限是否与 `role-permission-matrix.md` 一致 | 按钮级可见性、数据范围、无权表现三者均对齐矩阵 |
| 5 | 操作按钮、反馈及交互场景是否与页面计划和用户故事验收标准对应 | 所有交互场景与操作闭环均实现，无遗漏且无计划外入口 |
| 6 | 业务状态展示是否与页面计划及需求状态机一致 | 状态差异完整 |
| 7 | 跨端数据流是否与页面计划一致 | 产生端、消费端和动作均可追溯 |
| 8 | page-specs 页面集合是否为 PRD 页面清单的唯一来源，且与 mock-box/Frame、页面计划一致 | 不存在 page-specs 之外手写的页面清单；ID、名称、类型、来源双向一致 |

**Figma 模式附加检查（必须产出证据）**：

| # | 检查点 | 可复现通过标准 |
|---|--------|---------------|
| F1 | Variable 使用 | 对每个受审 Frame 调用 `get_variable_defs`；所有可映射到已有 Variable 的颜色、间距、字体均使用 Variable。硬编码值逐项列出并标记“已修正”或给出合理例外 |
| F2 | 组件化 | 同一结构在受审范围重复 ≥3 次时使用 Component/Instance；不组件化时逐项记录原因 |
| F3 | Frame 可追溯 | state.md 页面进度中的每个 completed 页面均有唯一 nodeId，且 `get_metadata` 可定位 |
| F4 | 视觉证据 | 每个页面或每批页面有 `get_screenshot` 验证结果并记录在 state.md |

**Figma 证据表格式**：

```markdown
| Frame | nodeId | Variables 结果 | 硬编码值及处理 | 重复结构及组件化 | Screenshot | 结果 |
|-------|--------|----------------|----------------|------------------|------------|------|
| 规则列表 | 1:234 | 12 个变量 | `#F4F5F6`：插图专用色，例外 | RuleCard×4 → Component | 通过 | 通过 |
```

禁止使用无法复现的百分比或“看起来一致”作为通过依据。

**未通过处理**：
1. 为每个不一致项分配冲突 ID，在交叉验证报告中记录需求、用户故事、UI 三方描述、影响范围和建议；不得把语义差异直接归因于任一方错误。
2. 仅缺少证据、命名映射或 page-specs 对应关系的机械性问题可直接修正。涉及产品语义时，将 state.md `设计状态` 标记为 `blocked`、记录失败门禁，并按 `common-question-format-guide.md` 创建或更新 `docs/aidlc/inception/ui-mock/ui-conflict-questions.md`。
3. 加载并执行 `common-workflow-changes.md` 的“产品产物一致性协调”；该规则统一定义用户裁决选项、禁止提前修改、代码基线分流、就地更新、下游失效和重审恢复。
4. 未决冲突为零且适用审查全部通过后，才能将 state.md `设计状态` 更新为 `approved`，`下一操作` 更新为“进入 I11 工作流规划”。

## 审查项 f：页面基准产出物一致性（变更后）

**执行条件**：变更请求涉及已有前端页面（CR4 就地基线更新完成后触发）

**目的**：验证变更回写后，每个受影响页面的需求、用户故事、UI 设计三者描述一致且完整，防止同一页面出现多版本需求。

**输入文件**：
- 受影响页面的 UI 设计（HTML Mock 模式：对应 mock-box；Figma 模式：对应 Frame）
- 需求文档中描述该页面的段落
- 涉及该页面的所有用户故事
- 该页面的实际代码实现（如已有）

**审查清单**：

| # | 检查点 | 通过标准 |
|---|--------|---------|
| 1 | UI 设计中该页面是否包含变更后的所有功能入口 | 无遗漏入口 |
| 2 | 需求文档中该页面的描述是否反映变更后的完整状态 | 描述完整且无矛盾 |
| 3 | 是否存在同一页面的多份矛盾描述（不同文件中） | 无矛盾描述 |
| 4 | 源模块/单元中被迁移的功能是否已标记为"不再维护" | 旧描述已标记迁移 |
| 5 | 变更新增的功能是否已合并到页面基准（而非仅存在于变更日志） | 已合并到基准 |
| 6 | 代码实现中的页面内容是否与 UI 设计 + 需求一致 | 代码与产出物对齐 |

**未通过处理**：
1. 列出不一致项（明确指出哪个产出物缺失了什么内容）
2. 回退到 CR4 的就地基线更新，补充回写缺失的内容
3. 重新执行审查项 f 直到通过

**规则参考**：详细的页面级单一真相源判定规则见 `common-page-source-of-truth.md`

## 审查项 g：PRD 质量审查（I16）

**执行条件**：I15 已生成 PRD 且用户要求审查。

**目的**：验证 PRD 内容质量，确保无臆造内容、关键信息完整、来源可追溯。

**输入文件**：
- PRD 文件（`docs/aidlc/inception/prd.md` 或 `docs/aidlc/product/scenarios/<scenario-id>/prd.md`）
- 已有 Inception 产物（如存在）
- SSOT 检索记录（如使用）

### 审查清单

| # | 检查点 | 通过标准 | 未通过处理 |
|---|--------|----------|-----------|
| 1 | 无臆造业务规则 | 所有 `[待确认]` 已汇总；无未标记的不确定内容 | 标记为 `[待确认]` 或删除 |
| 2 | 功能需求有验收标准 | 每个功能点至少一条可验证的验收标准 | 补充验收标准 |
| 3 | 非目标明确 | 至少有 1 条排除项 | 与用户确认边界 |
| 4 | 来源索引完整 | 每章在来源索引表中有对应记录 | 补充来源标注 |
| 5 | 无技术实现细节泄露 | 不含 URL 路径、数据库表结构、API 设计、代码片段 | 移除或移至技术设计文档 |
| 6 | 与已有产物无冲突（条件：有 Inception 产物时） | PRD 描述与已有需求/故事/UI 产物无语义矛盾 | 按已有产物修正或标记差异待用户裁决 |
| 7 | 待确认问题可操作 | 每个待确认项有负责方和是否阻断标记 | 补充缺失信息 |

### 审查执行方式

1. 逐项检查上表，记录每项结果
2. 全部通过 → PRD 状态从 `draft` 更新为 `reviewed`
3. 存在未通过项 → 列出具体问题和修正建议，修正后重新检查未通过项（不重审已通过项）

### 与旧流程的差异

本审查替代原有的 13 项强制证据审查。不再要求：
- scenario-manifest SHA-256 校验
- 逐句溯源矩阵
- "分子/分母"数量证据
- 审查前门禁（4 项）

```markdown

**审查对象**：{被审查的产物}

### 审查结果

| # | 检查点 | 结果 | 说明 |
|---|--------|------|------|
| 1 | {检查点描述} | ✅/❌ | {具体说明} |
| ... | ... | ... | ... |

### 总结
- **通过项**：{N} / {Total}
- **未通过项**：{列出未通过项及原因}
- **整体结论**：✅ 通过 / ❌ 未通过，需修正

### 修正建议（如未通过）
1. {具体修正建议}

```

## 与步骤完成协议的关系

- 审查步骤本身也是一个步骤，完成后必须执行步骤完成协议（更新 state.md、微型摘要、审计记录）
- 审查步骤在 state.md 中记录为 `{步骤编号} 交叉验证 ✅/❌`
- 如果审查未通过并修正后重新通过，在审计中记录"首次未通过 → 修正后通过"
