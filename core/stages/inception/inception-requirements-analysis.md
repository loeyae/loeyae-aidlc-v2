## 步骤 2：分析用户请求（意图分析）

#### 请求清晰度
- **清晰**：具体、明确、可操作
- **模糊**：笼统、含糊、需要澄清 → **触发需求澄清流程**
- **不完整**：缺少关键信息 → **触发需求澄清流程**

> **需求澄清**：当请求清晰度为"模糊"或"不完整"时，加载 `inception-requirement-clarification.md` 执行系统性追问，完成后再继续步骤 3。

#### 模糊信号强制检测（防止过度自信判定"清晰"）

即使主观判定为"清晰"，存在以下任一信号时仍必须触发需求澄清流程：

- 未明确验收标准或成功条件；
- 未明确核心用户角色或目标受众；
- 存在多种合理解读（"可以理解为 A 也可以理解为 B"）；
- 关键业务规则缺少边界条件（如：金额范围、时间限制、状态约束）；
- 涉及多个系统或模块但未明确调用方向或数据归属；
- 使用了模糊动词（"处理"、"管理"、"优化"）但未定义具体行为。

判定为"清晰"时必须记录依据（一句话说明为什么足够清晰）。存在上述信号但仍判定清晰，必须逐条说明为什么该信号不适用。

#### 请求类型
新功能 / Bug 修复 / 重构 / 升级 / 迁移 / 增强 / 新项目

#### 初始范围估计
单文件 / 单组件 / 多组件 / 系统级 / 跨系统

#### 初始复杂度估计
微小 / 简单 / 中等 / 复杂

## 步骤 3：确定需求深度

**最小深度** — 请求清晰且简单：
- 跳过多角色澄清、其他专业方法论、优先级排序和五维验证
- 仍执行**最小澄清三问**（强制，不可跳过）：
  1. 核心目标：这个需求完成后，用户能做什么之前做不到的事？
  2. 验收标准：怎样判断做完了且做对了？
  3. 不做什么：明确排除哪些看似相关但不在本次范围的内容？
- 三问任一回答缺失或模糊时，不得继续生成需求文档——优先补充答案
- 仍执行业务流程图与状态流转适用性判定，再生成需求文档

**标准深度** — 正常复杂度：
- 执行产品视角 + 用户视角 + 架构视角澄清（3轮）
- 执行优先级排序（MoSCoW）
- 执行 5 维度验证（简化版：完整性 + 可验证性）

**全面深度** — 复杂/高风险项目：
- 执行业务流程图和其他专业方法论（利益相关者、画像、竞品）
- 执行全部 5 轮+角色澄清（含基于画像的多用户角色视角）
- 执行优先级排序（MoSCoW + RICE）
- 执行 5 维度验证（完整版 + 量化评分）
- 执行状态流转适用性判定和完整数据建模（ER 图 + 实体字段）

## 步骤 6：多角色澄清（自适应轮次）

**自适应规则**：
- 最小深度 → 跳过，直接进入步骤 11
- 标准深度 → 轮次 1（产品）+ 轮次 2（用户）+ 轮次 3（架构）
- 全面深度 → 全部轮次（含基于画像的多用户角色）+ 条件触发全局一致性

**每轮执行规则**：
1. 以当前角色视角分析需求，识别缺失/歧义点
2. 生成澄清问题（遵循问题格式指南）
3. 等待用户回答
4. 如有后续歧义则追问（同一角色内最多追问 1 次）
5. 进入下一角色轮次

**问题文件**：`docs/aidlc/inception/requirements/requirement-verification-questions.md`

---

### 轮次 1：产品视角

**角色**：产品经理 | **关注**：业务价值、用户场景、优先级、验收标准

**必须评估**：
- 业务目标、目标用户、用户场景
- 优先级、验收标准、业务约束
- 前端维度：页面、交互方式、设计稿

### 轮次 2：用户视角（标准深度 + 全面深度）

**标准深度**：以统一的"最终用户"角色执行单轮澄清。

**角色**：最终用户 | **关注**：使用体验、操作直觉性、痛点解决、学习成本

**必须评估**：
- 操作流程是否符合用户心智模型
- 核心任务的完成路径是否顺畅
- 异常/错误情况下用户的感受和预期反馈
- 学习成本和上手难度
- 前端维度：信息层级、操作反馈、引导提示

**全面深度**：基于步骤 5 产出的用户画像，为每个关键角色分别执行子轮次。

**动态角色确定规则**：
1. 从步骤 5 的用户画像中提取 2-3 个关键用户角色
2. 每个角色作为独立子轮次（轮次 2a、2b、2c...）
3. 每个子轮次以该角色的特征、目标、痛点为出发点提问

**每个子轮次必须评估**：
- 该角色的核心使用场景是否被满足
- 该角色的操作习惯和期望是否被尊重
- 该角色可能遇到的困惑和障碍
- 该角色对功能的优先级感知（与产品视角可能不同）
- 前端维度：该角色的典型设备、使用环境、交互偏好

### 轮次 3：架构视角

**角色**：架构师 | **关注**：技术可行性、系统边界、集成点、性能约束、**数据源真实性**

**必须评估**：
- 系统边界、集成点、技术约束
- 性能需求、可扩展性、安全需求
- 前端维度：状态管理、接口契约、兼容性
- **数据源溯源**（强制）：对每个功能需求中涉及的数据读取，必须追问并确认：
  - 数据从哪来？（用户输入 / 系统自动生成 / 外部接口同步 / 已有功能写入）
  - 如果是"已有功能写入"，该写入功能是否存在？入口在哪？
  - 如果是"外部接口同步"，接口是否已对接？数据格式是否已确认？
  - 如果数据源不存在或不明确，标记为 **🚨 数据源缺失风险**，要求用户澄清或纳入本次开发范围

### 轮次 4：开发视角（仅全面深度）

**角色**：开发者 | **关注**：实现细节、数据模型、接口定义、边界条件

**必须评估**：
- 数据模型、接口定义、业务规则
- 边界条件、错误处理、数据迁移
- 前端维度：组件拆分、表单校验、列表需求

### 轮次 5：测试视角（仅全面深度）

**角色**：测试人员 | **关注**：测试场景、边界用例、异常流程

**必须评估**：
- 正常流程、异常流程、边界用例
- 并发场景、权限场景、验收标准可测试性
- 前端维度：交互异常、响应式、可访问性

### 轮次 6：全局一致性（条件触发）

**触发条件**：前述轮次发现跨角色矛盾、用户视角与实施视角冲突、前后不一致、遗漏或优先级冲突时执行。

- 全面深度：完整版（5 维度 + 量化评分）
- 验证失败时：按回退路径修复后重新验证

## 步骤 11：生成需求文档

创建 `docs/aidlc/inception/requirements.md`，包含：
- 意图分析摘要
- 业务流程图引用：显式引用 `requirements/business-flows.md`，每个 FR 标注所属流程节点
- 状态流转判定：记录触发及状态图引用，或“不涉及状态流转”及依据
- 功能需求（按优先级排序，含 GWT 验收标准）
- 非功能需求（含量化指标）
- **数据源溯源表**（强制）：每个功能需求对应的数据来源清单
  - 格式：`| 功能 | 读取的数据 | 数据来源类型 | 来源确认状态 | 备注 |`
  - 来源类型：用户输入 / 系统生成 / 外部接口 / 已有功能写入 / 本次新增
  - 确认状态：✅ 已确认存在 / ⚠️ 需本次开发 / 🚨 来源不明
  - **规则**：如存在 🚨 来源不明 的条目，需求文档不得标记为完成
- 优先级排序结果（标准+全面深度）
- 数据模型引用（全面深度）
- 验证结果（标准+全面深度）
- 已知风险与约束
- 决策记录

## 可视化标准

业务流程、状态和关系图先按 `core-workflow.md` 的“文档图表格式决策”选择格式。普通文档创建或优化默认写入 Mermaid；用户明确指定 SVG、目标文档已有有效 SVG 引用，或后续 `requirements-methods` 的 `diagram-contract` 契约要求 SVG 时，调用 `aidlc-diagram-design` 并加载 SVG 标准。格式选择、图型语义、拆图和验证均由共享规范定义，不得因工具失败静默切换格式。

图表不能清晰表达或事实不足时，使用文字/表格并记录 `NEEDS_CONTEXT`。Mermaid 模式执行语法与正文一致性检查；SVG 模式在只要求源时交付 SVG 源并将未执行的目标几何/视觉标记为 `UNVERIFIED`，只有明确要求 `preview`、`render` 或 `export` 且没有可验证 Provider 时返回 `NEEDS_CAPABILITY`。不得把源不存在与 Provider 能力缺失混为一谈。
