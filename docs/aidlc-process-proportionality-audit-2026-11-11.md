# AI-DLC 流程必要性与执行成本审计

日期：2026-11-11。性质：代码、协议与既有证据审计；包含隔离夹具的短边界验证，不包含业务试跑或生产修复。

## 1. 结论与原目标

原目标是：人类完成本批次的范围、行为、接口和 UI 设计及关键决策后，Agent 在既定授权与预算内连续实施，完成真实功能和 UI 验证；可委托决策采用兜底策略并留下待复核记录，中断不丢失进度，局部问题不阻塞无关工作。

**当前实现存在局部过度实施和跨层耦合，尚不能认定实现了“低干预、低控制成本的持续交付”。** 问题集中在：局部状态变更使用较大冲突域、普通操作反复检查同一批不可变事实、证据依赖范围过宽、文档事实多处表达，以及选定宿主适配器承担过多额外编排。质量验证、授权边界和未知副作用对账仍然必要。

此前“P1/P2 工程实现完成”的结论只说明相应功能和工程测试已落地，不能推出设计足够精简、用户实际项目已畅通或业务端到端已验证。本报告收窄这一结论，不撤销仍有效的具体测试结果，也不把旧业务失败冒充当前版本回归。

## 3. M11：恢复路径与阻塞范围

用户案例：workflow `6b149b81-fb83-4f37-a4c2-2fdf1229a6f8`，`application-design@module:m11-recommend`。其他模块仍工作时，M11 因过期领取或凭据遗失无法报告，模块维护又要求全仓释放领取。

| 条件 | 当前代码的实际行为 | 审计判断 |
| --- | --- | --- |
| claim 过期，直接发布 | 拒绝 | 必要，不能让过期写入继续生效 |
| claim 过期，保有精确旧 binding | 显式续领成功，generation 更新 | 复现；不是所有过期领取都死锁 |
| binding 丢失，仍使用原 owner、原 session | 续领拒绝；附加人类指令引用也不替代旧凭据 | 复现；入口需要给出准确的恢复指引 |
| 同 owner、新 session、明确人类指令引用、精确 expected | 已有转交路径成功，无须旧 binding | 复现；其他模块状态和 registry 字节未变，未授予阶段批准 |
| 指定目标 module 的 maintenance | 仍收集全仓 workflow claims；其他模块活动即拒绝 | 复现；目标模块已无 claim 时仍被另一模块阻断 |
| binding 输入是 JSON `null` | 原始 TypeError | 复现；应该返回可操作的结构化诊断 |
| 对未停放的当前实例使用 resume | 受 parked/current-instance 条件拒绝 | 代码；resume 不等于任意过期领取恢复 |

源码：`core/tools/aidlc-session.ts:99`；`core/tools/aidlc-light-state.ts:1023、1068、1470、1581`。

因此，现场描述的维护阻塞成立，但“所有正常恢复路径都死锁”不能推广到当前仓库全部情况。优先统一现有 bind/renew/transfer 的语义与错误修复建议，明确区分 **租约过期、凭据遗失、所有权变化、工作流停放**。不要立即再增加一套与 transfer 平行的恢复引擎。

若仍需 `recover-claim`，它应是现有精确领取事务的受控入口：仅处理过期目标；读取当前 inspect token；要求真实可审计人类授权；锁内复核目标 claim；生成新所有权代次和 binding；记录前后 owner/session/generation、理由及授权；保留原证据但重新判断其有效性；不得修改兄弟模块。对同 session 凭据遗失，要显式选择恢复语义，不能靠把 `human-instruction-ref` 当密码绕过身份检查。未知旧进程副作用须继续保留并对账；普通 claim 转交也不自动迁移自主运行的 ExecutionGrant。

state 是当前领取事实，audit 是历史，registry 承担索引与布局关系，不应把三者都视为可独立编辑的领取事实源。仍不得通过手工删一处来修复。全仓静默维护可保留给布局/全量状态重建；不应成为局部领取恢复的前置条件。

## 4. 主要发现与收缩建议

### F-01：局部状态变更的冲突域过大——高优先级

**复现**：一个单元领取更新后，另一个单元即使自己的 claim 仍有效，基于旧模块 revision 的保存也会冲突。`persistWorkflowStateInner` 和 `saveClaimTransaction` 都检查整个 workflow revision（`aidlc-light-state.ts:1270、1581`）。这不是同一所有权被抢占，却表现为类似“重新读取/重新转交”的拒绝。

**建议**：先保留现有存储，使用目标实例/目标字段的条件事务；在锁内重读并合并无关字段，只对真正重叠写入拒绝。不要简单忽略 revision，也不要无条件自动重试过期 owner。仅因无关字段变化时，在提交层有界重放变更，不重跑整个报告或证据链。`aidlc-orchestrate.ts` 当前报告冲突可递归进入 `handleReportInner`，需把提交重试与语义验证重试分离。

### F-02：状态触碰、续领与审计混在同一变更机制——高优先级

**复现**：无业务变化的保存仍使 revision 增加 1、audit 增加 981 字节。每次 bind/renew 都生成新 generation，租期固定 30 分钟（`aidlc-session.ts:167` 附近）。它增加派生状态失效与旧 binding 使用失败的机会。

**建议**：无变化不落盘、不加 revision；审计记录变化事件而不是每次重复完整领取快照。区分所有权 epoch 和续租记录：真正转交/恢复轮换 epoch；正常续租在精确凭据校验下更新 lease 字段。续租仍不得超过原 ExecutionGrant 上限；若变更 epoch 语义，须检查所有消费者与旧记录兼容性，不能只改一个字段。

**代码风险**：`aidlc-native-host.ts` 不同 select 路径的续领行为不一致；日志心跳不等于 claim 续租。合法长阶段可能碰到领取过期，需用虚拟时间覆盖所有阶段切换路径。本次没有把它归因于某次真实失联。

### F-03：锁的竞争、遗留和未知状态诊断不充分——高优先级

- `aidlc-grant-store.ts:229`：其他进程持有正常活动 control lock 时，路径会拒绝为 `RECOVERY_CONTROL_LOCK_OWNER_UNKNOWN`；缺少已知竞争的有界等待/明确 busy 返回。
- `aidlc-evidence.ts:1628`：producer lock 是空文件，进程异常结束可留下无法凭所有者身份判断的锁；与实际并发生成的拒绝容易混淆。
- `aidlc-workflow-layout.ts:368`：多条路径加载所有模块，某无关模块缺失/不一致可能影响局部工作。

这些是**代码发现**，没有在真实项目中强杀进程复现。建议给现有锁补齐可验证拥有者和有界竞争语义，复用既有安全清理逻辑；只在确定死亡且精确匹配时清理，未知保持隔离。局部读取只检查依赖闭包，全批次汇合才检查全范围。不能以锁文件年龄作为接管依据。

### F-04：重复检查中混入大量不可变输入工作——高优先级

`aidlc-native-host.ts:141` 的 directive 入口绑定 grant，prepare 又按 operation/path 检查。`aidlc-execution-grant.ts:138` 加载 workflow parts、校验 claim/grant/dependency；`aidlc-grant-store.ts:313、323、397` 会重新读冻结输入与准入基线；证据执行、发布、报告路径还要分别校验。

其中授权撤销、当前所有权、期限和发布前候选一致性的边界复查**必须保留**。过度部分是同一请求、同一未变化快照反复解析签名、全量读文件、计算相同摘要。减少 CLI 次数不等于减少这部分工作。

**建议**：一次受控请求内生成经验证的输入快照，复用不可变部分；副作用执行前和结果提交前只重查必要动态事实。跨请求复用必须有明确输入身份与失效策略，不能单靠 mtime、TTL 或永久缓存。批量准备应共享验证结果，不是循环调用单路径完整检查。C8 保留完整验收矩阵，不对每个文件读都做一次 C8 级扫描。

### F-05：所谓局部证据仍有全范围成本和失效范围——高优先级

**复现一**：只指定一个文档的 scoped source digest，仍读取范围外 4 MiB 文件。`aidlc-revision.ts:251` 同时计算全局摘要，scope 限制结果的适用性，却没有限制实际读取工作。

**复现二**：普通 `traceability-matrix` checker identity 读取 143 个 Core 工具文件，包含 `aidlc-worker-recovery.ts`。`aidlc-checker-identity.ts:23、81` 仅对部分传感器使用收窄依赖，其他仍绑定整个 tools 目录。无关 worker 改动可使文档类证据身份失效。

**建议**：全局候选摘要与局部语义摘要分开按需计算；最终候选屏障仍使用完整所需范围。为每类 sensor 定义可验证依赖闭包和版本，未知依赖保守扩大，不把实现关系漏掉。与语义无关的工具改动不得强制重跑该传感器。先补齐现有缓存/选择性复用机制，不另建第二套证据系统。

### F-06：文档结构对小任务仍偏重——中优先级

阶段目录共 38 项，但 **不能说每个任务都执行 38 阶段**。express/bugfix/refactor/workshop 有 8 个 ALWAYS 项；feature/enterprise/mvp 的另外 30 项为条件阶段。已有跳过不适用设计和选择性读取规则。

仍需收缩的是被选中阶段内的事实重复：应用设计包含主设计、components、component-methods、application-services、component-dependency 五份 Markdown；功能设计包含主设计及业务逻辑、规则、实体、数据源验证等五份；另有计划、阶段报告、追踪矩阵与机器证据。每份独立编辑、校验、哈希会把一次语义修改放大为多处变更。

**建议**：人类确认的一份设计/验收事实源，按需要输出视图；派生列表和报告由事实源生成，不再要求 Agent 分别维护相同事实。以行为、风险、外部依赖和 UI 需求决定材料，不能只以阶段名强制篇数。无行为变更用简洁、结构化不适用结论；不要为填表生成假 RED。保留对真实行为的测试派生和必要回归。阶段 frontmatter 与“始终执行”等正文冲突也应统一。

判断文档必要性的标准：是否承载一个尚未表达的决策、验收事实或独立审阅视角；单纯重复名称和状态的文档应删除或自动投影。

### F-07：受控宿主适配器承担过多额外约束——高优先级的架构收缩

Skill 已明确由宿主选择模型、上下文、执行器、并行与委托。当前选定 Codex 适配器（`harness/codex/runtime/aidlc-codex-host.mjs:59` 及 gateway/driveBatch）另外启动 read-only 原生线程，只允许 `aidlc_action`，约束原生 shell/patch/MCP/委托，串行派发；普通 rule/read 也经过 `validation-execute` 检查。逐阶段交回宿主选择，再进入模型，增加控制往返。

这些限制有明确用途：在不能可信拦截原生工具时，防止模型越过受控写入与证据边界。因此不能直接删掉 gateway 后声称约束仍成立；也不能把它当成所有宿主、所有任务的必需流程。

**建议职责边界**：

| Core 必须负责 | 宿主应负责 |
| --- | --- |
| 范围、设计/验收契约、依赖和写入权限 | 模型、上下文、原生工具调用与委托 |
| claim 所有权、授权与撤销、精确发布条件 | Supervisor、进程生命周期、调度及预算执行 |
| 证据真实性、有效性、最终候选与完成判定 | 向 Core 提供可信工具事件、资源/预算事实 |
| 对恢复是否合法作判定 | 在许可范围执行恢复动作与现场对账 |

优先适配宿主现有工具前拦截、审批和 Supervisor；只读上下文可批量提供，不为每个读文件启动完整 Core 控制调用。缺少可信拦截的宿主继续使用受限 gateway 或不开放自主模式。Core 不再硬编码具体模型，也不再增加一套通用 Agent 调度器。现有 Core 内 `codexRuntime()` 等具体宿主装配应逐步移到 Harness。

H5 必须由真实用户确认精确范围，但终端输入 `Approve <digest>` 只是当前实现渠道（`aidlc-grant-store.ts:255`），不是不可替代的安全要求。可支持有可信来源证明的宿主原生审批；普通聊天确认、模型填写 JSON 均不能伪造成授权。宿主具有 Supervisor 不等于所有所需拦截能力已验证，应按能力而不是产品名决定可用适配方式。

### F-08：P2 持久记账已减量，但频率仍需按语义收缩——中优先级

`harness/codex/runtime/host-progress.cjs` 在 turn/step/checkpoint/observation 等位置持久化进度，操作 intent/finish 又单独记录。`aidlc-grant-store.ts` 保存签名增量和周期快照；读取恢复状态还需要检查记录集合。现有优化已经降低全快照写入，不能称其“每次都全量重写”。

历史 P2 工程样本：100 操作由 6,700,886 字节降至 459,522 字节，减少约 93.1%；耗时由 36.2 秒降至 32.6 秒。体积改进明显，但单次样本的时延改进有限；这不是业务端到端提速证明（来源 `docs/aidlc-autonomous-implementation-p2.md:98`）。

**建议**：副作用前的预算预留、操作 ID、fencing 和未知结果必须持久；把可原子合并的预算预留与 intent 合并，去掉无变化 checkpoint，将纯诊断日志与恢复权威记录分离。不要为减少 I/O 丢掉执行前 intent，造成重启后重复副作用。优先优化现有文件事务，不因本次审计新增数据库、事件总线或另一套恢复调度器。

单次执行已有期限、步骤、回合和无进展上限，所以并非字面上的无限执行。实际拖长来自：跨轮重新准备和授权、长前缀重跑、冲突重验、证据过宽失效，以及缺少对同一优化目标的总成本/收益停止条件。继续提高步数或增加新试点不能解决这些原因。

## 6. 已有措施应保留，不能重新实施一遍

- 显式采用、批次边界、非采用模式兼容。
- 委托决策与缺失关键设计分流，原始 RED/失败证据保留。
- 候选版本屏障、提案隔离、范围变化不能偷换既有授权。
- 部分语义证据选择性复用、请求内摘要缓存、能力证据按原期限/HostRef/配置复用。
- 浏览器复用与用例状态隔离、真实 API/导航/UI 断言。
- 有界资源等待、终止信号与实际退出分离、未知副作用不自动接管。
- P2 增量持久化与原授权/预算约束。

本次需要扩展它们的实际覆盖、减少重复消费者与宽范围读取，而不是再创建一层同名机制。

## 7. 建议的实施顺序、验证与停止条件

以下为建议，尚未修改生产实现。为避免审计本身继续扩张，不新建一轮长流程和逐项真实试点。

| 顺序 | 一次完成的调整 | 最小必要验证与退出条件 |
| --- | --- | --- |
| S1 状态与恢复 | 统一 renew/transfer/recovery 诊断；处理 null；局部 claim 条件事务；无变化保存；busy/未知/遗留锁区分 | 短并发/虚拟时间测试：无关单元更新不误拒绝；真正重叠写拒绝；新 session 精确恢复不改兄弟；缺 token/授权、非过期恢复拒绝；旧写入被 fence；不绕过 approved gate。现场 M11 另核对实际版本与命令 |
| S2 校验与记录成本 | 分开不可变快照和动态边界检查；局部摘要实际局部读取；sensor 依赖闭包；合并既有 P2 可合并写入 | 固定输入计数验证：同请求不可变输入不重复计算；局部摘要不读无关大文件；无关工具变动不失效 sensor；撤销/到期/变化在提交前仍拒绝；无变化持久写为零；崩溃后的 intent/预算仍准确 |
| S3 文档与宿主 | 合并重复事实源与派生视图；清理冲突规则；复用原生工具、审批和 Supervisor，受限 gateway 作为能力不足时的选项 | 协议/分发检查与工具前拦截契约测试；只读上下文无逐文件 CLI 往返；全部适用 AC、API、UI 和候选门禁不降低；没有可信宿主能力就不宣称该适配方式已支持 |
| 最终一次汇合 | 冻结最终来源，复用仍有效局部证据，完成一条完整工程链和关键拒绝矩阵 | 不重复每项长前缀；工程集成通过后再安排一次全新真实验收，授权须有效；失败保留尾段，优先定点复现，不默认开下一轮试点 |

性能比较必须使用相同冻结场景、相同硬件和输入，分别记录 CLI 次数、读取字节、摘要次数、持久写次数和互斥耗时分段。结构性计数先达标，再讨论 wall time；模型/RPC 波动不能用于证明 Core 优化。可将控制面耗时至少减半设为后续评估目标，但它是待测目标，不是本次结论。

停止新增机制的条件：同一风险已有一个权威事实源、一个执行前边界和一个提交边界即可；新校验必须说明它捕获了哪种现有边界漏掉的故障，否则合并或删除。已通过且输入/检查器未变化的证据直接复用。只有新失败、来源变化或未覆盖风险才扩大验证。

最终完成标准仍是：在既定设计和授权下实际连续交付，所有适用功能与 UI 验收通过，局部恢复不拖停无关工作，真实状态可解释，控制成本有同场景对照。工程测试数量、文档数量和新增拒绝分支数量都不能代替这一标准。
