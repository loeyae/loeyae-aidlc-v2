# AI-DLC 全流程减负复审（2026-11-12）

## 结论和核验范围

仍有过度设计与迁移遗漏，不能认定“所有 AI-DLC 流程都已减负”。仓库默认主入口已经解除旧控制面的执行阻断，但安装落地、子 Skill、元数据与详细规则尚未统一。两个业务试点通过的结论有效；它们验证了当前会话按新协议直接实施，没有覆盖所有独立 Skill 或已安装入口。

本轮核对十种 Harness 入口/安装与 Hook、21 个 Core Skill、38 个阶段声明、需求/设计/UI/单元/测试/审查/交付规则，以及状态写入、续领、证据复用的关键实现。各 Skill 和阶段清单记录于 `.artifacts/process-audit-20261112/inventory.json`。这是全类别静态审计与关键入口实测，不是对全部实现语句或所有分支的动态穷举。

没有修改生产代码、全局安装、业务试点或状态，没有重跑真实业务试点。只新增本报告及本地只读审计输出，根 state/audit SHA-256 与此前一致。

## 已证实的问题

### A1 高：日常安装入口尚未采用新版

实际 PATH 指向 `E:/Work/repo/node/loeyae-aidlc.ps1`，其包目录 `E:/Work/repo/node/node_modules/loeyae-aidlc` 没有 `aidlc-host-work.ts`。实际执行该包 `work --help` 返回 exit 1、`unknown command: work`；仓库相同命令 exit 0。

`C:/Users/loeye/.agents/skills/loeyae-aidlc/SKILL.md:13` 仍默认 `orchestrate next`，第 22 行仍要求精确领取。已安装测试派生和构建 Skill 也没有宿主协议。之前试点显式调用仓库 CLI，不能证明日常 PATH/Skill 已升级。

处置：同步可部署包和 Skill，再核验实际解析路径、功能和默认指令。升级应保留用户配置和旧项目记录，不在每次工作时重新做安装/版本准入。

### A2 高：Skill 元数据与正文仍把旧要求带入上下文

21 个 Skill 中只有 8 个显式引用宿主协议；其余 13 个不等于全部有问题，独立 SVG/DOCX 等专用能力可有必要格式要求。但已改的部分 Skill 也只是前置短说明，旧正文仍全部进入上下文。

直接例证：`core/skills/aidlc-test-case-derivation/SKILL.md:3` 的 description 仍规定“所有进入代码生成的 scope 都必须执行 I13”，第 9 行却说不要求 I13。元数据会在正文加载之前影响宿主选用行为。构建 Skill 为 12,111 字节，仍加载 C8 阶段和 11,151 字节测试策略；审查 Skill 直接加载 27,897 字节阶段文件；测试派生协议为 21,877 字节。前置豁免文字没有减少这些加载成本。

处置：默认 Skill 只保留原生能力步骤、必要输入、实际验证与结果；元数据一并更新。旧受管细节移到独立兼容参考，仅明确使用旧接口时读取，而不是继续给长正文加前言。

### A3 高：UI 及若干能力入口仍显式依赖受管产物

- `aidlc-ui-mock-design/SKILL.md:19–38` 要求页面计划路径、skeleton/content 阶段、manifest，以及当前签名 Stage 的受控 producer。
- `aidlc-figma-design/SKILL.md:21–41` 要求编排层能力结果、Core canonical manifest 和签名 I9 choice；第 33 行还禁止直接使用服务读取工具，与宿主原生读取设计的默认职责不一致。
- `aidlc-ui-implementation-bridge/SKILL.md:23` 要求当前 directive 的 module/unit/artifact_root；缺任一输入返回 NEEDS_CONTEXT。
- 逆向工程、部署配置/验证等仍通过加载旧阶段规则引入固定产物或编排前置。必要环境/部署授权应保留；“缺已有部署配置”“缺规范化阶段记录”不应作为新项目或单纯静态验证的拒绝条件。

这是已确认的指令依赖，不宣称本轮复现了模型被阻断。两个试点复用了完成的设计且是纯 Web，未触达上述设计准备与跨端桥接入口。

处置：已有设计直接读；缺业务事实才澄清；页面清单/组件映射按实际复杂度需要生成，不要求先构造受管身份。真实 UI 状态、尺寸、交互、API 和约定像素验收保持。

### A4 高：新版 work 的默认输出仍会挤占上下文

当前仓库只读实测：

| 命令 | exit | 单次耗时 | stdout |
| --- | --- | --- | --- |
| 仓库 work --help | 0 | 304 ms | 189 B |
| 全局安装包 work --help | 1 | 242 ms | 0 B，错误在 stderr |
| 仓库 --help | 0 | 283 ms | 14,407 B |
| 仓库 work（未限制 paths） | 0 | 1,451 ms | **114,205 B** |

work 中 Git status 为 71,296 B，diff 统计为 39,934 B。`core/tools/aidlc-host-work.ts:30–37` 的 maxBuffer 是进程输出上限，不是提供给模型的摘要限制；第 57–59 行直接返回全文。每个 Git 调用有 10 秒 timeout，因此不是无限等待，但大仓库直接使用默认命令仍可能加载大量无关路径。不能由此推断实际 token 数或其他仓库的耗时。

处置：默认只返回计数、有限相关路径和清晰截断标记；详细 Git 变化显式按需读取。默认 help 只展示宿主路径，兼容命令移到专门帮助。不要因此再建立摘要数据库或强制分页会话。原始输出及测量见 `.artifacts/process-audit-20261112/entry-checks.json`。

### A5 中：旧阶段仍有重复文档结构，状态成本不能误判为已删除

阶段图共有 97 项产物声明，其中 51 项 `.aidlc` evidence、37 项 Markdown，124 次 sensor 声明对应 39 种 sensor。**这是目录声明统计，不代表任何单个任务会执行 38 阶段或生成全部产物。**

明确可精简的重复包括 units + manifest + unit-of-work/dependency/story-map，以及 NFR/基础设施设计的主文档、同名子正文和附加计划。默认路径不运行这些阶段，但旧 Skill 或旧安装仍可能引入它们。业务事实应在现有设计中保持一个权威来源，索引由读取派生；特殊合规/客户交付文档按明确需要保留。

当前 `persistWorkflowState` 已有无变化不发布（aidlc-light-state.ts:1313），独立领取可 rebase，正常未过期续领保持 generation（aidlc-session.ts:168）。不能重复引用旧审计结论，声称现在每次保存都写状态或续领都换代。

旧受管路径仍有 revision/lock/binding/facts/runtime 等成本；work 不导入它们、不写控制状态。暂存旧运行的身份保护有必要，不能为了简化手工删除未知 claim。后续应明确退出旧模式的使用路径，而非再次扩展通用恢复体系。

### A6 中：审查、构建和“没有行为”证明仍有相互依赖风险

构建 Skill 第 28 行要求审查已通过；代码审查阶段第 43–52 行要求测试、构建与运行证据，第 98 行又禁止审查前启动 C8。旧引擎可借助早期执行记录区分这些动作，独立调用者却必须理解整套阶段语义。测试派生仍为无行为范围要求 `non-applicable.json`、approval_ref、alternative_validation 等，与“简单文档变更仅检查相关链接/结构”的目标不相称。

测试策略已经强调最小充分验证与不默认全量，这是有效改进。问题在同一入口又要求 freshness/签名/阶段记录，因此“无需重测”与“重新产证”边界仍可能被模型误解。旧受管替代观察已有复用逻辑（aidlc-evidence.ts:992），不能把所有复验称为真实测试重跑。

处置：宿主自由安排构建、测试、审查，按实际发现返修；通过声明引用实际结果，不能以审查尚未完成禁止运行测试。纯说明文档不强制建立 I13 不适用证明。相关实现、依赖或验收变化才重验；只复核未变输出无需再执行命令。

### A7 中：调试与返修的收敛规则尚不匹配

`common-systematic-debugging.md:24–44` 将四阶段方式用于任何技术问题，第 55 行开始要求可复现步骤等，Skill 缺复现/证据返回 NEEDS_CONTEXT。必要的根因思考应保留，但不能把收集复现条件本身挡在门外；小语法/路径错误也不需要正式调查记录。

默认宿主协议规定失败继续修复，却未具体说明重复同样失败且没有新证据时如何收敛。旧审查循环有“未通过→修复”，不足以保证宿主不会陷入无进展循环。这是规则缺口，不是本轮已观测到无限运行。

处置：按风险决定调查深度。重跑必须有变化或新的诊断目的；无新增信息时更换诊断方式、缩小范围或说明实际阻塞，并继续其他独立工作。不要恢复 AI-DLC 自有步骤计数器、续验租约或统一 8 分钟硬终止。

### A8 低：默认安装仍注册低价值 Stop Hook

Codex 安装分支仍调用 registerCodexHooks（bin/cli.ts:1102），本机 hooks.json 仍有该入口。仓库版未绑定时已快速返回，绑定时也最终 exit 0；OpenCode idle 派发已经删除。因此不能说当前新版 Stop 仍强制阶段完成，但每次回合退出保留一个主要服务旧模式的命令钩子没有必要。

处置：新默认安装不主动注册；既有诊断入口作为旧模式可选项。迁移仅移除本工具拥有的钩子，不修改其他用户 Hook。

### A9 中：现有验收不足以证明所有入口统一

`test_host_execution_distribution.ts` 验证主入口关键词、协议链接、工具文件存在及 OpenCode 行为；不覆盖 21 个独立 Skill 的元数据/加载依赖，也不检查实际 PATH 和安装 Skill。因此“十种分发通过”不能推出所有能力已经迁移。两个试点是有上下文的当前会话直接执行，设计准备、Figma/跨端、部署准备等未覆盖。

处置：以少量入口契约检查覆盖默认元数据、能力加载、安装解析及文档-only/已有 UI/存量项目三个代表场景。先验证这些边界，不为每个 Skill 建完整业务项目或重跑旧长前缀。

## 不应误删的内容

保留明确业务验收、实际功能/边界测试、相关集成验证、真实 UI 比对、实际部署授权、未知运行/他人修改的保护。SVG 与 DOCX 的专项格式要求不因文件较大就判为普遍过度设计；按需加载才是关键。旧引擎物理存在不等于当前每次工作都承担其耗时。

## 建议收口顺序与验收

1. **统一入口**：默认 Skill 元数据与正文分离旧模式，补齐 UI/逆向/调试/交付能力；实际包与 Skill 同步升级。验收真实 PATH 支持 work，直接调用能力无需 phase/claim/manifest 才能开始。
2. **限制默认上下文**：work/help 默认简短，详细路径按需。验收大工作区输出有明确上界与截断说明，不要求使用者先提供完整路径才能避免大输出。
3. **缩减产物和重复验证**：同一业务事实一处维护，实际测试结果可复用；构建与审查不相互挡住，普通文档无需无行为证明；不增加新状态权威。
4. **验证收敛与安装**：覆盖元数据、直接能力调用、纯文档、现有 UI、旧状态损坏和无进展失败诊断。保留必要质量检查，停止相同无信息重跑。通过后只做一次所需代表性验收，不再逐项重跑两个试点。

上述为审计时点的结论和修复建议。后续已完成本轮默认入口减负、上下文边界与实际安装升级，逐项关闭依据和验证限制见 [实施方案与记录](aidlc-flow-simplification-implementation.md)。原始审计证据保持，不把静态规则检查视为所有宿主/能力的真实模型验证。
