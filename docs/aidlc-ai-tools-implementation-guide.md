# 在 AI 工具中使用 AI-DLC 实施项目指南

本文面向在 Kiro（IDE / CLI / Crew）、Claude Code、Codex、OpenCode、CodeBuddy、Qoder、ZCode 和 Multica 的**对话**中推进项目的人。全程用自然语言提示词驱动：你描述工作、回答问题、做决策；AI 负责执行 `loeyae-aidlc` 命令、写产物、跑测试和上报阶段。

| 场景 | 典型诉求 | 章节 |
| --- | --- | --- |
| 正序实施（新项目 / 新功能） | 从零做一个系统或一个完整功能 | §4 |
| 已有项目定制开发 | 在存量代码上加功能、改造模块 | §5 |
| 缺陷修复 / 无行为重构 | 修 bug、整理代码但不改变行为 | §6 |
| 变更请求（CR） | 已交付的行为、契约或验收标准要改 | §7 |

命令本身不需要你记。想核对 AI 是否执行了正确的动作时，查附录 B 或 `docs/loeyae-aidlc-cli-guide.md`。

## 1. 对话中的分工

每一轮对话都是同一个循环：

```text
你：提示词（开工 / 继续 / 回答 / 批准）
AI：读取当前阶段 → 产出文档或代码 → 运行检查 → 上报阶段
AI：展示“下一步提示”（handoff_prompt），需要你决定时停下来提问
你：回答，或说“继续”
```

你需要把握的五件事：

1. **提示词里带上“使用 AI-DLC”。** 各工具的 AI-DLC Skill 靠这类关键词加载（“使用 AI-DLC”“开始新工作”“继续当前工作”等）。不带关键词时，AI 可能按普通对话处理，绕开流程。
2. **流程由引擎决定，不要让 AI 跳步。** AI 每次只做引擎给出的当前阶段。你说“快一点”“跳过设计”，AI 应当拒绝跳过必需门禁，最多缩小交付范围。
3. **只有你能做决策。** 单/多模块选择、需求优先级、UI 设计方式、应用设计批准、部署批准、CR 风险确认、最终 merge，AI 都必须问你，不能替你回答。
4. **看“下一步提示”。** 每完成一个阶段，AI 会原样展示一段 handoff_prompt，写明工作目标、当前阶段、产物和下一步。换会话、换人、换工具都靠它续接；AI 没展示时，直接说“展示 AI-DLC 下一步提示”。
5. **完成以检查通过为准。** AI 写出文件不等于阶段完成；阶段只有在引擎检查（产物、追溯矩阵、测试证据）通过后才算完成。证据文件由引擎生成，AI 手写会被判为伪造。

## 2. 一次性准备

安装需要在终端执行一次，也可以让 AI 代劳。

**让 AI 代劳的提示词：**

```text
帮我安装 loeyae-aidlc：从 https://github.com/loeyae/loeyae-aidlc-v2/archive/refs/heads/main.tar.gz 全局安装，
然后部署到 Kiro IDE，并给当前项目安装 Stop Hook。装完用 install --list 和 version 自检。
```

**要点：**

- 全局安装后需重启工具，Skill 才会生效。
- Kiro IDE / Kiro CLI 的 Stop Hook 是项目级的，每个业务项目单独安装一次（`--project`）；没有 Hook 时流程照样能走，只是会话结束时不会提醒你“流程仍在进行”。
- `--project` 指向的路径不存在时，CLI 会先装好全局 Skill 再报错，只缺 Hook，修正路径后重来即可。
- 安装细节和升级步骤见 `docs/loeyae-aidlc-v2-installation.md`。

**项目侧配置（按需，可以交给 AI）：**

| 情况 | 提示词 |
| --- | --- |
| 源码不在 `src/`（如 Python 的 `app/`、前端 `web/src`） | `使用 AI-DLC，本项目源码根是 app 和 web/src，帮我配置 source-roots` |
| 业务代码在独立的嵌套 git 仓库 | `使用 AI-DLC，app/ 是独立 git 仓库，按嵌套仓库配置 source-roots` |
| 到了 RED / GREEN / 构建测试阶段 | AI 会根据项目实际测试命令生成 `.aidlc/commands/<stage>.json`；你只需确认它用的是真实命令（如 `npm test`、`mvn test`、`pytest`） |

## 3. 在各工具中怎么开始

| 工具 | 在哪里说 | 补充 |
| --- | --- | --- |
| Kiro IDE | Chat 面板 | 一个 Chat 会话当“协调者”，从头到尾在同一个会话推进最省事 |
| Kiro CLI | `kiro-cli chat` | 与 Kiro IDE 共用同一个 Skill，提示词完全相同 |
| Kiro Crew | 主会话 | 遇到可并行或需独立审查的阶段，主会话会派发子 agent；只有主会话能上报阶段和接受批准 |
| Claude Code | 对话 | 审批阶段可直接输入 `/aidlc-approve` |
| Codex / OpenCode / CodeBuddy / Qoder / ZCode | 对话 | 提示词与上面相同 |
| Multica | 父议题评论 / 对话 | 由父议题的协调者推进，子议题只交付产物（见 §8.3） |

### 3.1 开工提示词怎么写

工作描述决定了后面的需求、故事和测试会不会跑偏。建议按这个模板写：

```text
使用 AI-DLC 开始新工作，scope 用 <feature / classic / express / bugfix / refactor …>。
目标：<要实现或修复什么>
范围：<涉及哪些模块、页面、接口>
不做：<明确排除的内容>
约束：<技术栈、兼容性、性能、合规>
验收：<怎样算完成>
```

不确定 scope 时可以不写，AI 会列出可选项问你。scope 选择见 §4.1。

## 4. 流程 A：正序实施（新项目 / 新功能）

### 4.1 选 scope

| scope | 阶段数（单模块） | 经过的流程 | 适用 |
| --- | --- | --- | --- |
| `feature` / `enterprise` / `mvp` | 45 | 完整 Inception → Construction → 部署运维（条件） | 常规功能、新系统、需要部署准备的交付 |
| `classic` | 43 | 同上，不含部署运维 | 不需要部署准备 |
| `express` / `workshop` / `bugfix` / `refactor` / `poc` | 8 | 工作区检测 → 状态模板 → 测试用例派生 → RED → GREEN → 代码审查 → 构建测试 → 实现报告 | 小改动、演示培训、缺陷修复、重构、概念验证 |

- 以上为 loeyae-aidlc 4.13.0 实测；选多模块后，模块级和单元级阶段按模块数、单元数展开。
- 8 阶段 scope 没有需求、故事和设计阶段，工作描述就是需求输入；也没有单/多模块选择，不能并行拆分。
- `poc` 与 `express` 路由完全相同，并不更宽松：同样要求测试用例、RED、GREEN、审查和真实构建测试。
- 需要 PRD 时在开工提示词里说“需要生成 PRD”，只在完整 scope 开工时有效，之后不能补选。
- 开工后发现小 scope 不够用（需要需求或设计），说“暂停并归档当前 AI-DLC 工作”，再用完整 scope 重新开工。

### 4.2 开工示例

```text
使用 AI-DLC 开始新工作，scope 用 feature。
目标：订单导出支持按条件导出 CSV，超时自动重试 3 次。
范围：订单模块后端接口和管理端导出页面。
不做：Excel 格式、异步任务中心。
约束：Spring Boot 3，单次导出不超过 10 万行。
验收：1 万行 30 秒内完成；失败重试 3 次后提示用户。
```

AI 会初始化流程，并自动把当前提交记为基线，然后进入第一个阶段。

### 4.3 全流程对话路线图

下表按阶段顺序列出 AI 会做什么、哪里会停下来问你、你可以怎么回答。没有“需要你”的阶段，你只需说“继续”或什么都不说，AI 会自动推进。条件不满足的阶段（如没有 UI 需求时的 UI 设计）会被引擎自动跳过。

| 阶段 | AI 会做 | 需要你 | 你可以这样说 |
| --- | --- | --- | --- |
| 0.1 工作区检测 | 识别技术栈、构建与测试入口、模块边界 | 选单模块还是多模块 | `单模块` / `多模块，订单、库存、结算三个模块` |
| 1.x 产品 Inception（多模块） | 模块划分、跨模块契约、场景映射、PRD（如已选） | 确认模块边界与契约 | `模块划分可以，库存模块不对外提供写接口` |
| 2.1 逆向工程（存量项目） | 分析现有代码，产出架构与业务梳理 | 产物已存在时确认是否重做 | `代码没大改，跳过逆向工程` / `重新分析` |
| 2.2 需求分析 | 写需求，编号 `REQ-xxx` 并标注类型 | 审阅需求 | `REQ-003 的超时改为 60 秒` |
| 2.2.1 需求澄清 | 每次只问一个问题，附推荐答案 | 逐个回答 | `按推荐` / `不对，重试间隔用指数退避` |
| 2.2.4 需求优先级 | 给出优先级建议 | 定优先级 | `REQ-001、002 是 P0，导出页面美化放 P2` |
| 2.4 用户故事 | 生成故事与验收标准 | 审阅 | `补一个“导出失败通知管理员”的故事` |
| 2.5 UI 设计（有界面时） | 页面规划，再按你的选择做 HTML Mock 或 Figma | 选设计方式 | `用 HTML Mock` / `用已有 Figma 稿，链接是 …` / `跳过 UI 设计` |
| 2.5.9 交叉验证 | 对账需求、故事、UI 是否一致 | 有冲突时裁决 | `以需求为准` / `以 UI 为准` / `重新定义：……` |
| 2.6 工作流规划 | 规划后续执行路径 | 无 | `继续` |
| 2.7 应用设计 | 组件、接口、依赖图（默认 Mermaid） | **批准** | `批准应用设计` / `接口要拆成同步和异步两个，改完再给我看` |
| 2.8 单元生成 | 拆分工作单元 | 团队开发时认领单元（§8） | `我负责 export-api 单元，分支 feat/order-export-api` |
| 2.8.1 测试用例派生 | 为每个行为生成测试用例（UC-D） | 知会即可，无需批准 | 有意见时：`UC-D-004 漏了空结果导出的场景` |
| 3.1–3.4 单元设计 | 功能设计、NFR、基础设施、共享契约（按条件） | 审阅 | `继续` |
| 3.5 RED | 先写测试并运行，证明测试真实失败 | 确认测试命令是真实的 | `测试命令用 mvn -pl order test` |
| 3.5.1 GREEN | 写实现代码，测试全部通过 | 无 | `继续` |
| 3.6 代码审查 | 需求符合性与代码规范两方面审查 | 看审查结论 | `审查提的第 2 点先不改，记为已知风险` |
| 3.7 构建与测试 | 运行真实构建和测试 | 无 | `继续` |
| 3.8 实现报告 | 汇总交付内容和验证证据 | 审阅 | `继续` |
| 4.1 部署运维（条件） | 部署目标、配置、回滚说明 | **批准** | `批准部署方案` / `部署目标改为 K8s` |

**两条底线：**

- 设计阶段需要画图时默认用 Mermaid。确实要 SVG，请明确说“这张图用 SVG”，AI 不会自己改格式。
- RED 必须真实失败、GREEN 必须真实通过。不要接受“测试已编写，逻辑上会失败”这类文字说明；AI 应当给出实际运行结果。

### 4.4 多模块并行

模块划分完成后，可以让每个模块独立推进，避免一个模块卡住拖累全部：

```text
使用 AI-DLC，先预览按模块拆分的结果，确认没问题再拆分
使用 AI-DLC，继续推进 order 模块
使用 AI-DLC，现在各模块进度和阻塞是什么
```

拆分后说“继续”时，若有多个模块可推进，AI 会问你推进哪个，而不会自己挑。跨模块集成（尾部的构建测试和报告）要等所有模块完成、所有共享契约验证通过后才会开始。

### 4.5 收尾

```text
使用 AI-DLC，为 export-api 单元生成 merge plan
```

AI 只给出建议的 merge 命令，**由你或有权限的人执行 merge 和 push**。全部完成后：

```text
使用 AI-DLC，归档当前工作，原因：订单导出 v1 交付完成
```

归档后才能在同一个项目开始下一项工作。

## 5. 流程 B：已有项目上定制开发

阶段与正序实施相同，区别是要先看清并锁定现状。

### 5.1 开工前

1. **先提交或清理工作区。** 开工时引擎会自动把当前提交记为基线，之后判断“哪些代码是本次改的”“存量行为是否被改坏”都以它为准。工作区里有未提交的改动会混进基线判断。
2. 源码不在 `src/` 或有嵌套仓库时，先按 §2 配置。

### 5.2 开工提示词

```text
使用 AI-DLC 开始新工作，scope 用 feature。
这是已有系统上的定制开发。
目标：在现有订单模块上增加按门店导出。
范围：只改 order-service 的导出接口和管理端订单列表页。
不能影响：现有按时间导出的行为和接口格式。
验收：……
```

### 5.3 对话中的关键点

| 时机 | AI 会做 | 你要关注 / 可以说 |
| --- | --- | --- |
| 开工后 | 自动记录基线 | `使用 AI-DLC，展示当前基线`，确认是你预期的起点提交 |
| 逆向工程 | 梳理现有架构与业务 | 产物已存在且代码没大改时可以说 `跳过逆向工程` |
| 需求分析 | 新需求照常编号 | 涉及改变现有行为的，要求 AI 写明“当前行为 → 期望行为” |
| 测试用例派生 | 区分新行为与存量行为 | 新功能用新行为用例（先失败再通过）；本次会触碰但必须保持不变的存量行为，用“特征化”用例锁定（在改代码前先跑一遍证明现状通过）。可以说：`按时间导出的现有行为用特征化用例锁定，理由是本次要改同一个 Service` |
| 构建测试 | 只检查本单元相对基线改动的文件 | 存量代码里的历史问题不会卡住本次交付；但本次交付的文件里至少要有一处引用本单元的需求编号 |

不存在“重构可以不写测试”的豁免。

### 5.4 多个单元先后改同一批代码

前一个单元完成并提交后，下一个单元开始前要推进基线：

```text
使用 AI-DLC，unit-a 已完成并提交，推进基线到 unit-a 的完成点，再继续 unit-b
```

AI 会核对 unit-a 的测试证据所在提交再推进。某个单元做到一半（已跑特征化用例、还没通过实现）时不能推进。

### 5.5 存量项目的特殊情况

| 情况 | 提示词 |
| --- | --- |
| 旧项目需求没有 `REQ-xxx` 编号 | `使用 AI-DLC，旧需求缺编号，帮我按迁移计划补齐`（引擎会降级放行并给出缺失清单，详见 `docs/optimization-notes/legacy-migration-plan.md`） |
| 4.6 之前开工的老流程没有基线 | `使用 AI-DLC，给当前流程补登基线，起点是提交 <完整 sha>`（只能用开工前的提交） |
| 某模块在接入流程前已按旧方式提交了实现 | `使用 AI-DLC，把 order 模块在提交 <sha> 的现有实现登记为接管基线，批准记录是 <评审单号>`（仅拆分模块后可用） |
| 合并分支后提示存在另一条流程 | `使用 AI-DLC，检查流程 lineage`，再由负责人决定保留哪条；合并冲突时不要对 `aidlc/active/` 整个目录选“保留本地” |

## 6. 流程 C：缺陷修复与无行为重构

两者都不改变已批准的行为，**不走 CR**，也不经过需求和设计阶段（8 个阶段，见 §4.1）。工作描述是唯一的需求输入，要写清依据。

**缺陷修复：**

```text
使用 AI-DLC 开始新工作，scope 用 bugfix。
缺陷：订单导出超过 1 万行时超时。
依据：REQ-012 验收标准要求 1 万行 30 秒内完成。
复现：导出 2026-09 全量订单。
```

AI 必须先写一个能复现缺陷的测试并证明它失败，再修代码；只有特征化用例、没有复现用例的 bugfix 会被引擎拒绝。

**无行为重构：**

```text
使用 AI-DLC 开始新工作，scope 用 refactor。
目标：拆分 OrderExportService，外部行为和接口不变。
锁定行为：按时间导出、按条件导出、失败重试。
```

AI 用特征化用例锁定这些行为，重构后证明行为不变。

**边界：** 修复后行为回到已批准的需求 = 缺陷；修复时“顺便”改了验收标准或接口 = 需求变更，要转 CR。拿不准时直接问：`使用 AI-DLC，这个改动算缺陷还是需求变更？`

## 7. 流程 D：变更请求（CR）

完整规则见 `core/knowledge/protocols/change-request-process.md`。核心：CR 是临时差异，正式需求、故事、设计等文档要**就地更新**，Git 历史是唯一长期记录。

### 7.1 发起

```text
使用 AI-DLC 发起变更请求：
当前行为：订单导出同步返回文件。
期望行为：改为异步任务，接口返回任务 ID，完成后站内通知。
原因：大批量导出导致网关超时。
```

AI 会先判断这是不是 CR：

| AI 的判断 | 含义 | 后续 |
| --- | --- | --- |
| 在途协调 | 受影响的部分还没有代码基线（没实现或没通过构建测试） | 不建 CR；你裁决以哪份文档为准，AI 就地更新并从最早受影响的阶段重做 |
| 缺陷修复 / 无行为重构 | 实现与已批准内容不符，或只改内部结构 | 转 §6 |
| 需求 / 契约变更 | 已有代码基线，且改变行为、验收标准、接口、数据语义 | 进入 CR1–CR5 |

### 7.2 CR 对话过程

| 步骤 | AI 会做 | 需要你 | 你可以这样说 |
| --- | --- | --- | --- |
| CR1 定位 | 找出受影响的需求、故事、用例、设计、代码，列出当前/期望行为 | 确认目标 | `目标没问题，通知渠道只用站内信` |
| CR2 影响评估 | 沿需求→设计→契约→消费者→代码→验证评估，给出 L1–L5 风险级别 | **确认风险级别与范围** | `同意 L3，结算模块只需验证不用改` |
| CR3 计划 | 按依赖与部署顺序列出步骤 | 确认计划 | `按计划执行` |
| CR4 执行 | 改代码，并就地更新 PRD、需求、故事、设计、契约、测试用例 | L4–L5 时批准迁移与回滚方案 | `批准迁移与回滚方案` |
| CR5 合并门禁 | 一致性验证与关闭清单 | 执行 merge | `门禁都过了，我来合并` |

风险级别：

| 级别 | 含义 | 处理 |
| --- | --- | --- |
| L1 | 单文件 / 单组件，不改外部行为 | 定向修改与验证 |
| L2 | 单服务行为变化，无跨边界影响 | 精简 CR，服务级回归 |
| L3 | 多服务受影响，但接口兼容 | 完整影响域，逐个消费者验证 |
| L4 | 破坏性接口、共享配置、数据迁移 | 从最早受影响的需求/设计阶段重做，审批迁移与回滚 |
| L5 | 关键链路、难回滚或影响未知 | 严格审批、系统级验证 |

缺少消费者、负责人或契约信息时，AI 至少按 L4 处理，你不能要求它降级。

### 7.3 流程状态不同时怎么说

- **当前流程还在进行**：直接在当前会话发起，AI 按 CR 协议就地处理，受影响的已完成阶段会重新检查。
- **上一个流程已归档**：作为新工作开工，描述里带上 CR 编号。L4–L5 用完整 scope；L1–L2 的局部变化也必须经过测试用例 → RED → GREEN。

  ```text
  使用 AI-DLC 开始新工作，scope 用 feature。
  CR-023：订单导出由同步改为异步任务，接口返回任务 ID。
  ```

### 7.4 关闭前自查

可以直接问：`使用 AI-DLC，CR-023 的合并门禁还差什么？` 关闭条件：

- 需求、故事、设计、测试用例已就地反映新行为，没有遗留旧描述；
- 构建测试与一致性验证通过；
- 提交信息包含 CR 编号；
- CR 临时文件已删除；
- 影响 PRD 时已更新 PRD。

旧流程遗留的 CR 文件，可以说 `合并历史 CR 文档`，AI 会把已关闭的合并进正式文档后删除；进行中或状态不明的不会动。

## 8. 团队协作

### 8.1 认领单元

单元生成之后，每位成员在自己的会话里说：

```text
使用 AI-DLC，列出可认领的开发单元
使用 AI-DLC，我是 alice，认领 order 模块的 export-api 单元，分支 feat/order-export-api，并准备独立 worktree
```

认领只是协作记录，不是锁。两人选了同一个单元时，协商后让 AI 用替换方式更新记录。需要防重复认领时，说“按模块认领 order 模块”，引擎会带心跳和过期时间。

### 8.2 多人、多工具混用

不同成员可以用不同工具（A 用 Kiro IDE、B 用 Claude Code），注意：

- 每个流程（或拆分后的每个模块流程）同一时刻只有一个会话负责上报阶段，其他人只交付产物；
- 流程状态和证据随 Git 同步，先拉取再说“继续”；
- 接手别人的工作时说 `使用 AI-DLC，继续上次的工作`，以 AI 展示的下一步提示为准，不依赖上一位的聊天记录。

### 8.3 在 Multica 中编排

依赖 `aidlc-multica-orchestration` Skill。在父议题中对协调者说：

```text
按 AI-DLC 当前阶段拆解任务，先给我看任务矩阵，确认后再建子议题
```

- 只有父议题的协调者推进 AI-DLC 状态；子议题只交付文档、代码、测试或审查结论。
- 协调者按阶段的执行方式决定落地形态：可并行的按单元建子议题；需要多角色同场的建一个协作议题；审查类建审查子议题（审查者不能是作者）；顺序类建串行议题链；需要你回答或审批的阶段由协调者在对话里直接问你，不外派。
- 跨模块集成排在所有模块完成之后的独立批次。

## 9. 中断与恢复

| 情况 | 提示词 |
| --- | --- |
| 关闭会话、换工具、换人 | `使用 AI-DLC，继续上次的工作` |
| 想要可复制的交接说明 | `生成 AI-DLC 交接` |
| 主动暂停整个流程 | `暂停 AI-DLC`；恢复：`恢复 AI-DLC` |
| 只暂停某个模块（仅拆分后） | `暂停 AI-DLC 的 order 模块`；恢复：`恢复 AI-DLC 的 order 模块` |
| 上下文太长被压缩 | `使用 AI-DLC，按流程状态恢复上下文`（以引擎状态为准，不依赖记忆） |
| 跨天继续 | 直接 `继续`；证据 24 小时过期，上游过期不算失败，本阶段的会自动重新生成 |
| Kiro 提示“流程仍在运行” | 这是 Stop Hook 的提醒：继续做，或明确说 `暂停 AI-DLC` |

## 10. 检查没通过时怎么说

| AI 报告的问题 | 含义 | 你可以这样说 |
| --- | --- | --- |
| 证据缺失 / 不匹配 / 判为伪造 | 证据没生成、已过期，或产物在之后被改过 | `重新上报当前阶段，让引擎重新生成证据，不要手写证据` |
| `REQ-xxx: BROKEN@<层>` | 该需求在某一层（故事、设计、用例、代码、测试）丢了 | `在 <层> 补上 REQ-xxx 的覆盖，再上报` |
| `MIGRATION_REQUIRED` | 旧项目缺需求编号或类型标签 | `列出缺失清单，按迁移计划补齐` |
| RED 没失败 / GREEN 没覆盖全部用例 | 测试没有真正针对新行为，或测试命令漏了 | `检查测试是否真的覆盖 UC-D-xxx，修正测试命令后重跑` |
| 特征化用例被拒（代码与基线不一致） | 在锁定现状前已经改了代码 | `先还原 <文件> 的改动，跑完特征化用例再改` |
| “本单元未交付任何源码变更” | 本单元相对基线没有改动文件 | 确认该单元是否本就不交付代码；契约类单元说 `把这个单元声明为豁免并给出替代验证` |
| 模块被跨模块依赖阻塞 | 提供方没完成或契约未验证 | `现在在等哪个模块？先推进它` |
| 已有流程，无法开新工作 | 当前项目还有未归档的流程 | `继续当前工作`，或 `暂停并归档当前工作` 后再开工 |

## 11. 常见误区

- **不带“使用 AI-DLC”直接让 AI 写代码**：Skill 不会加载，变成没有门禁的普通对话。
- **把 AI 生成的文档当作完成**：以阶段上报通过为准。
- **替 AI 说“我同意你自己选”**：单/多模块、优先级、批准这类决策，要给出明确答案；AI 不应接受“你看着办”。
- **为通过检查删测试、关检查、把未验证标成不适用**：协议禁止，也会让后续 CR 无法评估影响。
- **CR 只写一份变更说明**：必须就地更新正式文档，CR 文件只是临时摘要。
- **多个会话同时推进同一个流程**：会造成状态冲突，一个流程只能有一个协调会话。
- **以为 merge plan 会自动合并**：它只给建议，merge 和 push 由人执行。

## 附录 B：提示词与 AI 执行的命令

用于核对 AI 是否做了正确的事。完整参数见 `docs/loeyae-aidlc-cli-guide.md`。

| 你说 | AI 应执行 |
| --- | --- |
| 开始新工作 | `orchestrate next --scope <scope> --work "<描述>"`（需要 PRD 时加 `--with-prd`） |
| 继续 | `orchestrate next`，并展示 `handoff_prompt` |
| 回答单/多模块 | `orchestrate report --stage workspace-detection --result completed --instruction-ack workspace-detection --user-input <single-module\|multi-module>` |
| 批准 | `orchestrate report --stage <slug> --result approved --user-input Approve` |
| 查看进度 | `orchestrate next --status` 或 `runtime summary` |
| 认领单元 | `unit select --module <id> --unit <id> --member <名字> --branch <分支>`，需要时 `worktree prepare` |
| 拆分 / 推进模块 | `orchestrate split --from <workflow-id> [--dry-run]` / `orchestrate next --module <id>` |
| 查看 / 推进基线 | `orchestrate baseline` / `orchestrate baseline --advance <commit> --expect <当前基线> --user-input Approve --reason "<原因>"` |
| 补登 / 接管基线 | `orchestrate baseline --set <commit> …` / `orchestrate baseline --adopt <commit> --module <id> --approval-ref … …` |
| 图用 SVG | `orchestrate diagram-format --set svg --user-input "<你的原话>"` |
| 暂停 / 恢复 | `orchestrate park [--module <id>]` / `orchestrate next --resume`（模块：`next --module <id> --resume`） |
| 合并准备 | `worktree merge-plan …`（只输出建议，不执行 merge） |
| 归档 | `orchestrate archive --reason "<原因>"`（运行中的流程先 `park`） |

两条硬性检查：

- 带 `--user-input Approve` 的命令，必须发生在你明确说了批准之后；
- AI 不应手写 `.aidlc/evidence/` 下的任何文件。
