### 2.3 关键源码发现

1. UI 夹具明确 `interaction_mode: explanatory`，HTML 是静态发布按钮和结果文字，未提供完整服务和真实交互。因此不能作为 P1 的 executable UI 直接通过。
2. UI fixture 将 ready/draft 及失败反馈作为语义来源，但未冻结可重复渲染的视觉资源、容差和必需视口。不得在最终实现完成后用实现截图反向补设计基准。
3. 无 UI 单元夹具的 pythonTests 中包含 `assert True`；observer 依据源码标记存在性构造观察。这可用于引擎范围门禁回归，不能证明订单行数、顺序、空集和超时行为。
4. 夹具中的“Fixture owner confirmed”“approved”等为测试数据，不能成为 AutonomyPolicy/ExecutionGrant 的真实 AuthorityRef。
5. 本机 Python 入口指向 WindowsApps 别名，未执行解释器能力验证。若 P1 复用 Python 版本，需要独立验证；不能把命令可发现当解释器可用。

## 3. P0-02：两个批次的范围与单元

以下批次标签仅用于桌面演练，不是已签发的 workflow/unit/claim。

### 3.1 desk-ui-publish

目标：在 ready 状态执行发布并显示真实结果；draft 状态保持禁用，失败显示可恢复反馈。后端仍须拒绝不合法状态，不能只有前端禁用。

| 角色 | 单元/能力 | 修改责任与完成条件 |
| --- | --- | --- |
| implement | publish-api | 发布状态检查、成功/失败结果和接口断言；唯一后端写入责任 |
| implement | publish-page | 页面布局、状态、点击、错误反馈与视觉还原；唯一 PAGE-001 最终实现责任 |
| consume | 发布接口契约 | 类型、状态、结果和错误定义；独立于后端是否运行 |
| verify | 最终集成候选 | 两单元相同版本组合、真实接口联调、UI/业务矩阵 |

publish-api 与 publish-page 若实际属于不同服务，仍保持分开 unit；批次负责整体完成。试点的具体工作目录、模块根和真实 UnitRef 在接收实际试点时生成，当前不能伪造为已存在路径。

必要依赖：

| 依赖 | 消费检查点 | 准备条件 | 桌面推演结论 |
| --- | --- | --- | --- |
| API 契约 → publish-page | 页面实现/局部检查 | 真实验证的契约基线 | 不等待整个后端服务完成 |
| publish-api → 实际点击发布 | 集成验证 | 对应版本 runtime_ready 与实际断言 | 受控替身只能支持局部检查 |
| UI 基准 → 页面验收 | 实现验收 | 预先冻结设计、数据、视口和资源 | 当前夹具不足，列入试点准备阻塞 |

### 3.2 desk-order-pagination

目标：对上游完整有序列表按每页 50 导出，不丢失、不重排，空集得到空结果，上游超时按原语义传播。

| 角色 | 单元/能力 | 修改责任与完成条件 |
| --- | --- | --- |
| implement | order-export | 导出入口与分页行为作为内聚增量；局部数据准备不拆成额外正式 unit |
| consume | fetch-orders-contract | 完整有序列表和超时定义；测试可用可控输入，真实集成按环境适用性另验 |
| verify | 导出结果与错误通道 | 实际运行函数/入口的内容断言及必要集成，不依赖源码中出现某个标记 |

P1 可保留 Python 以复用既有样本，也可将内部试点行为实现为 Node；选择及理由需在真实接收时记录。语言选择不改变分页规则，不能把迁移实际业务项目伪装为内部试点细化。当前演练不引入新的语言迁移授权。

### 3.3 范围约束

- UI 样本不顺带实现整个 BOM、SKU、本地化或 OMS 业务；这些是原 fixture 的其他输入，不属于本次选定发布场景。
- 无 UI 样本不新增页面、持久化数据或不必要部署。
- 无需求的鉴权模型、重复发布幂等或更多业务状态不作为未经确认的新功能；若真实试点存在这些要求，接收时纳入来源和验证。
- 每个样本使用独立 workflow。P1 不在同一活动状态上先改成 UI、再改成无 UI 以制造两次完成。

## 4. P0-03：交接与兜底策略定稿

采用总体方案 H1–H6。人类决定本批次目标、业务/UI 约束和验收；Agent 推导单元与依赖、辅助完成设计，在准入后负责连续实施和批次整体验证。下一批次设计可以并行准备，不能改动当前冻结基线。

以下为试点接收时的策略建议，尚未带真实 AuthorityRef，因此不直接生效：

| 决策项 | 兜底规则 | 质量与范围限制 |
| --- | --- | --- |
| 文件和组件路径 | 先沿用实际项目规范；无规范则选最小内聚结构，并在计划中登记 | 不越 write_scope、不改服务所有权 |
| 未指定的失败文案 | 优先项目统一错误文案；没有则用明确、可重试的反馈 | 不吞掉错误，不把失败显示为成功；保留既定状态语义 |
| UI 细节 | 已冻结值严格还原；明确允许设计的区域由 Agent 先形成基准再实施 | 不省略按钮/状态，不在看到候选偏差后修改基准 |
| 每页数量 | 固定 50，来源已明确 | 不可用“默认值”改为 20/100 |
| 空集与超时 | 保留空结果与超时传播语义 | 不用空结果吞掉超时，不加无需求重试改变行为 |
| 测试选择 | 真实结果断言覆盖固定分母，复用有效既有结果 | 不以 assert True、函数名或源码标记替代业务观察 |
| 技术故障 | 有限诊断/重试，记录环境问题 | 不绕过 grant/沙箱，不删除必要检查 |

委托决策的 human_review=pending 不阻塞工程完成；实现、验证和记录缺失仍阻塞。核心规则冲突或推翻明确决定不适用兜底。当前没有要求人类逐项决定普通文件路径的新规则。

## 5. P0-04：数据契约定稿与落点

[契约 v1.0](aidlc-autonomous-contracts-v1.md)已具体确定字段、类型、必需性、版本、摘要、enum、来源、失效和拒绝语义。主要决定如下：

| 设计决定 | 结论 |
| --- | --- |
| 业务真相 | canonical Markdown/manifest 单写；batch/policy/decision 用唯一结构化 record；投影不可独立编辑 |
| 同文档局部变化 | 新来源可用 json-record-v1，避免追加 decision 污染 policy 摘要；旧 sensor 不自动享受优化 |
| 批次身份 | batch_id/scope_revision 固定分母，effective_revision 表示合法细化，不能删除必要验收 |
| 单元/依赖 | 写入范围与证据输入分离；能力依赖与失效传播分离；跨模块使用完整引用 |
| 授权 | 真实人类来源 + Core 受控签发 + 当前 grant 校验；同本机操作信任边界，不夸大成独立身份认证 |
| P1 恢复边界 | successor_policy=disabled；单会话授权不静默升级为跨会话接管 |
| 候选 | 最终集成候选与期间 dirty 源码观察区分，提交后依原算法复核 |
| 实际验证 | format valid 不等于 business verified；UI 实际交互、截图和视觉观察单独绑定候选 |
| report 幂等 | 原 journal 可借鉴，但 report 泛化属于 P2 新工作，不宣称当前已有 |
| 旧 workflow | 未采用标记保持旧行为，显式接收与迁移才启用新契约 |

本文“定稿”表示技术设计基线已经具体化，不代表给当前活动 workflow 追加审批，也不声称代码已支持这些字段。

| ui-draft | 既有 region：draft 禁用，API 拒绝非法发布 | 页面按钮禁用；直接调用接口也拒绝 |
| ui-result | action 指向 result，异步结果可见 | 完成后实际结果入口可见，状态与后端一致 |
| ui-failure | failure feedback/retry | 失败显示可恢复反馈，不显示成功；重复操作符合真实设计 |
| ui-structure | PAGE-001/publish/action 归属明确 | 页面、区域、按钮、结果区域存在且可操作 |
| ui-visual | 总体方案要求运行时还原 | 冻结设计资源、必要视口/状态后获取实际候选截图并审查 |
| ui-integration | batch 负责整体完成 | 相同最终候选的前后端版本完成实际联调 |

ready/draft 是真实夹具语义；完整网络失败、加载态、视觉容差及视口矩阵仍需试点设计接收后冻结。它们当前是明确准备项，不能把表格存在标为 UI 完整设计已经通过。
