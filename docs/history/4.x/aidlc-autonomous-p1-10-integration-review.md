### 4.2 具体低效位置

1. **授权后排队**。最初四组双项目实际串行运行。发布页 r7/r9/r10/r11 授权后分别等待约 8.3/11.4/17.1/24.9 分钟才开始，合计约 61.6 项目分钟预算消耗在启动前；相邻订单结束与发布页开始只差 0–8 秒，证实了串行衔接。r8/r12 与 r9/r13 已改为近乎同时首次派发，此项已有真实并行证据，但不证明业务已成功。

3. **发布页的浏览器验证确有成本，且被反复触发**。publish-r13 最终归档 RED/GREEN 为 126.1/81.2 秒；实际提出 RED 5 次、GREEN 4 次工具请求，两类请求区间约 785.7 秒，含失败，不能只算正常测试。该轮有 90 个通过的 Native 像素观察覆盖十个组合。单次 browser-case 经新的 Node/TSX 子进程调用，每次 observeBrowser 又新建 Chrome/profile。重复次数本身不能证明冗余，必须补源/候选/计划指纹后判定。
4. **能力检查过粗**。当前每次真正 admission run 都要求新的 adapter.observe，执行三个实际模型 turn，必要时启动浏览器。业务证据的重验与宿主能力的重新探测未分离；仍有效、同 HostRef/配置/原授权约束的能力证据不能被选择性复用。复用必须由 Core 验证已有签名来源、原 observed_at/valid_until，不能给旧结果重新计时。

### 4.3 优化原则与性能目标

性能目标是待验证的准入要求，不是本次已经达成的结果；保留最终业务完整性、像素阈值及原授权上限。

- 分开计量 human/design waiting、grant-to-start、host control、model/RPC、producer、browser/visual、cleanup 和 evidence publish；父子区间按嵌套关系计算，不重复加总。记录安全的命令族、步骤、输入/候选摘要、refresh reason 和语义进度；不记录私有 binding/generation/key。
- 按实际依赖复用证据，当前 Core 的授权/撤销/领取/期限检查每次仍有效。Core 可提供可信进程内 API 适配以减少 Node/TSX 启动，但必须与 CLI 一致，并校验固定 Core 包摘要；不得缓存“已授权”结论或放宽写权限。
- 结构化阶段输入包、工具目录与 write_contract 降低探索式 read/help/错误参数调用；不可变规则按摘要消费，过期或变化则刷新。宿主预算约束单 turn 内重复成功动作，不只计失败。
- 动态工具契约应使用宿主实际支持的类型化动作、枚举和条件必填字段，减少当前通用 action 字符串加任意 args 的猜测成本；契约来自 Core 可消费元数据，仍执行 Core 最终检查。按风险和已批准 scope 传递最小必要阶段输入与当前缺口，已确定不适用的阶段不反复生成说明；必要的 NA 证据仍绑定当前 schema/workflow/scope，不跳门禁。
- UI 优先减少冷启动：受控浏览器进程可复用，每个用例独立 page/context、存储与服务状态；保持两尺寸十组合、真实交互/网络/像素检查。跨候选结果复用必须有明确 Core 受控依据，不能把旧截图改名。

## 7. 再次试跑准入与停止条件

再次试跑必须同时满足：IR-01～04 局部复现转为期望行为、IR-05/06 完成故障注入/生产入口集成、IR-07 的同 attempt 返修范围经设计确认并验证、所有动作路径矩阵有证据、L2 与分发在最终冻结来源通过、效率记录及目标达标、原审批/质量分母/原 RED 保留、历史未知状态未被改造、用户确认优化结果并在真实终端签发精确 H5。旧 readiness 仅证明当时准备检查，不能替代此 Go。

停止条件：

1. 同一输入和同一阻断不得靠等价重试推进；在原许可次数以内仍实行更严格的根因停止线。同一根因族三次修复/验证失败必须进入整体方案复审，不进行第四次猜测修补。
2. L0/L1 失败先修受影响路径，不启动 L2 或真实模型；已通过且来源/依赖无变化的检查复用。最终源码未完成审查不得开始“最后一轮全套”。
3. 出现未知操作、进程/关闭未对账、权限或冻结范围变化、RED 输入漂移、真实门禁失败，保持正式拒绝和现场，不自动恢复、不延长授权、不降质量。
4. 单 turn 的重复动作或语义停滞由宿主步骤预算处理，需先确认无仍在合法期限内执行的已知动作。超过性能预算不能只扩大 timeout；输出已完成检查点、未决操作和耗时归因，进入工程优化。
5. L3 每项目最多一个授权 attempt，允许其中正常的预期 RED 和预算内代码修复，不能把每次测试失败都变成新试跑。attempt 最终失败、出现新框架缺陷、失联或性能不达标时停止该次验收，不自动开新工作流或请求新 H5。若将来选择并行终验，需预先定义组内框架故障的受控取消策略，不能为收集更多错误任由另一份预算耗尽。

质量、可靠性、效率分别报告：Core 的历史 business_verified 不因效率结果被重写；同样，效率达标不能替代完整矩阵、Native 与候选一致性。P1-10/P1 当前仍未验收，P2 自动恢复与多宿主能力均未新增。

上述“不恢复”针对未知/已结束 attempt；同一仍活跃 attempt 内，只有获 Core 正式 same-attempt repair directive 的有限返修才属于正常实施。不能把期望 RED 或可修复代码缺陷都算作新一轮试跑，也不能用“Agent 可修复”作为绕过门禁的理由。
