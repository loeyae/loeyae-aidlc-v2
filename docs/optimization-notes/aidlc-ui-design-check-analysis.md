## 一、背景问题

现有 UI 设计流程采用：

生成一页/一批
→ 独立审查
→ 修正
→ 再次复验
→ 下一页/下一批

实际使用中出现以下问题：

1. 每页或每批都启动审查代理，重复读取需求、设计系统和 Figma 节点。
2. 独立审查结果写入和循环停止条件存在时序差，已通过的批次可能再次启动冗余复审。
3. 普通 Figma 写入、临时截图清理等低风险事项也会暂停等待用户确认。
4. 用户回复进度问题后，生成任务可能停顿，不能持续执行。
5. 全量生成锁定了旧需求 revision，但最终校验没有先对比当前最新需求，导致新增 AC 未及时同步。
6. 每页确认造成大量等待、上下文恢复和重复检查，降低整体效率。
7. 深度逐页审查并未替代最终全局一致性检查，反而形成重复验收。

M02 实践表明：

- 第一批采用独立审查循环，经历多轮修正才结束；
- 后续批次采用“直接生成 + 自动读回”，多数一次完成；
- 全量完成后集中验证，再针对变化的 AC 只修正受影响页面，整体成本更低；
- 但不能完全取消技术读回，也不能省略最终需求版本新鲜度检查。

## 二、调整范围

只调整以下阶段：

- HTML UI Mock 生成；
- Figma UI 生成；
- Figma 既有页面增量更新；
- UI 设计的自动验证和交付登记。

不得改变：

- 正式 PRD 的权威性；
- requirements 和 user stories 的需求确认流程；
- 涉及安全、数据删除、生产环境和不可逆操作的确认机制；
- 代码实现、发布和部署阶段已有的必要质量门禁。

## 三、目标流程

将 UI 设计阶段调整为以下标准流程。

### 阶段 1：输入和版本锁定

生成前记录：

- 正式 PRD 路径、版本、Git blob 或文件 SHA-256；
- 用户故事路径、Git commit、blob、STORY 数和 AC 数；
- 页面清单及编号；
- 基座源码 commit；
- 只读参考 Figma fileKey/nodeId；
- 目标 Figma fileKey/Page；
- 设计系统、Variables、Components 和页面壳层来源。

需求优先级固定为：

当前用户明确指令
> 正式 PRD
> 已确认用户故事/AC
> 已批准设计来源
> 基座源码现状
> 通用 UX 规范

若当前任务已明确指定用户故事为主要操作输入，应保持该约定；正式 PRD只能补充故事未覆盖的空白，不能推翻已有故事结论。

### 阶段 2：设计系统和代表页定标

全量生成前：

1. 建立或复用 Variables、Components、Variants、Effects、Auto Layout 规范；
2. 选择一张信息量最丰富的代表页；
3. 完成代表页的视觉、密度、标注、状态条件表和交互清单；
4. 对代表页只执行一次定标确认。

用户已明确批准参考设计或已有稳定设计系统时，可以跳过人工代表页确认，直接自动定标，但必须记录使用的参考节点。

代表页确认后，后续页面不得逐页暂停确认。

### 阶段 3：全量连续生成

按页面依赖顺序连续生成全部页面：

- 不设置逐页人工确认门禁；
- 不设置每批“独立审查→修正→复验”的 repeat loop；
- 一个 Figma 文件同一时间只能有一个写者；
- 可按批次写入，但批次只用于控制写入规模和错误恢复，不是人工评审门禁；
- 每次回复、汇报或状态更新后，后台生成任务继续运行；
- 普通写入、布局调整、API 重试和自验证不请求用户确认。

只有以下情况允许暂停：

1. 存在会改变业务结论的真实需求歧义；
2. 多个同级权威需求源冲突；
3. 需要执行删除、覆盖原稿、强推、生产写入等高风险操作；
4. 连续两次等价工具失败且替代方案也不可用。

不影响其他页面的需求缺口不得阻塞全量生成。应在“开发说明 · 不渲染”中标记阻断缺口，并继续生成其余内容，禁止臆造规则。

### 阶段 4：每批轻量技术读回

不能完全取消批次检查，但应限定为自动技术检查，不做深度语义审查。

每批写入后只检查：

- 节点是否真实生成；
- 编号和顶层 Frame 是否唯一；
- 目标 nodeId 是否稳定；
- 是否误改只读来源或旧版本；
- 是否发生 API 原子回滚；
- 是否有顶层碰撞、明显越界、缺失字体或文字截断；
- Variables、Components、Auto Layout 是否存在真实引用；
- 临时截图和报告是否生成。

技术读回由当前写者自动完成，不启动独立 reviewer，不等待用户确认。

Figma 写入失败时：

1. 根据错误修改调用参数；
2. 将脚本拆成更小批次；
3. 先建立 Auto Layout 父级，再设置 FILL；
4. 自动重试；
5. 同一等价方案连续失败两次后切换实现方式，不得无限重试。

非必要临时文件不清理，避免因删除确认阻塞主任务。

### 阶段 5：最终需求新鲜度检查

全量生成结束、最终验收开始前，必须重新获取最新需求版本。

对比：

生成时 commit/blob
vs
当前 origin/main commit/blob

至少检查：

- 正式 PRD；
- requirements；
- user stories；
- STORY/AC 数量及实际正文差异；
- 页面清单；
- 已确认设计决定。

如果没有变化，进入最终验收。

如果发生变化：

1. 找出新增、删除或改写的 STORY/AC；
2. 建立 STORY/AC → 页面编号影响矩阵；
3. 只同步受影响页面；
4. 不重新生成未受影响页面；
5. 更新需求基线记录；
6. 完成后再进入最终验收。

禁止只比较文件时间或 AC 数量。必须读取实际 diff，确认业务语义是否变化。

### 阶段 6：一次全量集中验收

同一任务默认只执行一次全量语义和视觉验收，检查：

- 页面数量、编号、顺序和唯一性；
- 已取消页面是否确实不存在；
- 用户故事和 AC 是否完整追溯；
- 局部改动是否正确标注新增、变更和移除；
- 多状态和表单联动是否完整；
- Modal、Drawer、Toast、确认操作和返回路径是否闭环；
- 确认类操作的信息量是否足够；
- Loading、Empty、Error、Disabled、Focus、Selected 是否覆盖；
- Variables、Components、Variants、Auto Layout 是否实际使用；
- 缺失字体、文字截断、可见越界、裁切和碰撞；
- 只读来源、旧版本和无关页面是否保持不变；
- HTML 的 data-change/data-us/data-ac/data-src 是否有效；
- Figma 节点登记、截图和交互说明是否齐全。

最终验收不得递归触发另一轮同级全量审查。

### 阶段 7：定向修正

最终验收发现问题后：

- 按问题清单只修受影响页面；
- 保留原 nodeId，禁止删除重建已登记 Frame；
- 修复后只做定向复验；
- 除非发现共享组件、公共契约或全局设计系统问题，否则不得再次执行全量验收。

完成条件为：

- 无未解决 HIGH/MEDIUM 问题；
- LOW 问题已修复或明确记录；
- 未确认需求缺口已标注但未臆造；
- 当前需求 revision 与设计登记一致。

## 四、HTML 和 Figma 的职责边界

统一规定：

- 业务规则、校验、计算和边界：看正式 PRD及用户故事/AC；
- 最终视觉、布局、组件和状态：看 Figma；
- HTML 单页 Mock：作为机器可读开发差异地图；
- HTML 中 `data-change/data-us/data-ac/data-src` 用于定位改动和源码；
- 阶段1汇总骨架不得被误认为最终 UI；
- 没有单页 HTML 的页面，不得从阶段1骨架反推最终实现；
- 不要求为了形式统一，把所有 Figma 页面再复制成完整 HTML；
- 只有研发确实需要源码级定位时，才补缺失页面的 data-src 差异地图。

## 五、自动执行和用户确认规则

UI 设计阶段默认自动执行：

- 读取需求；
- 创建或修改 Figma；
- 普通布局修正；
- 工具重试；
- 截图；
- metadata 读回；
- 结构检查；
- 状态检查；
- 生成登记表和报告。

以下情况才请求用户确认：

- 覆盖或删除现有正式 Figma 版本；
- 改变正式需求结论；
- 多个正式来源无法判定优先级；
- 修改生产数据；
- 执行不可逆 Git 操作；
- 页面拆分、合并或编号变化。

进度汇报不得暂停工作流。发送普通 info 消息后必须继续当前步骤。

## 七、验证要求

修改后执行最小充分验证：

1. 静态检查 workflow/schema/steering/Skill 语法；
2. 验证流程中不再存在逐页人工确认门禁；
3. 验证不存在每批独立 reviewer repeat loop；
4. 验证批次轻量读回仍保留；
5. 验证最终需求新鲜度检查存在；
6. 验证同一任务全量审查最多一次；
7. 验证修复后走定向复验；
8. 验证高风险操作仍需要确认；
9. 使用一个不写生产数据的模拟模块做 dry-run：
   - 输入版本锁定；
   - 代表页定标；
   - 连续生成计划；
   - 模拟需求 revision 变化；
   - 输出受影响页面矩阵；
   - 一次全量验收；
   - 定向修正；
10. 运行 `git diff --check`。

不要为了验证修改而执行完整生产 Figma 生成；使用 dry-run 或测试 fixture 即可。

## 九、关键验收标准

只有同时满足以下条件才可报告完成：

- UI 生成阶段不再逐页等待用户确认；
- 批次不再使用独立审查循环；
- 每批仍有自动技术读回；
- 最终验收前会重新检查最新需求 revision；
- 需求变化只增量同步受影响页面；
- 同一任务全量验收最多一次；
- 修复后只执行定向复验；
- 高风险操作仍需确认；
- 进度回复不会停止后台生成；
- 所有调整通用化，不包含 M02、固定节点或临时路径硬编码；
- 所有验证均有真实结果，未执行项明确标为未验证。
