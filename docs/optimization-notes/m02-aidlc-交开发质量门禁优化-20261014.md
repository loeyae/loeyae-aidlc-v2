# M02 商品域 AI-DLC 交开发质量门禁优化要求

> 日期：2026-10-14  
> 适用范围：需求分析 → 用户故事 → UI Mock → 交开发的 AI-DLC 工作流  
> 目标：把可提前发现的语义、追溯、技术可行性和跨域问题前移，在 Mock 与交开发前阻断，而不是由开发复核后再回流修订。

### 1.2 问题不是同一类原因

| 类别 | M02 中的表现 | 应由哪个门禁前移 |
|---|---|---|
| 语义实现错误 | 库存紧张公式与 AC 不等价；状态 / 失败反馈遗漏 | 规则语义门禁 |
| 故事内部冲突 | 草稿不可勾选与“勾选含草稿批量失败”并存；HKMS 必填口径冲突 | 用户故事一致性门禁 |
| 机器可读交付不足 | 新增页面只在根容器标 `data-change`，开发无法按区域追溯故事和 AC | Mock 追溯门禁 |
| 静态交付缺陷 | 正式复核前仍有 HTML 校验失败 | 静态校验 fail-closed 门禁 |

| 技术可行性晚发现 | 扩展字段定义仅有单语 `fieldName`，无法承载 C 端双语标签与字段值需求 | 字段技术可行性门禁 |
| 外部事实后续变化 | BOM 独立接口、全量覆盖、HKMS 树同步、库存口径等在后续才明确 | 外部依赖冻结与变更门禁 |

## 二、总体原则

1. **文档存在不等于语义正确。** REQ、故事、Mock 都有内容，不能证明公式、状态边界、默认值、异常路径一致。
2. **静态校验通过不等于可交开发。** HTML 标签、ID、交互表的结构检查必须配合规则语义检查。
3. **技术可行性必须早于交付设计。** 字段存储、双语、查询、导入导出、C 端展示、索引能力均应先核实真实基座实现。
4. **变更必须按影响面回写。** 任何字段、默认值、状态、接口语义改变，都必须检查 REQ、故事、页面规格、Mock、交接清单五类产物。
5. **交开发状态采用 fail-closed。** 任一阻断项未闭合，产物状态只能是“待交付”，不得标记为“可交开发”。

## 三、门禁 0：需求来源与外部依赖冻结

### 触发时机

进入用户故事之前，以及外部系统 / 业务方给出新结论之后。

### 必须产物

`source-and-dependency-register.md`，每条外部输入至少包含：

| 字段 | 要求 |
|---|---|
| 主题 | 例如 BOM 关系、HKMS 类目树、库存口径 |
| 当前结论 | 只写已经确认的结论 |
| 来源 | 正式 PRD、当前用户决定、外部接口确认或其他明确来源 |
| 影响范围 | REQ / Story / Mock / 接口 / C 端 / 跨域 |
| 状态 | 已冻结 / 待确认 / 已变更 |
| 变更动作 | 需回写的文件清单 |

### 阻断规则

- 外部接口的粒度、全量 / 增量语义、删除表达、默认值或字段含义不清楚时，不得在故事或 Mock 中把推测写成结论。
- 外部事实变更后，未完成影响面清单前，不得继续标记“需求已定稿”。

## 四、门禁 1：字段技术可行性门禁

### 触发时机

设计字段存储方案之前；新增字段、双语、筛选、导入导出、C 端展示均触发。

### 必须产物

`field-capability-matrix.md`。每个字段必须完整回答：

| 维度 | 必填内容 |
|---|---|
| 权威来源与业务含义 | PRD / 用户决定 / 外部事实的定位 |
| 粒度 | SPU、SKU、店品、门店、订单或其他 |
| 入站来源 | OMS 推送、运营维护、系统生成或默认值 |
| 存储方案 | 实体列、关联表、JSON、扩展字段、描述属性 |
| 双语能力 | 字段名、字段值、枚举文案分别由谁提供 |
| 查询能力 | 列表、筛选、排序、索引 / ES 能力 |
| 编辑能力 | 编辑位置、权限、校验、默认值 |
| 导入导出能力 | 是否可导出、是否可导入、字段映射 |
| C 端能力 | 是否展示、标签名来源、可见性开关、排序 |
| 下游依赖 | 搜索、交易、店仓、营销、OMS 等 |

### 必须执行的代码核实

AI-DLC 负责人必须读取并记录：

- 实体 / 表结构；
- DTO、VO、入站转换；
- 查询和筛选实现；
- 导入导出实现；
- 国际化 / 字段定义实现；
- 真实调用方。

### 阻断规则

以下任一项未核实，不得决定字段落点：

- 扩展字段是否支持双语字段名和双语值；
- 固定列是否已被下游消费；
- JSON / 扩展字段是否满足筛选、排序、性能要求；
- C 端展示字段名由运营、静态词典还是接口提供；
- 同名字段是否在商品、店品、订单层有不同含义。

## 五、门禁 2：用户故事一致性与可达性门禁

### 触发时机

用户故事完成后、UI Mock 开始前。

### 必须产物

`rule-state-reachability-matrix.md`。对每一条高风险规则列出：

| 维度 | 内容 |
|---|---|
| 规则 ID | REQ / AC / 决策编号 |
| 状态前提 | 草稿、就绪、禁售、已发布、未发布等 |
| UI 可见性 | 展示 / 隐藏 / disabled |
| 可执行动作 | 用户是否可以触发 |
| 前端校验 | 拦截条件和反馈 |
| 接口防御 | 即使前端不可达是否仍校验 |
| 成功反馈 | 页面、Toast、列表刷新、任务回执等 |
| 失败反馈 | 字段错误、Toast、弹窗保持、任务失败明细等 |

### 必查问题

- 某操作在 UI 上被禁用后，故事是否仍把它当成可达的异常场景？
- 两个 AC 是否对同一个字段给出不同的必填、默认、展示或编辑结论？
- “选择器过滤”和“添加后拒绝”是否分别承担前端体验与接口防御，而不是二选一混写？
- 某默认值是否会把所有新数据导入草稿或不可用状态？
- 公式、阈值、比例、日期口径能否逐字追溯到 AC？

### 阻断规则

故事内存在未裁决冲突、不可达场景或未定义失败反馈时，不进入 Mock 阶段。

## 六、门禁 3：UI Mock 语义与追溯门禁

### 触发时机

每页 Mock 完成后、交开发前。

### 强制检查项

1. **状态条件表**：同一区域在两种及以上状态下有差异，必须有条件表；表内列出组件显示、隐藏、disabled、替换和完整按钮组合。
2. **操作闭环**：每个按钮必须说明去向、成功反馈、失败反馈和结果查看位置。
3. **公式与口径**：所有金额、库存、阈值、默认值、枚举必须能定位到 REQ / AC / 已确认决定。
4. **局部改动还原**：未标注区域必须基于实际基座结构；不允许为了展示需求重排基座页面。
5. **机器可读追溯**：
   - 每个新增 / 变更 / 移除的功能区域必须有 `data-change`、`data-us`；
   - 能定位 AC 时必须有 `data-ac`；
   - 新增页面不得只在整个根容器标一次，至少按表单、筛选、列表、按钮、反馈等功能区域标注；
   - 多故事页面按区域标不同故事，不能只在页面头部罗列故事号。
6. **UI 最小化**：不可选项默认从待选列表排除；不可操作默认不展示控件；不得为未要求的约束额外增加 UI。

### 阻断规则

- HTML 静态校验有 ERROR → 不得标“可交开发”；
- 任一交互入口无目标或无结果反馈 → 不得标“可交开发”；
- 新增页面没有区域级追溯 → 不得标“可交开发”。

---

## 七、门禁 4：变更影响回写门禁

### 触发时机

用户决定、开发技术反馈、外部接口澄清、PRD 修订任一发生时。

### 强制影响面清单

| 产物 | 必查内容 |
|---|---|
| requirements.md | REQ、GWT、字段矩阵、跨域交接点、决策记录 |
| user-stories.md / Epics | Story 正文、AC、Examples、备注、故事副本 |
| page-specs | 页面编号、类型、入口、闭环表、取消 / 基座承接项 |
| 差异清单 | 元素、依据、基座代码定位、已确认决定 |
| HTML Mock | 状态表、布局、交互清单、`data-*` 标注、开发说明 |
| 开发交接清单 | 迁移、接口、默认值、回归测试、待技术确认项 |
| 审计报告 | 历史统计是否失效、当前结论是否需要追加修订节 |

### 阻断规则

变更只改一个产物、没有完成影响面扫描时，不得宣称“已同步”。

---

## 八、门禁 5：交开发门禁

### 交付包必须包含

1. 最终 requirements / 用户故事 / 页面规格 / HTML Mock；
2. 字段能力矩阵、规则可达性矩阵、外部依赖登记；
3. 开发交接清单；
4. 静态校验报告；
5. 当前有效决策清单和已废止决定清单；
6. 已知待确认项及其阻断级别。

### 开发确认范围

开发确认的是：

- 表结构和迁移可行性；
- 基座组件是否可复用；
- 字段双语、查询、导入导出的实现可行性；
- 跨域接口、字段粒度和默认值；
- 回归测试范围。

开发不承担重新解释需求或替代产品侧发现故事冲突的职责。

### 交付状态定义

| 状态 | 条件 |
|---|---|
| 待交付 | 任一门禁未通过，或存在阻断 / 高风险待确认项 |
| 可交开发 | 所有静态检查通过；语义矩阵无未裁决冲突；技术可行性已确认；变更影响面已回写 |
| 开发实施中 | 开发已接收交付包，并对技术实现方案完成确认 |
| 需回流 | 新业务结论、接口事实或技术可行性推翻当前设计时进入；必须重新走门禁 0~4 的受影响部分 |

## 九、建议的自动化与度量

### 9.1 应自动化的检查

- Story / AC 编号唯一性、主故事与 Epic 副本一致性；
- HTML `data-us` / `data-ac` 目标存在性；
- 新增页面与多故事页面的区域级追溯覆盖；
- 交互清单入口与页面 / 抽屉 / 弹窗目标闭环；
- 禁用术语、已废止字段、已废止决定的残留；
- 字段矩阵与 REQ / Story / Mock 的字段名对齐；
- 状态条件表是否覆盖对应 AC 的状态分支。

### 9.2 每次交付应记录的指标

| 指标 | 目的 |
|---|---|
| 交开发前 HTML ERROR 数 | 必须为 0 |
| 交开发前未裁决故事冲突数 | 必须为 0 |
| 高风险规则矩阵覆盖率 | 必须为 100% |
| 新增 / 多故事页面区域级追溯覆盖率 | 必须为 100% |
| 交付后回流问题数 | 按语义错误、同步缺口、外部变化、技术可行性分类 |
| 因外部变化产生的回流占比 | 区分流程质量问题与后续事实变化 |

## 十、实施优先级

| 优先级 | 改造项 | 完成判定 |
|---|---|---|
| P0 | 交开发 fail-closed、HTML ERROR=0、区域级追溯 | 不再出现结构错误或根容器级笼统标注的“可交开发”产物 |
| P0 | 字段能力矩阵 + 基座代码核实 | 所有新增 / 变化字段在写故事前已有存储、双语、查询、导入导出结论 |
| P0 | Story 一致性 / 可达性矩阵 | 状态冲突、不可达异常、默认值副作用在 Mock 前裁决 |
| P1 | 自动化跨文件同步检查 | REQ、Story、page-specs、Mock、交接清单发生变更后可发现遗漏 |
| P1 | 外部依赖登记与变更影响清单 | OMS / 外部接口变更不会只改一份产物 |
| P2 | 交付后回流问题分类统计 | 可量化流程改进是否降低可避免返工 |

## 十一、验收清单

交开发前，AI-DLC 负责人必须能逐项确认：

- [ ] 每个业务字段都在字段能力矩阵中，且已经核实真实基座能力。
- [ ] 每条高风险规则都有状态 / 可达性矩阵。
- [ ] 用户故事没有未裁决的内部冲突。
- [ ] UI Mock 静态校验无 ERROR。
- [ ] 新增 / 多故事页面有区域级 `data-us` / `data-ac` 追溯。
- [ ] 所有可操作元素在交互清单中有去向、成功与失败反馈。
- [ ] 需求变更已完成五类产物的影响面回写。
- [ ] 开发交接清单包含迁移、接口、默认值和回归测试要求。
- [ ] 外部依赖的未确认事实已明确列出，未被写成已确认需求。
- [ ] 满足“可交开发”状态定义后才允许交付开发。
