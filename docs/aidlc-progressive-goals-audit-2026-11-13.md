# AI-DLC 4.27.4：渐进式披露与目标导向审计

审计日期：2026-11-13。审计基线：4.27.4，提交 `b0380a285019a38da92347e8a87ea1d1226ff71f`。以下发现保留审计时的事实；用户随后授权的修复方案、实现与验证结果见文末。

**结论：默认入口和短技能已明显简化，但这种简化尚未贯穿引用链。** 默认 CR 的两条业务参考仍混入全局产物或阶段要求；主要使用指南仍以旧受管流程展开；独立工具的发现入口被一起放进 legacy 帮助。显式受管模式的规则和 Provider 知识加载则仍以依赖集合、版本兼容集合代替当前任务真正需要的内容。

确认六项可优化问题。其中 A01—A04 影响默认路径的规则一致性或能力发现，建议先修；A05—A06 只影响显式采用相应受管能力的任务。没有把旧系统整体复杂、包体积大或签名校验严格本身列为问题，也没有据此推算执行时间和 token 节省。

**审计范围与判据**

盘点 10 个 Harness、21 个 Core 技能、38 份阶段文件和 34 份协议。阅读默认技能及入口，沿 CR、PRD、运行时依赖、测试、续作、完成、CLI、规则加载、Provider 知识等主要路径追踪引用；对关键实现运行实际函数和 CLI 测量。目录盘点不等于每份历史文档逐行审查，也不等于这些文件会同时进入模型上下文。

| 检查层 | 渐进式披露判据 | 目标导向判据 |
|---|---|---|
| 能力发现 | 描述、README 和短帮助说明当前可用能力及下一入口 | 用户能直接找到与目标有关的能力，不必先理解完整流程 |
| 默认执行 | 首次仅暴露目标、约束、必要输入及当前动作 | 已有授权与业务决定沿用；以实际实施和验收推进 |
| 按需参考 | 选择一项能力后，仅展开相关业务规则 | 引用内容不能把局部任务变成补齐全项目产物 |
| 验证与交付 | 展示相关证据和未验证项，按需要展开原始结果 | 完成依据是授权范围和验收条件；记录、提交、部署分别判断 |
| 显式受管扩展 | 仅在主动采用后加载；扩展内部仍按条件和任务展开 | 保留真实权限及证据约束，同时避免重复加载无关操作步骤 |

**已成立的改进**

- [宿主执行协议](../core/knowledge/protocols/host-execution.md)明确目标、实际代码及验证优先；第 68 行还明确旧 stage 中的路由、凭据和 report 不能覆盖默认协议。这是有效防护，因此下文的引用冲突不能等同于“默认模式一定被引擎强制阻塞”。
- 21 个技能中，18 个入口文件不超过 1,412 字节；另外三个是独立的 DOCX、估算、排期能力。文件大小只是入口信息量指标，不代表执行 token 数，也不应为了统一短小而删除这些独立能力的必要约束。
- [work 实现](../core/tools/aidlc-host-work.ts)限制默认 Git 摘要、标明截断、只读显式选择的输入；验收返回 `not_evaluated`，不把上下文视图当完成证明。
- 默认批准、测试、审查、交接、续作技能不要求先补齐阶段记录。纯进度说明不自动使业务测试失效；未通过的实际测试仍须处理。
- 当前完成协议区分实施、验收、提交/合并和 CR 收口；事实归属优先一处维护，有真实消费者的完整副本可由既有工具生成，不以删除历史文件制造“去重”。
- 无 Provider 的项目不因离线知识能力增加探测或确认过程。显式受管的签名、来源完整性和真实权限边界仍有必要。

**A01｜默认 PRD Patch 参考仍混有全量生成及阶段契约——优先修复**

触发路径：默认 CR → [change-request-process.md](../core/knowledge/protocols/change-request-process.md) 第 133、174 行 → [product-prd-generation.md](../core/stages/ideation/product-prd-generation.md) 的 Patch 模式。

同一被引用文件同时规定：

- 第 18 行：独立能力与编排内路径均固定输出到 `docs/aidlc/ideation/prd.md`。
- 第 283—291 行：Patch 只改受影响章节，但无条件要求 minor 版本升级。
- 第 297—309 行：输出前全量自审，每章有来源、全体待确认问题归入固定章节、阻断项为零。
- 第 338—344 行：完成需按当前 directive 提交，由引擎记录阶段状态。

这与当前 [aidlc-prd-synthesis](../core/skills/aidlc-prd-synthesis/SKILL.md) 第 9—17 行“更新已有 PRD、保留未知项、旧契约只在显式采用时读取”不一致。生成流程中另有理解确认及范围确认，但 CR 指向的是 Patch 小节，本次没有证据证明 Patch 必然重走那些确认轮次。

影响：仅修改已有 PRD 的一个已批准规则时，参考文件没有明确限定哪些全量生成要求对局部修改适用。可能额外迁移文档、补齐全局内容或追求阶段完成。默认宿主协议能否被实际模型始终正确用于消解这些冲突，需要冷启动会话验证。

建议：让默认 CR 引用独立的业务 Patch 说明，明确沿用现有路径、项目版本约定和已确认范围，仅检查受影响语义及相关级联影响。全量生成、固定 sensor/report 和受管产物要求留在显式受管参考中。新重大业务决定仍需真实确认，未知项仍须如实披露。

验收场景：项目已有非规范目录下的 PRD，用户已批准一条规则修改，其他章节有不相关待确认项。应原位完成本次修改和相关核对，不为此迁移 PRD、补完整项目章节或重新申请既有业务授权；若本次规则本身缺少关键决定，只等待该决定。

**A02｜局部依赖分析仍继承全系统产物及完成要求——优先修复**

触发路径：默认 CR 实际涉及跨进程调用、共享契约或消费者变化 → [change-request-process.md](../core/knowledge/protocols/change-request-process.md) 第 68—69 行 → [common-runtime-dependency-analysis.md](../core/knowledge/standards/common-runtime-dependency-analysis.md)。

CR 入口已经要求从目标节点展开、不扫描全系统；但引用标准第 42—48 行要求创建或更新三份系统基线文档，第 70 行把“所有可部署单元与外部系统有稳定标识和证据位置”列为完成条件。第 65 行允许局部增量刷新，但没有清楚区分“建立完整系统基线”与“本次 CR 计算影响域”的产物和完成范围。

影响：跨服务变更确实需要验证消费者，但在没有现成目录的项目里，当前标准容易把一个已定位的接口调整扩成补建 `service-catalog.md`、`runtime-dependencies.md`、`external-systems.md` 并盘点无关服务。三份文档分别承载不同事实，不能仅因数量为三就判为重复；问题是它们被无条件绑定到本次任务。

建议：明确两种任务范围。全系统逆向可产出完整基线；局部 CR 只记录真实影响闭包、证据和未知边界，优先更新已有机器契约或业务记录，只有实际消费者需要时才补充系统目录。保留提供方、消费者、数据所有权及相关未知项检查。

验收场景：十个服务的项目修改一个接口字段，已确认影响两个消费者且原先没有三份系统目录。应完成相关提供方及消费者的适配和验证，不要求盘点另外七个服务；发现新消费者时据实际依赖扩大范围。

**A03｜主要使用指南只有默认入口提示，正文仍教旧流程——优先修复**

[README](../README.md) 第 56—57 行将“在 AI 工具中实施项目”和“CLI 指南”作为主要阅读入口。[实施指南](aidlc-ai-tools-implementation-guide.md) 第 1 行虽说明默认走宿主，第 5 行和之后正文却仍以 directive、阶段和最终合并角色为主：第 22 行首个 CLI 示例启动 `orchestrate next`；第 42 行按 state/audit/领取恢复；第 52—54 行强调受控产证和引擎记录。[CLI 指南](loeyae-aidlc-cli-guide.md)同样在顶部提示后，直接从“新 workflow”展开。

这是导航和正文不一致，而非旧命令本身不应存在。用户遵循主要指南的首个完整例子，仍可能进入与 README 默认承诺不同的工作方式。

建议：两份指南先提供完整的默认路径：交代目标 → 读取必要材料 → 持续实施和验证 → 说明结果及真实待办；`work` 仅作可选上下文。旧命令放到明确命名的兼容章节或独立指南，README 链接说明对应范围。对主入口文档沿用已有“默认区/兼容区”校验，不只在文件开头增加免责声明。

验收场景：从 README 进入这两份指南的新用户，完成一个已授权表单修改并续作，不需要创建 workflow、领取阶段或提交受管 report。用户明确要求维护旧流程时，仍能找到完整原契约。

**A04｜短帮助隐藏独立能力，发现层描述仍偏向旧流程——优先修复**

实际运行 CLI 得到：

| 命令 | 退出码 | 输出字节 | 输出行数 | 发现结果 |
|---|---:|---:|---:|---|
| `node bin/cli.js --help` | 0 | 1,025 | 18 | 仅 work、安装、卸载、版本及 legacy 帮助入口 |
| `node bin/cli.js help legacy` | 0 | 14,523 | 140 | 才能看到 export、docx 等独立工具及旧受管命令 |
| `node bin/cli.js work --help` | 0 | 306 | 4 | 有 work 视图参数 |
| `node bin/cli.js help export` | 0 | 1,025 | 18 | 返回根帮助，未提供该能力的分层入口 |

`help export` 不是已承诺的子命令，此处只验证替代发现路径是否存在，不将它的返回单独认定为 API 缺陷。主要矛盾是 [README](../README.md) 第 52 行让用户用 `--help` 发现图表、文档导出等能力，而 [CLI 根帮助](../bin/cli.ts) 第 1259—1276 行没有提供它们的目录，实际条目在第 1382—1383 行的 legacy 帮助中。

此外，Codex、Kiro Crew、CodeBuddy、Qoder、ZCode 的根技能描述仍突出 `Markdown state/audit, unit selection`；部分插件目录及 [安装器生成描述](../bin/cli.ts) 第 651 行也是旧表述。技能正文已轻量化，但发现层没有同步。

建议：短帮助保留简短，同时增加“独立工具”的分类入口，再按具体能力展开参数；legacy 仅承载显式受管流程。技能和插件描述统一围绕任务方法、实际验证与按需参考，不再以状态维护作为主要卖点。

验收场景：从根帮助经过一个分类入口能找到 DOCX 和导出，再进入具体参数；不需要阅读受管许可、领取和证据章节。根帮助仍保持简短，不把全部旧帮助搬回来。

**A05｜受管规则加载把执行依赖闭包当成当前阅读范围——随后优化**

适用范围：显式使用旧受管编排。默认宿主模式不调用此计划，不能把这里的负载算到所有默认 CR 上。

[buildRuleLoadPlan](../core/tools/aidlc-rule-load-plan.ts) 第 49—55 行仅接收 scope、可选阶段、execution profile 和目标阶段；第 86—108、145—162 行将目标及所选依赖的递归闭包全部放入 `load_now`。[实际编排调用点](../core/tools/aidlc-orchestrate.ts) 第 5789—5795 行没有传入 UI 分支条件、已跳过实例或本会话已读取内容。[续作协议](../core/knowledge/protocols/common-token-management.md) 第 10 行要求按 `load_now` 加载规则。

对当前真实图和函数调用的结果如下。没有设置持久 execution profile，使用实现的兼容默认选择；不是模拟任意新工作流策略。

| Scope | 当前目标 | `load_now` 文件数 | 文件原始字节总量 |
|---|---|---:|---:|
| feature | workspace-detection | 1 | 2,965 |
| feature | application-design | 10 | 159,220 |
| feature | code-generation | 5 | 88,387 |
| feature | build-and-test | 7 | 129,042 |
| feature | operations-authorization | 10 | 140,502 |
| bugfix | code-generation | 4 | 74,684 |
| bugfix | build-and-test | 6 | 115,339 |

`application-design` 的十份文件同时包含 Figma 读取、Figma 生成和 HTML Mock 生成。后两支在阶段定义中分别带有 `ui_mode_figma` 与 `ui_mode_html_mock` 条件，规则加载器没有消费这些条件。这里确认的是加载计划包含两支，并非引擎一定执行两支。

这些字节只统计计划列出的 stage 文件，不含后续引用的知识文件；也没有证明宿主实际把所有字节都读入，更不能当成 token 数或耗时。它们足以证明当前计划只延后未来节点，没有做到按当前选择及阅读需要收敛。

建议：保留执行图及其证据依赖，把“必须验证上游成立”与“必须重新阅读上游全部生成步骤”分开。当前阶段加载当前操作、适用质量约束和必要输入引用；已完成上游优先读取相关结果，已明确不适用分支仅保留判断依据。会话已有可用上下文可复用，失去上下文或来源变化后按需重读。不要为去重再建一套强制持久阅读凭据。

验收场景：选择 HTML 分支的应用设计不加载 Figma 操作步骤；已完成需求的代码阶段不要求重读全部需求生成指令；新会话仍能取到必要约束和上游事实；任何优化都不绕过原有实际条件、授权和证据验证。

**A06｜Provider 知识按兼容性过滤，尚未按任务相关性分层——随后优化**

适用范围：显式绑定离线知识 Provider 的受管路径，无 Provider 的默认项目不受影响。

[loadProviderKnowledge](../core/tools/aidlc-provider-knowledge.ts) 第 65 行输入只有 plan/node；第 81—90 行读取同一 topic 下所有符合模块依赖条件的章节。[协议](../core/knowledge/protocols/provider-offline-knowledge.md) 第 92 行要求将返回的全部章节放入当前 execution context 后确认，第 95 行据此决定是否派发阶段。

目前已有的 `requires` 解决“该模块版本是否适用”，并不表达“这次任务是否需要章节全文”。4 MiB 上限是载荷保护，不是上下文相关性控制。包作者可以拆分 topic，但同一 topic 内仍没有先读目录、再按目标选择的接口。本次没有运行实际 Provider 会话，也没有把某个包的磁盘总量宣称为实际上下文负载。

建议：区分必须遵守的基础约束、章节目录和按任务展开的操作说明；允许按当前目标选择适用章节，再把实际选择集合绑定到既有 delivery 摘要和确认语义。选择机制不能遗漏必需约束，不能跳过锁定版本、来源摘要或真实批准，也不能把摘要回传当成模型已经理解。

验收场景：同一兼容模块中，任务只调整持久化查询时，获得基础约束及相关章节，不自动加载无关消息或管理界面详解；目标转向消息处理时能继续展开；锁或所需章节变化仍使对应确认失效。

**修复顺序与保护范围**

1. 先处理默认路径的 A01—A04：分开业务 Patch 与受管契约，限制局部依赖分析范围，重写两份主要指南的默认正文，补齐独立能力发现入口和描述。这直接服务于普通 CR、局部功能和文档任务。
2. 再处理 A05：从现有阶段条件和真实输入出发改进阅读计划，保留执行依赖判定。先以相斥 UI 分支及已完成上游为回归场景，不建立通用 token 硬停止门禁。
3. A06 随 Provider 协议演进处理：先确定基础约束与可选详解的表达及选择校验，再改确认集合；不能仅让宿主少读一部分却继续确认原来的完整载荷。

期望的信息层次是“目标和必要约束 → 当前任务方法与业务参考 → 具体输入及相关验证 → 显式选择的受管契约”。不需要新的统一目标状态机、流程审批层或与现有任务说明并存的追踪文档。
