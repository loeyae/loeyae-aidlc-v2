# AI-DLC 关键词指南

## 默认：宿主直接实施

普通请求遵循[宿主执行协议](../core/knowledge/protocols/host-execution.md)。已有 CR、流程目录或历史证据不自动选择受管模式；已有目标、验收和授权直接沿用。

| 场景 | 常见表达 | 默认动作 |
| --- | --- | --- |
| 开始新工作 | `使用 AI-DLC`、`开始新工作` | 读取相关需求与代码，用宿主工具连续实施；可选 `work` 获取只读上下文 |
| 继续工作 | `继续上次工作`、`继续当前项目` | 核对当前 Git、实际代码、验证及待办，在已有授权内继续 |
| 分工 | `选择开发单元`、`我负责这个模块` | 明确修改范围与协作边界；有重叠写入时使用独立分支或 worktree |
| 关键决定 | `确认架构方案`、`批准部署方案` | 只询问尚未授权的重大决定，记录真实答复，已有批准直接沿用 |
| 代码审查 | `代码审查`、`review` | 审查实际变更和相关验证，提供可定位的问题与结论 |
| 构建测试 | `构建`、`测试`、`验证` | 运行实际需要的命令，引用真实结果；只复验受影响或尚未验证的内容 |
| 提交与合并 | `准备合并`、`提交并推送` | 按用户授权与项目要求处理 Git 操作，验证结果不代替操作授权 |
| 暂停 / 恢复 | `暂停 AI-DLC`、`恢复 AI-DLC` | 遵循用户暂停或继续指令，通过宿主保留必要进度 |
| 查看进度 | `AI-DLC 当前进度` | 从实现、实际验证和已有任务说明报告范围及待办，区分实施、验收、提交/合并和 CR 收口 |
| 缺陷修复 / 重构 | `修复缺陷`、`无行为重构` | 直接修改受影响实现并做定向验证 |
| 变更请求 | `发起变更请求`、`需求变更` | 按[CR 协议](../core/knowledge/protocols/change-request-process.md)追溯范围、决定与验收；“走 CR”不自动启用阶段引擎 |
| 清理历史 CR | `合并历史 CR 文档`、`清理遗留 CR 文件` | 按 CR 协议核实关闭、必要合并和记录持久化；仅实施完成或信息未提交时保留 |
| 结束或交接 | `归档当前工作` | 在现有任务说明中保留必要结论与下一步，按项目约定整理 |

## 显式受管兼容

只有用户明确要求维护旧受管记录时，才使用下列命令及其原有权限和证据约束。

| 场景 | 常见表达 | 执行动作 |
| --- | --- | --- |
| 开始新工作 | `使用 AI-DLC`、`开始新工作`、明确说明要实现或修复的内容 | 以 `orchestrate next --scope <scope> --work "<描述>"` 启动 Markdown workflow |
| 继续工作 | `继续上次工作`、`继续当前项目` | 先查看当前 workflow、目标和领取；按需绑定或交接，再调用 `orchestrate next` 并展示 `handoff_prompt` |
| 选择单元 | `选择开发单元`、`我负责这个模块` | 使用 `unit list` 或 `unit select` 记录成员与分支 |
| 人工审批 | `确认架构方案`、`批准部署方案` | 展示影响与质量证据；用户明确批准后以 `--user-input Approve` 报告 |
| 代码审查 | `代码审查`、`review` | 生成 review evidence，覆盖实际变更路径 |
| 构建测试 | `构建`、`测试`、`验证` | 运行真实命令并以 controlled Evidence 记录结果 |
| 合并准备 | `准备合并`、`merge plan` | 创建 worktree merge plan，由人执行实际 merge |
| 暂停 / 恢复 | `暂停 AI-DLC`、`恢复 AI-DLC` | `orchestrate park` / `orchestrate next --resume` |
| 查看进度 | `AI-DLC 当前进度` | `orchestrate next --status` 或 `runtime summary` |
| 缺陷修复 / 重构 | `修复缺陷`、`无行为重构` | 以适用的 `bugfix` / `refactor` scope 启动；涉及已批准行为的语义变更时按变更契约处理 |
| 变更请求 | `发起变更请求`、`需求变更` | 按 `core/knowledge/protocols/change-request-process.md` 分流；已有代码基线的语义变更走 CR1—CR5 |
| 清理历史 CR | `合并历史 CR 文档`、`清理遗留 CR 文件` | 同样遵守 CR 协议的统一关闭与清理条件，不以阶段完成代替验收 |
| 结束并开始新工作 | `归档当前工作` | 先 `park`（运行中时），再 `orchestrate archive` |

默认实施和兼容模式说明见[实施指南](aidlc-ai-tools-implementation-guide.md)。

受管单工作流的状态和审计位于 `aidlc/active/aidlc-state.md` 与 `aidlc/active/audit.md`；拆分布局还包含 registry 及各工作流的状态和领取记录。默认执行不为这些记录补建流程。
